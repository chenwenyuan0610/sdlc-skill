# 測試案例涵蓋範圍（正向 + 反向 + 紅軍測試）

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

> **這份檔案解決什麼**：`dev-setup`／`system-design`／`change-request` 產出的「測試描述」、`qa-handoff` 實際撰寫執行的測試，語意上都容易只涵蓋「使用者照規格操作」的正向路徑——因為描述測試時很自然會用「這個功能應該怎麼運作」的語氣寫，反向/誤用情境不會自動出現。這份檔案定義最低要涵蓋的反向案例類別，以及綠地專案額外要做的紅軍測試。
>
> **誰引用它**：`dev-setup` 附加產出（測試描述）、`system-design` 演進支線測試描述、`change-request`「在既有範圍內」測試描述、`qa-handoff` 步驟 25-27（撰寫與驗收）。**本檔是這條規則的唯一擁有檔**，別處只放指標。
>
> **觸發脈絡**：cloud-oa-system 專案 ISSUE-5（見框架缺陷登記簿 `FD-02`）——`implementation-handoff` 完工三關全過、300+ 單元/整合測試全綠、Lead 執行的 end-to-end 驗證也全部通過，但使用者手動測試仍發現至少 6 項真實缺陷（檔案數量未擋、重複檔案未擋、無法移除錯誤檔案、資料顯示錯誤、樣式回歸、資料源選擇方式錯誤）。根本原因：所有測試都只驗證了「照規格操作」的正向路徑，沒有系統性涵蓋「使用者會怎麼誤用」的反向情境。

## 規則一：測試描述／測試案例 MUST 同時包含正向與反向情境

**不分綠地／棕地專案，任何走 `dev-setup`／`system-design`／`change-request`／`qa-handoff` 的專案都適用。**

- **正向案例**：使用者依照規格操作，系統應正確完成。
- **反向案例**：使用者做了不合規格的操作，系統應該正確防呆/阻擋，並給出清楚錯誤訊息。

反向案例 MUST 至少涵蓋以下類別（不限於這些，依功能實際情況增列；沒有對應情境的類別可以寫「不適用＋理由」，不能整類跳過不提）：

| 類別 | 說明 | 例子 |
|---|---|---|
| 邊界數量 | 輸入數量有最低/最高限制，卻給了不合法數量 | 檔案上傳要求至少 2 份才能送出，只選 1 份時系統應阻擋並提示 |
| 重複／衝突輸入 | 同一份資料被重複提供 | 選了同一檔案兩次應被偵測並拒絕，不是靜默接受 |
| 錯誤修正路徑 | 使用者做錯後要能修正，不是只能整個重來 | 選錯檔案要能單獨移除，不是被迫清空整批重選 |
| 資料一致性／合法性 | 欄位值超出合法範圍、格式不符、跟既有資料源對不上 | 沿用既有資料源（如下拉選單）時，要驗證選項確實來自該資料源、不是自由輸入的殘留 |

## 規則二：綠地專案 MUST 額外涵蓋紅軍測試（Red Teaming）

**只有創世模式（`dev-setup` 有觸發，`docs/sdlc-mode.md` 標 `mode: full` 或沒有宣告檔）適用**——演進模式（`change-request`/`system-design` 的既有系統增量變更）不強制，但發現攻擊面擴大（例如新增對外端點、新增檔案上傳）時 MUST 依風險自行評估是否比照辦理，不得因為「演進模式」就自動排除。

紅軍測試模擬真實攻擊者，MUST 涵蓋：

- **繞過防呆機制**：嘗試用非正規手段（直接呼叫 API 跳過前端驗證、竄改請求參數/欄位）繞過規則一的防呆檢查，驗證**後端本身也擋得住，不能只靠前端**——前端驗證永遠可被繞過，這是預設假設不是需要另外證明的前提。
- **偽造／竄改信號**：模擬釣魚、偽造成功回應（假綠燈）、竄改回傳碼／狀態碼，驗證系統不會被騙、不會把偽造信號當真。
- **偵測與通報**：驗證攻擊行為發生時，系統是否有偵測、記錄、觸發警示/通報，不是靜默放行或靜默失敗——「擋下來但沒有任何紀錄」不算完整通過。

紅軍測試案例 MUST 由 `qa-handoff` 步驟 27（驗收測試）覆核，比照一般驗收測試同樣的獨立角度要求（實作者不得自己驗自己）；高風險項目（認證、金流、對外開放端點）加派 `sdlc-verifier`（`target=security`）。

## 規則三：三層驗證缺一不可

每個功能的測試 MUST 同時驗證：

1. **前端提示**——使用者操作當下看得到的錯誤/警告訊息。
2. **後端阻擋**——不能只靠前端擋，後端本身也要正確拒絕不合法請求（前端驗證可被繞過，見規則二）。
3. **修正路徑**——使用者做錯後，能不能在畫面上自行修正並重新完成操作，不是卡死或只能整個重來。

只驗證其中一兩層不算完整覆蓋；**規則一的反向案例表沒有標明涵蓋這三層的，視為未完成**。

## 規則四：測試有效性的改壞實驗（Phase 6）

測試寫完後、驗收通過前 MUST 執行。反向輸入測試與本實驗不同：本實驗保留測試、故意改壞產品行為，驗證測試是否能抓到指定錯誤；通過不代表所有錯誤都已涵蓋。

1. **正常版本基線**：以本次待驗版本（包含未提交變更）建立獨立副本，先跑選定測試並確認通過；原本失敗就先處理，跑不起來記 `BLOCKED`。
2. **獨立選題**：由未參與本次產品及測試修改的覆核者，從需求／AC 反推「做錯會長什麼樣子」。列出本次關鍵行為、修復的 bug 與容易假綠燈的斷言，對每個選定情境記錄需求、選題理由、故意製造的錯誤及預期失敗的測試／斷言；選題依風險，不要求全專案 mutation 或固定數量，不只挑容易變紅的測試。未選範圍與理由也須揭露；真正無可變異行為（如純文字文件）依 `severity-format.md` N/A 條款處理，缺工具或時間不是不適用。
3. **一次改壞一件事**：只改隔離副本的產品邏輯，保持測試不變；看 diff 確認精確位置及僅有預期改動，確認測試載入的是改壞副本而非原目錄／舊建置，再執行同一測試指令。每個情境從已還原的基線開始，不能累積多個改壞點。
4. **判讀紅燈原因**：只有對應需求的目標斷言因預期錯誤失敗，才算抓到。語法／匯入／環境錯誤、其他無關斷言失敗都不算；修正實驗後重驗。仍全綠時，先查修改是否生效、路徑是否執行及是否為等價變異；等價變異須有理由並重選有效情境。確認錯誤已生效仍全綠，就是測試缺口，記 `NEEDS WORK`（符合 Critical 條件則 `FAIL`），不得宣稱保護有效。
5. **修測試並重驗**：缺口由測試作者修正，覆核者重新對新測試版本跑正常 → 改壞 → 還原；覆核者不得自行修原專案測試後再替自己的修正背書。還原產品邏輯後同一組測試必須通過；必要情境尚未完成、阻塞或未確認時不得收關。
6. **證據綁定版本，複審不能只看 diff**：每組實驗證據 MUST 能識別當時的產品程式、測試與會影響該情境的 fixture／設定版本（commit、快照來源或雜湊均可）。證據產生後，只要相關產品行為、測試、fixture 或設定又被修改，受影響情境的舊證據就失效；複審 MUST 在最終候選版本重新跑正常 → 改壞 → 還原，不得只確認 finding 的 diff 已照建議修改。覆核者須重新評估修正帶來的風險：仍適用的既有選題要重跑，新增或改變的風險要補選題；不要求固定 mutation 數量，也不因無關的純文字／歷史註記改動重跑不相干情境。若變更宣稱淘汰或換寫舊契約／術語／格式，另依 `traceability.md`「規則六」做全域殘留掃描。

### 隔離與角色權限

reviewer／verifier 可建立獨立暫存副本，僅在副本內修改實驗產品檔、執行測試及產生實驗輸出。副本不得透過 hardlink／symlink／junction 回寫原專案，測試資料與服務也須隔離，不得連到正式環境造成寫入。原專案在實驗前後記錄 `git status`（若適用）及相關程式碼、測試、設定的雜湊，保留既有未提交變更；不得 reset／checkout 原專案來清理實驗。驗證無實驗改動留在原專案後，將證據交 Lead 落檔；reviewer 的同一工單 ID 結案紀錄更新仍僅依 `ticket-spec.md` 硬規則 5，verifier 不取得工單寫入權。角色沒有所需工具時回報 Lead 改派具能力的獨立角色；未實跑就是未驗證。

### 證據與判定

每個情境記錄：需求／AC、覆核者、選題理由、待驗產品／測試／fixture 版本或雜湊、副本來源、改壞位置與 diff、預期失敗斷言、各次指令／退出碼／關鍵輸出、實際判讀、還原結果及原專案未變動證據。Lead 放入 `docs/handoff-log.md` 的 Phase 6 分節或其連結的證據檔。未檢查範圍、無法執行原因與待辦須明列；不得把文字推演記成實跑，也不得只留「測試有效」的結論。實驗中預期的紅燈是實驗證據，不是交付版本 FAIL，也不算重跑碰運氣；正常／還原版本不穩定仍依 `severity-format.md` 判定。

### 依情境檢查常見盲點

- 模擬 UI 須保留被驗互動的真實顯示／隱藏規則，避免不開選單也能通過。
- 宣稱排除干擾項時，fixture 須讓放寬選擇器真的會選錯；例如 `.first` 情境把干擾項放在目標前。
- 需求要求精確文案／代碼時，比對完整字串或集合成員，不能用會誤中子字串的斷言。
- 宣稱去重時，直接檢查集合內容、數量／唯一性，不只驗證對重複不敏感的衍生值。

## 規則五：設定所依賴的外部狀態

本次功能若以設定值描述或要求外部環境狀態（例如後台語言、時區、服務版本或功能開關），需求／輕量 spec MUST 定義預期狀態、建立該狀態的責任者（產品或使用者／維運）、程式確認實際狀態的方式，以及狀態不符、無法讀取或切換失敗時的行為。設計與測試描述沿用這份契約；責任未定時先釐清，不自行假設產品有權切換。純粹控制程式內部行為的設定不觸發本條。

- **整合情境**：在授權的測試環境建立並確認真實初始狀態，涵蓋設定與實際狀態相符、不符，以及無法確認狀態。產品負責切換時，另驗證切換成功與失敗；由使用者／維運負責時，驗證程式依契約檢查並提示或拒絕。記錄初始狀態、預期值、產品入口、最終觀察與結果；僅更換設定值或 mock 回傳值，不能當作已驗外部狀態。
- **實際執行路徑**：整合驗收 MUST 經過承諾該行為的產品入口（例如登入後流程），確認狀態檢查／切換確實接上。可另直接呼叫共用產品函式做元件測試，但這不能取代入口整合證據。測試準備可以建立初始狀態；若切換是待驗產品責任，不得由驗證腳本預先切好或另寫一套切換邏輯代替產品。
- **獨立判定結果**：從外部可觀察狀態（如後台畫面、查詢 API 或實際操作結果）確認效果；不能只相信產品函式的成功回傳、腳本印出的成功訊息，或拿同一份內部對照表計算預期答案。切換失敗或前提未滿足時，同時驗證錯誤呈現與後續操作符合契約；依賴該前提的資料寫入不得繼續。
- **證據界線**：僅有模擬環境時標明驗證範圍；必要的外部整合跑不起來依既有規則標 BLOCKED，不能用單元測試綠燈代替。此規則不授予變更外部環境的新權限，沿用專案既有測試授權。

## 落在哪個產出物

- `dev-setup`/`system-design`/`change-request` 產生的「自然語言測試描述」：每條反向案例描述 MUST 標明屬於規則一表格的哪個類別（或說明為什麼不適用）。
- `qa-handoff` 步驟 25-27 撰寫的真正測試：反向案例（含紅軍測試，若適用）MUST 是可執行的測試案例，不是只在文件裡提過一句——**跟正向案例用同樣的「可重複執行」標準**，不因為是反向情境就允許只用文字描述帶過。
