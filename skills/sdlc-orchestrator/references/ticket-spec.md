# 工單規格（四種工單的共用格式）

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

> **這份檔案解決什麼**：以前 bug 記在測試階段、回饋記在維運階段、跨包狀態記在變更分析、工作票在需求發想——**四處各記各的，格式不一樣、狀態詞不一樣、找不到全貌**。這份定義四種工單共用的編號、欄位、狀態機。
>
> **這是規格不是流程**——它不會被「呼叫」，是各階段在自己的持久化段引用它。工單資料放專案的 `docs/`，不跑完整流程也能單獨用這份規格。

## 誰可以開工單

**任何人都可以提出。** 流程上不需要額外核准；實際落盤仍受外部系統 ACL 與當前角色的唯讀邊界限制。看到問題就登記——**登記的門檻必須低於「忍一下算了」的門檻**，否則問題就會消失在個人記憶裡。唯讀 reviewer／verifier 發現新問題時，在報告中提供六欄草稿與證據；無權安全配置流水號時，ID 寫「待編號」，由 Lead 或該保存位置的既有授權者配置正式 ID 並建立 `proposed`。這是代為落盤，不改變發現者，也不授權覆核角色寫原專案。

唯一的門檻是**證據欄要填**（見下方）。那不是為了刁難，是為了讓後面接手的人看得懂。

## 四種工單

| 類型 | 編號 | 記什麼 | 放哪 |
|---|---|---|---|
| **工作票** | 專案工單系統的 issue 號（例 `ISSUE-42`）；子項目寫成 `ISSUE-42／後端API` | 要做的事 | 工單系統；狀態回寫 `docs/handoff-log.md` |
| **缺陷** | `BUG-nn` | 系統行為不對 | `docs/handoff-log.md` 測試分節 |
| **維運回饋** | `FB-nn` | 上線後使用者／監控回報 | `docs/feedback-log.md` |
| **框架缺陷** | `FD-nn` | **流程規則本身**有問題（規則卡住人、規則矛盾、判準模糊、缺一步） | 使用環境的框架缺陷登記簿（位置由綁定層指定；本包預設 `framework-defects.md`） |

**編號規則**：各類型各自流水，`nn` 從 01 起、不補洞、不重用。**工作票沿用既有工單系統的號，不另發**——全程只在流程第一關開一次票，後續工作項目都掛同一個號底下的子項目。

## 共用欄位

每一筆工單，不分類型，都要有這六欄：

| 欄位 | 填什麼 | 空白的後果 |
|---|---|---|
| `ID` | 依上表編號規則 | 沒有 ID 就沒辦法被引用、被追蹤 |
| `發現於` | 哪個階段／哪次工作／哪個環境 | 之後看不出當時的脈絡 |
| `描述` | 一句話說清楚是什麼問題 | 三個月後自己也看不懂 |
| **`證據`** | **具體的東西**：檔案位置、實際錯誤訊息、重現步驟、當下的情況。**不是感覺、不是「好像有問題」** | **這欄空白 = 不受理。** 沒有證據的不是問題回報，是抱怨 |
| `status` | 見下方狀態機 | 不知道這筆還活著沒 |
| `負責人` | 認領的人；還沒人認領就留空 | 留空可以，但**不能一直留空**——見「不要讓它爛在那」 |

⚠ **欄位太多會讓表讀不動**：某一類型若把六欄全塞進同一張表會過寬，**可以拆成兩張表**（主表放 `ID`／`發現於`／`描述`／`證據`／`status`，另一張角色表放 `負責人` 與該類型額外的角色欄），但**六欄一個都不能少**，且兩張表以 `ID` 對應。

⚠ **六欄的適用範圍＝「一張票本身」，不是「引用票號的每一筆記錄」。** `handoff-log.md` 裡的完工紀錄（`ISSUE-42／後端API`、完成日期、品質門禁結果）記的是**某張既有工單底下某個子項目的狀態**，它引用票號、不是新開一張票，**不適用六欄**。同理，設計文件裡的任務子項目清單也不是票。**判準：這一列有沒有自己的 `ID`？** 有自己的 ID（`ISSUE-nn`／`BUG-nn`／`FD-nn`／`FB-nn`）＝是票，六欄全套；只是引用別人的 ID ＝不是票，照該產出物自己的格式記即可。

## 狀態機

```
proposed  ──►  accepted  ──►  in-progress  ──►  fixed
   │
   └──────────►  rejected（要寫為什麼不做）
```

| 狀態 | 意思 | 誰能改成這個 |
|---|---|---|
| `proposed` | 已登記，還沒決定要不要處理 | **任何人**（含 AI） |
| `accepted` | 決定要處理 | **人**。AI 不得自行標 accepted |
| `in-progress` | 有人在做了 | 認領的人 |
| `fixed` | 做完了，**要註明改了什麼** | **覆核者，不是做的人**（硬規則 5）——修正者做完後留在 `in-progress` |
| `rejected` | 決定不做，**要寫為什麼** | 人 |

**五條硬規則**（防止機制被玩壞）：

1. **證據欄空白 = 不受理。** 這條防止憑印象發明問題——尤其防 AI 生出「修正從未發生過的失敗」的假規則。這是每次登記/覆核都要重查一次的機械掃描，MAY 寫成腳本輔助（判準與做法 → `tooling-reuse.md`），沒有腳本時一樣要靠人工核對做到同樣結論。
2. **AI 在提案／決策階段只能自行建立 `proposed`；不得自行決定 `accepted`／`rejected`。** **能提議改規則的人，和拍板說「可以改」的人，必須分開**——否則等於讓執行者自己放寬對自己的約束。本條不禁止已由人標記 `accepted` 後，AI 認領工作並依狀態機標 `in-progress`；也不禁止未參與修正的 AI 覆核者在判定 PASS 後，依硬規則 5 的窄化寫入例外標 `fixed`。
3. **`accepted` 未標記前，MUST NOT 動規則。** 登記 `proposed` 之後、有人明確標 `accepted` 之前，任何人（含 AI）都不得開始改規則本身——否則「登記」只是形式，實際還是誰發現誰就地改。
4. **修正者宜與發現者不同。** 同一人扮完發現與修正時，MUST 在角色表留痕並在覆核時特別檢視——自己找出來的問題，自己最容易用自己順手的方式解掉。
5. **`fixed` MUST 由非修正者標記。** 結案權與執行權分離——動手改的人不能自己宣告改完了。修正者做完後留 `in-progress`，由覆核者確認後才改 `fixed`，並填入覆核者。**這條與發現者是誰無關**：不論缺陷由 AI 掃出或由人口頭指出，都走同一套關卡。

   **覆核對原專案維持唯讀；唯一例外是覆核者判定 PASS 後，更新「同一工單 ID」的結案紀錄。** 工單保存位置依上方「四種工單」表：工作票更新工單系統及 `docs/handoff-log.md` 的狀態回寫；`BUG-nn` 更新 `docs/handoff-log.md` 測試分節；`FB-nn` 更新 `docs/feedback-log.md`；`FD-nn` 更新綁定層指定的框架缺陷登記簿。外部工單系統仍受既有權限控制，本規則不授予新權限；沒有權限時必須由具權限、且已核對 PASS 證據的非修正者完成外部狀態更新，不能以本機回寫冒充外部工單已結案。

   **允許修改的是同一 ID 的兩類邏輯紀錄，不限定為同一實體列：**
   1. 狀態紀錄：`in-progress` → `fixed`、完成日期、以及「改了什麼」。
   2. 角色／覆核紀錄：覆核者與覆核證據。若欄位和狀態在同一列，只改該列；若依「共用欄位」規則拆成主表與角色表，可同時修改兩張表中同一 ID 的對應列。

   判定 `NEEDS WORK`／`FAIL` 時完全不得寫入原專案。PASS 後也不得修改程式碼、測試、需求、設計、其他工單 ID，或同一工單的其他欄位。寫入後 MUST 檢查 diff，逐項確認只碰到規格指定的保存位置、同一 ID、上述允許欄位；任一超出即不合格。使用環境可另加機械檢查輔助，但本規則不依賴腳本存在。

   **PASS 必須來自票種對應的覆核流程，不能只寫一個 PASS 字樣：**
   - 工作票／`BUG-nn`：依 `qa-handoff` 的測試、回歸與獨立覆核證據。
   - `FB-nn`：依 `ops-feedback`，由非修正者重跑原回饋的重現步驟並確認直接受影響的回歸檢查通過。
   - `FD-nn`：依 `rule-eval` 完成獨立情境覆核與反向檢查。
   各 phase 可以再縮限可寫角色；Phase 6 只有 `sdlc-reviewer` 能執行結案寫入，`sdlc-verifier` 即使回報 PASS 也不得寫原專案工單。

   **工作票同步順序**：需要同步外部工單系統時，由具既有權限的非修正者先核對 PASS 證據，再依環境可安全執行的順序更新外部系統與 `handoff-log.md`。任一處尚未更新就不得宣稱同步完成；未更新處維持 `in-progress`，並在覆核報告記錄「PASS、等待狀態同步」與失敗位置，不能自創第五種工單狀態。同步完成後再做跨位置核對。

隔離副本的改壞實驗另依 `test-case-coverage.md` 規則四；它不授權修改原專案的程式碼、測試或工單，也不改變結案權。

## 不要讓它爛在那

登記簿獨立，**但排程不獨立**。

- 每輪工作開始前掃一次，把 `proposed` 拉進當輪佇列排序
- 改善清單放在主流程外面、等「有空再看」，結果就是**永遠被跳過**
- `proposed` 超過兩輪沒被碰 → 要嘛認領、要嘛明確 `rejected` 寫清楚為什麼，**不要無限期掛著假裝之後會做**

## 框架缺陷（`FD-nn`）的特別說明

這類最容易被忽略，因為它不是「產品有問題」而是「**規則有問題**」，撞到的人通常會自己繞過去。

**觸發判準只有一條**：

> **規則本身把執行者卡住，而卡住的原因不是使用者做錯。**

**撞到當下**：不要就地改規則、不要停工 → 登記一列（`proposed`）→ 用最接近的合理解讀把工作做完。

**不算框架缺陷**（走各階段既有的停止條件，不要塞進來）：
- 專案產出物本身有問題（設計文件缺內容、需求不清）→ 回上一個 phase，具體的狀態回寫與連鎖回開規則 → `sdlc-entry.md`「回歸」段
- 技術問題、環境問題 → `debug`
- 需求本身模糊 → `converge`

⚠ **兩者可能同時成立**：內容確實錯了（回歸），且錯的部分原因是框架沒逼問到位（框架缺陷）——這種情況兩條都要走，不是二選一，細節見 `sdlc-entry.md`「回歸」段「跟框架缺陷的界線」。

完整說明與實際登記簿 → `framework-defects.md`。

## 跟需求編號的關係

工單號管**排程**（會合併、會關閉、會重開），需求編號管**追溯**（一經確認永不變）。**兩者分離，不要混成一套**——工單一合併，追溯就對不上帳。

缺陷與框架缺陷若源自某條需求，在描述欄註明是哪一條即可，不需要另外建對應表。
