# Implementation Handoff — SDLC Phase 5 開發實作

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 21-24。**Lead 依票直接執行或派工，範圍達門檻 MUST 派工**（判斷標準見步驟內「誰做」；分級表 / 模型選擇 / 派工 prompt 附帶 dev skill 規則 → `../sdlc-orchestrator/references/agent-teams.md`）。

**綁定層優先**：使用環境的 CLAUDE.md / AGENTS.md 若對本 phase 定義了工具綁定（例如「Phase 5 → 走某某既有開發流程」的綁定表），一律照綁定走；本 skill 的內建做法只是「無綁定專案」的 fallback。

## 觸發條件

**兩條合法入場路徑，任一成立即可進入**——⚠ 只認第一條會把既有專案的每一次變更都退回 Phase 4，而 Phase 4 又會把它退回 Phase 3／2：

| 路徑 | 前置 | 實作依據 |
|---|---|---|
| **創世模式** | 開發排程已定（來自 `dev-setup`） | `system-design` 的設計文件 ＋ `dev-setup` 的測試描述 |
| **演進模式**（既有專案，經 `change-request` 分診轉來） | **不經過 `dev-setup`**——既有專案的骨架／版控／排程本來就存在，Phase 4 是創世模式專用 | 「在既有範圍內」→ `docs/change-specs/<變更名>.md` 的輕量 spec ＋ 測試描述 ＋ 程式碼現況基線；「需要新設計決策」→ `system-design` 產出的 design-delta ＋ 該支線一併產出的測試描述 |

- 不適用：**全新專案**還沒排開發前準備 → 先回 `dev-setup`
- 不適用：演進模式但**連輕量 spec／design-delta 都沒有** → 先回 `change-request` 分診

**演進模式下，Exit Criteria 的「與設計文件不符須回寫」對照的是輕量 spec 或 design-delta，不是完整設計文件**（該路徑明文不產生 `docs/` 設計基線）——用實際存在的那份當基準，**不得因為沒有完整設計文件就跳過回寫**。

## 完成條件（Phase Exit Criteria）
4 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 可用的資料庫（若專案不涉及持久化儲存 → 標 N/A 並註明理由）
2. 可運行的後端 API（若專案不提供對外介面 → 標 N/A 並註明理由）
3. 完成的前端元件（若專案無使用者介面 → 標 N/A 並註明理由）
4. 可用的前端頁面（同上）

**標 N/A 的項目不算未完成**，但 **MUST 走 `../sdlc-orchestrator/references/severity-format.md` 的「N/A 條款」三條件**（具體理由＋**實作者以外的角度確認**＋記在產出物裡）——只寫理由、自己標自己過**不算**。四項中至少一項有實質產出即可進 Phase 6——資料分析、CLI 工具、函式庫、韌體等非 web 專案，用該領域的等價產出（分析腳本與輸出、可執行檔、可安裝套件、可燒錄映像）替換對應項目並註明。

## 持久化
每個工作項目完工狀態 MUST 記進 `docs/handoff-log.md`（工單號／子項目名稱，如 `ISSUE-42／後端API`、完成日期、品質門禁結果、**該子項目實作的 `[REQ-nn]`**——追溯規則 → `../sdlc-orchestrator/references/traceability.md`，該檔同時說明什麼情況下不必建表），**用固定標頭 `## Phase 5 — Implementation` 分節**。分節的第一行 MUST 是狀態行 `狀態：進行中` 或 `狀態：完成`——**標頭存在不等於做完**，沒有這一行的話下一個接手的人／agent 會誤判本階段已結束而跳過（`handoff-log.md` 由 Phase 5-7 共用，固定標頭讓下一個接手的人/agent 能單靠檢查這個檔案判斷目前在哪個 phase，不用回想對話）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。

⚠ **本 phase 不可裁剪**：實作與測試是流程裁剪的下限，**`## Phase 5` 分節永遠不得標 `狀態：不適用`**，不論專案宣告哪一種模式（裁剪規則 → `../sdlc-orchestrator/references/tailoring.md`）。

**依賴批次**：`system-design` 步驟16 標記為同一驗收批次的子項目（有依賴關係，如前端依賴後端），可以各自照依賴順序完工並各自記錄完工日期，但這只是「開發完工」狀態——`qa-handoff` 的驗收要等整批都完工才會一起做，不要因為某個子項目先完工就當作它已經可以獨立結案。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測（檔名固定 `docs/<phase>-evidence.md`）、風險清單。
⚠ **累加型紀錄例外**（`change-log.md`／`handoff-log.md`／`feedback-log.md`）：流水帳**沒有「段落語意」可拆、也沒有段落編號可保留**。改用**時間分卷**——超過 200 行時把舊內容整段移到 `<原檔名>-<年份或期別>.md`，主檔保留最近期內容 ＋ 一行分卷索引。**NEVER 為了守行數而刪除歷史。**

## 流程

### 步驟 21：資料庫建置
- ⚠ **動手之前 MUST 先確認「這條指令會打到哪個資料庫」**，並向使用者複述你查到的連線目標（來源：專案設定檔／環境變數／profile），**等他確認才執行**。專案的預設設定指向共用的開發或測試資料庫是常態——不確認就跑 DDL／migration，會改到別人正在用的結構，`ALTER`／`DROP` 類還可能造成不可逆的資料損失。
- ⚠ **MUST NOT 對任何非本機、非本次變更專用的資料庫執行結構變更**。只能動：本機資料庫、容器內的臨時實例、或使用者明確指名的隔離環境。共用 dev／staging／production 一律回報給使用者手動執行，本 phase 不代勞。
- Action：依 DB schema 建立資料庫、資料表
- 誰做：單一票 ≤20 行/單檔/無新依賴 → Lead-direct；範圍較大（多檔/新模組）→ MUST 派 `sdlc-implementer` agent（角色定義檔 `sdlc-implementer.md`，在你安裝時選的**角色檔目錄**下），多張範圍獨立的票平行派，不要序列一張張自己做
- Output：可用的資料庫

### 步驟 22：後端 API 開發
- Action：依 API 規格實作後端邏輯與端點
- 誰做：同上判斷標準
- Output：可運行的後端 API

### 步驟 23：前端元件開發
- Action：依元件清單實作元件（可跨頁重用，先用假資料）
- 誰做：同上判斷標準
- Output：完成的前端元件

### 步驟 24：前端頁面組裝與串接
- Action：把元件組裝成頁面，接上步驟 22 的真實 API
- 誰做：同上判斷標準
- Output：可用的前端頁面

## 完工關卡（三關依序，任一沒過就不算「完成」）

| 關 | 內容 | 誰 |
|---|---|---|
| **1 品質門禁** | 該語言／框架慣用的型別檢查／lint／測試／build，**0 issues**。MUST 附實際 command output——**不接受「跑過了」的口頭宣稱**。<br>**指令從哪來**：創世＝`dev-setup` 已定義並實跑過的那條；演進＝使用環境既有的門禁指令表，或該專案慣用的那組。⚠ **兩者都沒有時，MUST 在動手寫程式之前先定義出來並寫進本次的 `change-specs/` 或 design-delta**——演進模式跳過了 `dev-setup`，沒有人替它定義過這條指令，留到完工才想等於卡在一個從沒存在過的門禁上 | 實作者 |
| **2 獨立覆核** | **MUST 由實作者以外的角色，不分 Tier**（編制、角度、模型選擇 → `../sdlc-orchestrator/references/agent-teams.md`）。⚠ **「Lead 覆核輸出」不算獨立覆核**——Lead 是派工、定範圍、決定怎麼做的人 | 唯讀覆核角色 |
| **3 最小改動確認** | 這次的 diff 有沒有超出票的範圍（順手重構、改到別的模組、無關的格式或依賴變動）。判準：**這一行拿掉的話，本票的驗收條件會不會不過**——不會就該拿掉，真的該修另開一張票。**演進模式 MUST 逐項查** | 同上，覆核者一併看 |

**三關全過，才可以在 `docs/handoff-log.md` 的 `## Phase 5` 分節寫 `狀態：完成`。** 覆核結果 `NEEDS WORK`／`FAIL` → 修完重審，不是記錄一下就放行（四種狀態的定義與防假綠燈三條 → `../sdlc-orchestrator/references/severity-format.md`）。

⚠ **驗收測試不在本 phase**：這三關管的是「寫出來的東西自己站得住」，真正對照需求的測試由 `qa-handoff`（Phase 6）**獨立撰寫並執行**——**兩個 phase 都過才算這次變更做完**，不得因為 Phase 5 三關過了就宣告結案。

**⚠ 版控邊界（本 phase 一體適用，派出去的 agent 也適用）**：**NEVER 自動 `git commit`／`git push`／建立或切換 branch／開 MR**。完工時輸出 diff 與品質門禁 output，交由使用者自己決定要不要提交。理由：這條原本只寫在 `dev-setup`（Phase 4），而**演進模式明文不走那一關**——等於既有專案的每一次變更都沒有人把這條唸出來。使用環境若有更嚴格的版控規則，以那邊為準；但**放寬不算數**。

**測試界線**：開發者 MUST NOT 自行撰寫或修改驗收測試（單元測試以外，涉及驗收/spec 對齊的測試都不行）——這段測試由 `qa-handoff` 依 `dev-setup` 的測試描述獨立撰寫並對照 `requirements-spec.md` 覆核，開發者自己補測試容易不自覺照著自己寫的 code 邏輯走，等於測不出功能不符合規格的情況。

## 停止條件
- 前置條件沒確認就想開始開發 → 停下來，指出缺哪個前置條件。⚠ **「沒走過 `dev-setup`」對演進模式不是缺前置**——照上方入場路徑表判定，演進模式缺的是輕量 spec／design-delta，不是 Phase 4 的產出物；拿創世模式的前置去卡既有專案，等於把每次變更都退回 Phase 1-4 重跑
- 開發過程中發現前面階段（`system-design`/`dev-setup`）的產出有問題 → 明確告知使用者要回哪個 phase 重新確認，不要在已知有問題的情況下繼續往下做
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完

## 下一步
所有票開發完成 → **MUST 接 `qa-handoff`（Phase 6）**。**不自動呼叫**，只是提醒使用者——但要明講這不是可選項。

⚠ **兩條入場路徑的出口相同，測試都不可省。** 演進模式跳過的是 Phase 3-4（設計與開發前準備），**不包含 Phase 6**；不得以「這次變更很小」「只是既有範圍內的實作」為由跳過測試。既有專案的改動落在別人寫的、還在跑的程式碼上，回歸測試的價值比新專案更高。真的連一條測試都寫不出來 → 走 `../sdlc-orchestrator/references/severity-format.md` 的 N/A 條款（具體理由＋實作者以外的角度確認＋記在產出物裡），**不得自行免除**。
