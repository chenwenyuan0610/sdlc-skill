# Change Request — SDLC 增量變更分診（既有專案的演進入口）

**本 skill 不做需求分析、不做設計、不開發**，核心工作只有一件事：判斷這次變更該走哪條路，然後分診過去。不重複 `requirement-scoping`/`system-design` 的邏輯。

**基線是什麼**：優先用 `docs/` 裡的既有需求規格/設計文件當對照基線；**若專案是既有運行中系統但沒有這些文件（例如成立多年、從沒走過這套 SDLC 的舊專案），就用「程式碼現況」當基線**——讀相關的既有程式/schema/API 來理解現狀，據此分診。**不要因為缺 `docs/` 文件就把一個已經在跑的系統當成全新構想退回 `product-discovery`**（那是本 skill 最容易犯的誤判）。「一次性 vs 重複用」的架構意義：技術選型/整體架構這類一次性工作，舊專案早已定案不重做；本 skill 專門接住「重複用」那條——每次變更的需求-delta 與設計-delta 分診。

## 提問規則（分診路由確認一體適用）
向使用者確認走哪條路時 **MUST 選項化**：把三條路做成可勾選項（你判斷的那條放第一個並標「建議」，附一句理由），使用者勾選或回編號即可；自由補充永遠允許——選項是降低回答成本，不是限制答案。
**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：追到**維度覆蓋表每一列都標「已答」或「使用者說不適用」**才算問完（不是「使用者沒再補」；還有任何一列是「進行中」或「未走」都不算）；動手前 MUST 列出自決事項清單與**殘餘猜測清單**，猜測清單非空不得產出。

## 觸發條件
- 專案已存在一個運行中/已建置的系統（有 `docs/` 文件用文件當基線；沒有就用程式碼現況當基線），現在出現新的變更需求
- 不確定這次變更是「既有範圍內的小變更」還是「需要新設計決策」還是「其實是新方向」
- 不適用：**完全沒有任何既有系統的全新構想** → 這才是新方向，用 `product-discovery`（注意：舊專案缺 `docs/` 文件 ≠ 新構想）
- 不適用：變更明顯瑣碎（例如已知就是改一行 constant）→ 直接進開發，不需要先分診

## 完成條件
已經判斷出這次變更該走哪一條路，且使用者確認（依上方「提問規則」選項化）：
1. 讀到既有需求規格書/設計文件的相關內容（優先搜尋專案 `docs/` 資料夾找既有檔案，找不到才向使用者要內容/摘要）
2. 對照後給出明確路由判斷（見下方三選一）
3. 若判斷「既有範圍內」，已產出輕量 spec/ticket，且**已附測試描述——不分 Tier，一律要**（Tier 0-1 一句話即可；見下方步驟 2 表格與「測試不可省」硬性關卡）

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測（檔名固定 `docs/<phase>-evidence.md`）、風險清單。
⚠ **累加型紀錄例外**（`change-log.md`／`handoff-log.md`／`feedback-log.md`）：它們是流水帳，**沒有「段落語意」可拆、也沒有段落編號可保留**，套上面的拆檔規則會卡死。改用**時間分卷**——超過 200 行時把舊內容整段移到 `<原檔名>-<年份或期別>.md`，主檔保留最近期內容 ＋ 一行分卷索引。**NEVER 為了守行數而刪除歷史。**

## 流程

### 步驟 1：取得基線脈絡（三層 fallback，不要在第一層就放棄）
0. **出口**：連「這次變更是什麼」本身都講不清楚（不是找不到基線文件，是需求本身模糊）→ 停下來，轉 `converge`，等共識/路由確定後再回來走下面三層 fallback。
1. 先搜尋專案 `docs/` 找既有需求規格書/設計文件——有就用它當基線。
2. 沒有 `docs/` 文件、但專案有既有程式碼 → **用程式碼當基線**：讀跟這次變更相關的既有模組/schema/API/元件，理解「現在長怎樣」，據此分診。這是舊專案的正常情況，不是錯誤。
3. 只有在「連既有系統都不存在（純全新構想）」時 → 才停止並建議 `product-discovery`。
判斷「是不是既有系統」看得到程式碼/可運行的服務就算，不是只看 `docs/` 有沒有檔案。

### 步驟 2：對照判斷（三選一）

| 判斷 | 條件 | 路由 |
|---|---|---|
| 在既有範圍內 | 不涉及新的 DB/API/架構/元件/模組決策，只是既有設計下的具體實作 | Lead-direct 寫輕量 spec + ticket。**測試描述不分 Tier 一律 MUST 有**——依既有需求規格書／程式碼現況基線設計，格式同 `dev-setup` 的測試描述（例：「呼叫 `/api/orders/search` 帶 `status=pending`，應該只回傳待處理的訂單」），**寫在程式碼之前**，給後續驗收用，不是給開發者事後參考；Tier 0-1（改一行 log、調 config 值、修 typo）寫一句話即可，Tier 2 以上（Tier 定義 → `../sdlc-orchestrator/references/agent-teams.md`）逐條列。**去處**：帶著輕量 spec 進 `implementation-handoff`（Phase 5），**不必**走 `requirement-scoping`／`system-design`／`dev-setup`（Phase 4 是創世模式專用，既有專案的骨架／版控／排程本來就存在）；使用環境的 CLAUDE.md/AGENTS.md 若對 Phase 5 有工具綁定就照綁定走。**這條路不產生 `docs/` 設計基線**（因為沒有新設計決策）——舊專案要補基線是走下面「需要新設計決策」那條 |
| 需要新設計決策 | 涉及既有設計/程式碼沒涵蓋的 DB schema / API / 架構 / 元件 / 模組異動 | 提醒使用者接著用 `system-design`，明確指出**只需要做哪一個設計面向**（不必重跑全部 11-17，尤其舊專案的整體架構/技術選型是一次性、早已定案不重做）；`system-design` 會把這次的設計-delta 寫進 `docs/design.md`，等於順手替沒文件的舊專案補上基線，下次變更就有得對照 |
| 其實是新方向 | 跟既有問題陳述/商業目標矛盾，或既有需求規格完全沒提到這個方向 | 提醒使用者接著用 `product-discovery` |

**⚠ 硬性關卡：本次變更的驗證不可省，兩條路都一樣。** 分診到「在既有範圍內」而跳過 Phase 3-4，跳過的是**設計與開發前準備**，**不包含本次變更的驗證**：

- **測試描述 MUST 在動手寫程式之前產出**（見上表），不分 Tier、不因為變更小而免除。
- **開發完成 MUST 進 `qa-handoff`（Phase 6）驗證本次變更並執行必要測試**——`qa-handoff` 不是可選項，也不因為「這次只改一點點」而跳過。但遵守「既往不溯」：不要求為未修改、與本次無關的既有程式碼補測試；只有本次異動及其直接受影響的行為需要測試或說明驗證方式。
- 專案沒有 `requirements-spec.md` 時，`qa-handoff` 改以本路徑產出的輕量 spec ＋ 程式碼現況基線為覆核依據（該 skill 已有明文），**不是跳過覆核**。

**⚠ 既有專案很可能本來就沒有測試——那是常態，不是例外。** 分診時 MUST 一併查清楚並寫進輕量 spec；這不代表要回頭替整個舊專案補測試：

| 查什麼 | 怎麼影響後面 |
|---|---|
| **這次要動的程式碼，現在有沒有測試覆蓋？** | 沒有 → Phase 6 只需針對**本次異動及其直接受影響的行為**補測試；不需替未修改的舊程式碼補測試（見下） |
| **專案有沒有可跑的測試框架與指令？** | 沒有 → 建立最小可跑的測試環境是 Phase 6 的第一件事，**MUST 在輕量 spec 裡標明這件事要做**，不要等做到一半才發現 |

**測試描述在「沒有既有測試」時仍然要寫**，而且更重要——它是你對「這個功能應該怎麼運作」的唯一書面依據。**不需要先有測試才寫得出測試描述**：描述寫的是預期行為，不是現有行為。

真的存在「連一條測試都寫不出來」的變更（例：純文案、純註解）→ 走 `../sdlc-orchestrator/references/severity-format.md` 的 **N/A 條款**（具體理由＋實作者以外的角度確認＋記在產出物裡），**不得自行免除**。

### 步驟 2.5：變更橫跨多個 repo/子專案時（跨包變更）
單一 repo 的變更跳過本節。若這次變更會動到 **兩個以上的 repo**（例如後端 + 前端 + 模擬器）：
1. 建一份**需求級單一真相記錄**：規格 delta + 涉及的 repo 清單 + 各 repo 完成狀態表。**放哪裡由使用環境的 CLAUDE.md/AGENTS.md 綁定層指定**；綁定層沒指定時，預設放「發起變更的主 repo」的 `docs/change-log.md`（在該筆記錄內列出其他涉及的 repo 與狀態）。
2. 每個 repo 各自走自己的 pipeline（各自的設計-delta/開發/測試），完成後回寫狀態到單一真相記錄——不要讓整體進度只存在對話記憶裡。
3. 順序照依賴：介面供應方先行（通常後端 API → 前端/模擬器跟上）。

### 步驟 3：記錄這次分診結果與輕量 spec
一句話總結「這次變更是什麼、判斷走哪條路、為什麼」，MUST 寫成一筆記錄附加進 `docs/change-log.md`（累加記錄，不覆蓋歷史；專案尚無 `docs/` 資料夾就直接建立），跟其他 8 個 phase skill 的持久化規則一致。

**每一筆 MUST 帶狀態欄，且 MUST 定義得出「這次變更做完了沒」**——欄位：`變更名｜分診結果｜工單號｜狀態｜完成日期`。狀態只用 `ticket-spec.md` 的狀態機。**結案判準（演進路徑專用，因為它不走完 8 個 phase）**：

| 這次變更 | 什麼時候算結案 |
|---|---|
| 不需部署（純內部重構、文件、設定值） | `qa-handoff`（Phase 6）通過 |
| 需要部署才生效 | `release-handoff`（Phase 7）煙霧測試綠燈 |

⚠ **Phase 5 三關過了不算結案**（`implementation-handoff` 明文「兩個 phase 都過才算做完」）；**也不必為了一個小變更去走 Phase 8 建監控儀表板**——Phase 8 是產品層級的持續維運，不是單筆變更的收尾。沒有這條判準，兩個人會對「這張變更完了沒」給出不同答案，而 `change-log.md` 上看不出來。

**工單號從哪來（演進模式沒有 Phase 1，不會經過那唯一一次開票）**：本 skill 分診確定要做的當下 **MUST 取得一個工單號**，下游 `implementation-handoff`／`qa-handoff` 的 `handoff-log.md` 都以它記錄。依使用環境綁定層的工單規則取號；**綁定層沒指定、或工單系統查不到**時 MUST 停下來問使用者（選項化：使用者自己開好給號／改用本機文件工單自編 `CR-nn` 並註明日後回填／本次不開票）。⚠ **已接工單系統時號碼 MUST 由系統生成；本機開發／未接系統才可自編**——這條判準原本只寫在 `product-discovery` 的開票時機段，演進模式讀不到那份檔，故在此重述。

**輕量 spec MUST 獨立落檔，NEVER 只留在對話裡**：分診到「在既有範圍內」時產出的輕量 spec ＋ 測試描述，MUST 寫成 `docs/change-specs/<變更名>.md`，並在 `docs/change-log.md` 那一列回指它。**這份 spec 的第一段就是該次變更的 `REQ-nn` 表**——演進模式沒有 `requirements-spec.md`，它就是這次變更的唯一真相源，下游的設計、實作、測試都只引用 `[REQ-07]` 不重抄內容（規則與豁免條件 → `../sdlc-orchestrator/references/traceability.md`）。理由：`qa-handoff` 明文要拿這份 spec 當測試覆核依據——**只存在於對話裡的 spec，等於下游被要求去讀一份不存在的檔案**；且工作階段一結束就沒有人接得上（同 `converge` 共識摘要的落檔理由）。`change-log.md` 只記「這次做了什麼、走哪條路」，spec 內容不塞進去（會撐破下方的 200 行治理）。

**模式宣告（第一次用本 skill 時做一次就好）**：專案若還沒有 `docs/sdlc-mode.md`，在這裡建立它並寫 `mode: evolution` ＋理由＋決定者（格式與三種模式 → `../sdlc-orchestrator/references/tailoring.md`）。**沒有這個檔的專案一律當「全跑」**——所以少了它，下一個接手的人會以為這個專案該走完九關。已經有這個檔就不要改，模式變更是使用者的決定不是執行者的。

## 停止條件
- 使用者提供的既有文件內容太舊/跟現況對不上 → 停下來確認是否需要先更新既有文件，不要用過時脈絡做判斷
- 判斷卡在「在既有範圍內」跟「需要新設計決策」之間 → 傾向保守，判定為「需要新設計決策」，避免漏判導致設計品質不足
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完

| 路由 | 下一站 | 之後 |

| 在既有範圍內 | `implementation-handoff`（Phase 5）——**帶著 `docs/change-specs/<變更名>.md` 進去**，跳過 Phase 3-4 | 開發完 **MUST** 進 `qa-handoff`（Phase 6），見上方硬性關卡 |
