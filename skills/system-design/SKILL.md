# System Design — SDLC Phase 3 設計

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 11-17，做系統設計並產出設計文件。

## 提問規則（本階段所有對使用者的提問一體適用）
向使用者確認關鍵決策（技術選型/schema 異動/模組邊界）時 **MUST 選項化**：每題附 2-4 個具體選項（把你最建議的放第一個並標「建議」，附一句理由），讓使用者勾選或回編號即可；自由補充永遠允許。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。**禁止開放式問「你想用什麼技術？」**——先依需求規格提出具體候選讓使用者選。

**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：本階段最容易發生「問兩題就自己寫完整份 schema」——寫任何設計文件前 **MUST 列出自決事項清單**，且清單必須逐項列出欄位枚舉值、識別碼長度與格式、狀態機、唯一約束語意、預設／上限／逾時值、模組邊界與命名，讓使用者可以把任何一項拉回自己決定。**「我覺得這是實作細節所以沒問」正是本規則要擋的。** 若發現需求顆粒度不足 → 依該檔規則三回需求階段補挖。

## 觸發條件
- 需求規格書已存在（來自 requirement-scoping 或使用者直接提供），且需要正式系統設計決策（新系統、跨模組大改、新增資料來源等）
- 也適用：從 `change-request` 轉來、只需要「單一設計面向」的情況（例如只需要補一個 API 端點設計）——這時只做那一個面向，不必走完整 11-17 步驟
- 不適用：完全不涉及新設計決策的小範圍功能改動（用範圍判斷在這裡不循環，因為需求規格書已存在，範圍是已知資訊，不像 `product-discovery` 的入場判斷那樣「規模要等做完才知道」）

## 完成條件（Phase Exit Criteria）
**依模式分兩種，不要用創世的清單去卡演進**：

| 模式 | 完成條件 |
|---|---|
| **創世**（全新專案） | 步驟 11-17 的 Output **＋ 步驟 10.5 的架構意圖**，共 8 項全部產出 |
| **演進**（從 `change-request` 轉來、只做單一設計面向） | **只要四項**：①步驟 10.5 的架構意圖（縮減為一題）②**該指定面向**的 Output ③演進支線的測試描述 ④**REQ-nn 表**（本支線沒有 `requirements-spec.md`，設計文件索引檔第一段就是本次變更的唯一需求真相源，規則與放哪 → `../sdlc-orchestrator/references/traceability.md` 規則二）。其餘面向**不是 N/A、也不是未完成，而是本次不在範圍內**——`change-request` 已明確指定只做哪一個面向，不必逐項標記或找人確認 |

⚠ 演進模式**不得**要求交出 ER 圖／元件清單／模組劃分才准離開本 phase：只補一個 API 欄位卻要產出整套設計，等於把「只做一個面向」這句話作廢。

通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）。**創世模式的完整 8 項：**
1. 系統架構圖 + 技術選型
2. ER 圖 / DB schema
3. API 規格
4. 元件清單 + 頁面組成藍圖（若涉及前端）
5. 模組劃分
6. 任務清單（掛在 Phase 1 工單號底下的子項目）
7. 設計文件（彙整以上全部）
8. **架構意圖**（步驟 10.5 的定案：新建＝想要什麼架構與品質排序；既有系統＝要調整成什麼、哪些不能動）——**MUST 寫進設計文件**，且後續每個重大取捨 MUST 標明它服務哪一項

**⚠ 硬性關卡**：**步驟 10.5 未完成 → MUST NOT 進入步驟 11。** 沒有架構意圖就開始設計，等於用執行者的預設值決定整份架構，而使用者無從察覺。

## 持久化
步驟11-16 的中間產出至少要整合進步驟17的設計文件；設計文件 MUST 寫成 `docs/` 下的 md 檔（可依面向拆成多檔，如 `docs/architecture.md`/`docs/db-schema.md`/`docs/api-spec.md`/`docs/logic-flow.md`（領域模型 + 引用關係 + 狀態轉移），或彙整成單一 `docs/design.md`）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。不可只留在對話紀錄裡。

⚠ **檔案已存在時 MUST NOT 直接覆寫。** `docs/architecture.md`／`api-spec.md`／`design.md` 這些檔名在成熟專案幾乎一定已經存在（而且往往是人手寫的整體文件）。先讀它，然後三選一並向使用者說明你選了哪個：**①把本次的 delta 併進既有內容**（演進模式的預設做法）**②另存成不撞名的檔**（例 `docs/api-spec-<變更名>.md`）**③使用者明確同意覆寫**。**NEVER 用一份單一面向的 delta 取代人家的整體架構文件。**

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測、風險清單。

## 步驟 10.5 架構意圖確認（MUST 先做）

**歸屬**：本步驟屬 **Phase 3 的第一步**，由本 skill 負責、進本 skill 才做；編號 10.5 只表示它在步驟 11 之前，`requirement-scoping`（Phase 2）不需要做這一步。

**單一設計面向（delta）情境**：從 `change-request` 轉來、只補一個設計面向時，10.5 **縮減為一題**——「這個 delta 要服務既有架構意圖的哪一項？」；既有架構意圖若沒有文件紀錄，才需要完整跑一次。

**進入步驟 11 之前 MUST 與使用者確認「要什麼樣的架構」。** 缺這一步，執行者會用自己的預設值把整份架構寫完，而使用者無從察覺——**產出看起來完整，但它服務的是執行者的偏好，不是使用者的**。

兩種情境問的東西不同：

| 情境 | MUST 問到 |
|---|---|
| **新建** | 想要什麼樣的架構；優先服務哪些性質（可維護／可擴充／可變更／效能／上線速度／簡單度）——**請使用者排序，不是挑一個** |
| **既有系統** | 現在的架構**哪裡不滿意**、想調整成什麼；**哪些部分不能動**；這次變更的邊界到哪 |

提問要求：

- **MUST 選項化**；使用者不熟該領域時，依 `../sdlc-orchestrator/references/questioning-sufficiency.md` 規則二「跨領域提問」處理。
- 選項描述 **MUST 用具體後果，不得用術語**（❌「缺乏抽象層」 ✅「日後要加第二個資料源時，所有查詢程式碼都要動」）。
- **MUST 標明「這個選擇日後最難改的是什麼」**——架構決策的成本不在寫的時候，在改的時候。
- 定案 **MUST 寫進設計文件**，且**後續每個重大取捨 MUST 標明它服務哪一項**，讓事後可檢查一致性。
- ⚠ **抽象的判準**：對「猜測可能會變」的地方不抽象；對**使用者明講過會變**的地方抽象**不算過度設計**。先分清楚是哪一種，再談要不要做。

## 流程

| 步驟 | Action | 誰做 | Output |
|---|---|---|---|
| 11 系統架構設計 | 決定分層/服務/技術棧 | Lead-direct 或派工（見下方判斷標準） | 系統架構圖 + 技術選型 |
| 12 資料庫設計 | 設計 ER 與資料表。**MUST NOT 使用 DB-level `FOREIGN KEY`/`REFERENCES` 約束**：關聯欄位用純 ID 型別（如 `uuid`/`varchar(36)`），不宣告 `REFERENCES`；邏輯關聯寫進欄位說明（例：`parent_oid｜varchar(36)｜關聯至父物件 OID，無 DB-level FK 約束`）；關聯欄位仍 MUST 加索引——沒有約束不代表不用索引。**凡欄位的值「由應用層解讀」（自由文字／JSON／key-value 的 value 側），MUST 逐個 key 定義值的格式（單位、數值或字串、可列舉就列出）與比較語意（等值／大小／區間）**——只寫「由應用層依 key 解讀」不算數：被列舉的是 key，要被解析的是 value，那句話會讓下游各編一套；⚠ 若對該欄位建了 `(key, value)` 索引卻需要範圍比較，**索引根本用不上**，這在設計階段就要發現 | 同上 | ER 圖 / DB schema |
| 13 介面設計 | 定義端點/指令、請求與回應格式。**MUST 附完整範例，用該介面實際的序列化格式**（JSON / XML / 固定長度報文 / protobuf / CLI 參數與輸出…由專案自選，不預設 JSON）：不只成功案例，**至少一個錯誤回應範例（含狀態碼或錯誤碼）**；若有認證，附認證標頭範例；範例值 MUST 用真實感資料，不是 placeholder 型別字串（如 `"string"`/`0.0`）。**格式非文字或不易內嵌時**（如二進位報文），改附欄位對照表 + 一筆十六進位或編碼後樣本，**不得因為「不是 JSON」就跳過範例** | 同上 | 介面規格 |
| 14 前端元件規劃 | 識別可重用元件、頁面組成 | 同上（涉前端時） | 元件清單 + 頁面組成藍圖 |
| 15 模組拆分 | 切模組、定邊界，**並畫出模組/類別之間的引用關係**（誰呼叫誰、資料往哪流），不是只有對外介面 | 同上 | 模組劃分 + 引用關係 |
| 16 拆分任務 | 切成可執行任務，**不另外開票／指派獨立票號**——全程只在 Phase 1 開一次工單，這裡拆出的每個工作項目都是同一個工單號底下的子項目（例：「ISSUE-42／後端 API」「ISSUE-42／前端頁面」）——下游 Phase 5 的 handoff-log 以「工單號／子項目名稱」記錄完工狀態 | Lead | 任務清單（子項目，整合進步驟17設計文件） |
| 17 產出設計文件 | 彙整以上所有 | Lead | 設計文件 |

**領域模型（條件式，掛在步驟 12-15 之間；沒有領域物件的專案跳過）**：專案有「會被多處引用、且本身有生命週期」的領域物件時，MUST 一併產出：
- **物件與職責**：每個領域物件負責什麼、不負責什麼（從使用情境推導，不是從資料表反推）
- **引用關係**：物件/類別之間誰呼叫誰、資料往哪流——**這份要能單獨讀懂**，之後查邏輯只看它就夠，不用回頭翻程式碼
- **資料模型對應表**（有持久化或跨層傳輸時 MUST 有）：一列一個模型類別，寫出`模型類別 ↔ 資料表 ↔ 對外傳輸物件`的對應，以及**欄位不是一對一的地方**（改名、合併、拆開、只在某一層存在、轉換規則）。同一份資料在不同層換名字最容易讓人追丟——**不對照就要開三個檔案交叉比對才知道哪個欄位是哪個**
- **狀態轉移**（物件有多種狀態時 MUST 有）：列出所有合法狀態、每個狀態可以轉去哪、由誰觸發、**什麼條件下釋放/結束**。例：某資源「可借用 → 已借出 → 已歸還」，要寫清楚誰能借、何時自動釋放、逾時怎麼處理。**狀態沒列全或轉移沒定義，等於把 race condition 留給實作階段猜**

**依賴標記（步驟 16 一併判斷）**：拆分任務時，先看子項目之間有沒有依賴（最常見：前端頁面依賴後端 API 才能真的測到，不是各自獨立單位）。有依賴的子項目：開發仍照依賴順序進行（介面供應方先行，例如後端先做），但 MUST 標記為同一驗收批次——要等依賴的部分都做完才能一起宣告「驗收通過」，不能各自分開喊過。能用 mock/contract test 獨立驗收的部分，仍可以拆開平行做、各自驗收，不是「有依賴就整包合併」。

**誰做的判斷標準**（完整分級表 → `../sdlc-orchestrator/references/agent-teams.md`）：單一設計面向若範圍明確且不複雜 → Lead-direct 對話產出；範圍大/需要多角度比較（例如架構有多個候選方案）→ 派 `general-purpose` agent，每個面向一個 agent、可平行派多個，每次只指定一個設計面向不跨面向擴張，最後由 Lead 彙整成單一設計文件（步驟17）並跟使用者確認關鍵決策（技術選型、schema 異動、模組邊界）。**Core rule：不假設不清楚的地方**——既有系統慣例不確定時，先讀現有程式碼/文件確認再設計，仍無法確認就明確列出待使用者確認的問題，不要憑空猜。⚠ **但讀到既有程式碼只能得到「它這樣寫」，不等於「這樣做可行」**——後者需要測試證據。引用既有做法時 MUST 標注**有無測試證據**，並自行補上獨立推導與驗收條件；**不得把未經驗證的既有實作當成選型依據**。

## 停止條件
- 設計產出跟既有系統慣例衝突 → 停下來跟使用者確認是否要破例
- 步驟 12 產出的 schema 出現 `FOREIGN KEY`/`REFERENCES` 約束 → 這是違規，改成純 ID 型別 + 欄位說明寫關聯，不要保留約束
- 步驟 16 拆分任務時發現任務範圍模糊、或發現前面階段（`requirement-scoping`）的產出有問題 → 明確告知使用者要回哪個 phase 重新確認，不要憑空猜著往下做；確認要回頭後依 `../sdlc-orchestrator/sdlc-entry.md`「回歸」段回寫狀態（含連鎖回開判斷），不能只在對話裡講一講
- 涉及設定/機敏資訊管理系統異動、跨環境部署影響、新雲端資源 → 逐項確認風險（機敏資訊管理方式、各環境差異、新資源存取權限）
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完
