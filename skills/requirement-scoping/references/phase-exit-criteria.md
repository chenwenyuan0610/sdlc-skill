# Requirement Scoping — Phase Exit Criteria 詳細清單

每個步驟的具體檢查項，全部確認才算 Phase 2 完成、可以進入 Phase 3。

## 步驟 6 收斂功能清單
- 每項功能可獨立驗收，不是模糊描述（例如「優化體驗」不合格，「使用者可在列表頁篩選日期區間」合格）

## 步驟 7 劃定範圍
- 明確列出「不做」清單，不是只有「做」清單
- 範圍決定已經使用者拍板，不是 Lead 單方面認定

## 步驟 8 功能優先排序
- 排序有依據（重要性/急迫性），不是隨機或按提出順序排列

## 步驟 9 撰寫需求規格文件
- 每個功能都有明確規則，沒有「待補充」字樣
- 跟步驟 2 的問題陳述、商業目標對得起來，沒有矛盾
- **每條需求都有 `REQ-nn` 編號**，且編號流水、無跳號、無重用（規則 → `../../sdlc-orchestrator/references/traceability.md`）
- **需求編號與工單號是兩套**，沒有把工單號當需求編號用
- 這張 REQ 表是唯一真相源——**其他文件沒有重抄需求內容的第二張表**

## 步驟 10 盤點依賴、風險與限制
- 至少涵蓋技術依賴（既有系統/模組/API）與已知限制
- 範圍較大或涉及既有系統時，風險項目來自實際調查，不是憑印象列

## 提問充分性（`../../sdlc-orchestrator/references/questioning-sufficiency.md`「遵守證據」段，本 phase 一體適用）
- **維度覆蓋表**已承接自上一 phase 並逐支複查，**每一列都是「已答」或「使用者說不適用」**——⚠ **正面表列**，不是「沒有未走」
- 「已答」的深度依規則 1-E2 **需求分析級**：要**足以寫出可驗收條件**——答不出驗收條件就是還沒問透，MUST 回上一 phase 補挖
- **提問記錄**：輪數、每輪問什麼、**使用者主動補充幾次**（分開計「漏問維度」與「選項集失敗」）
- **自決事項清單**分 `已問並拍板` 與 `僅揭露未問` 兩區；驗收條件的具體門檻與預設值 MUST 在「已問並拍板」區
- **殘餘猜測清單為空**，或每項都註明誰放行、並在產出物裡標成假設

任一缺漏 → 本 phase Exit Criteria **不算通過**（SKILL.md 的硬性關卡，本檔同步）。
