# Tooling Reuse — 重複性機械檢查的腳本化原則（領域中立）

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

寫給所有 phase 共用：遇到「這件事會在專案生命週期裡重複做很多次、而且判斷本身是機械性/確定性的」時，MAY 寫一個可重跑的腳本/指令去做，不必每次都用 LLM 重新讀檔/推導一遍——省下來的是 token，不是規則本身。**這條是 MAY，不是 MUST**：判準不成立的檢查/文件，就是不用寫腳本，不算漏做，也不構成任何 exit criteria 的扣分項。

## 適用範圍（MUST 先確認）

**本檔案只管「採用這套 SDLC 流程的專案所產出的文件」**（`docs/` 底下的 `requirements-spec.md`／`handoff-log.md`／`change-log.md`／測試檔等），**不包含這套 skill 包自己的規則檔案**（`SKILL.md`／`references/*.md`／`agents/*.md`）。

⚠ **這條界線不是文字潔癖，是防止腳本的信任範圍偷偷擴大**：修改規則檔案本身是需要走 `../CHANGELOG.md` 治理流程、需要使用者明確核准的高風險動作。如果本檔案的範例裡混進「寫腳本檢查規則包自己的檔案」，等於暗示每個專案在做份內工作時，也該順手把手伸進規則包本身、變成無人把關的自動化動作——這正是「用這套流程」跟「改這套流程」的邊界，MUST NOT 讓前者滲透成後者。規則包自己的維護效率化（例如多份規則檔重複的樣板文字要不要抽共用範本）是完全獨立的問題，不適用本檔案，也不要在這裡混著討論。

⚠ **正確的判斷依據是「掃描對象是規則文字本身、還是登記簿裡累積的資料列」，不是「這份檔案放在哪個資料夾」**——`framework-defects.md` 是唯一的例外情況：`ticket-spec.md` 明文它可能就是 `FD-nn` 框架缺陷的**實際登記簿本身**（不只是指標檔），也就是說這份 `references/*.md` 檔案裡的「登記簿」表格，有時候裝的是專案執行過程中真實累積的資料列，屬於本檔案適用範圍；但同一份檔案裡定義欄位／規則的**文字本身**仍然不適用，改動那些文字一樣要走 `CHANGELOG.md` 治理。判斷準則：腳本讀的是表格裡的**資料**（哪一列、哪一欄空白）就在範圍內；腳本讀的或要改的是**規則定義本身**就不在範圍內。

## 判準：什麼情況該寫腳本

三個條件**同時成立**才值得寫：

1. **會重複做**——不是這次做一次就沒了，是同一個檢查會在後續的票／phase／專案生命週期裡再被觸發（例如每張票都要做一次的追溯窮舉核對、每次產出 `docs/` 文件都要做的長度檢查）
2. **判斷是機械性的**——輸入輸出有明確規則可以寫成程式（字串比對、行數計算、正則抓取、格式驗證），不需要語意判斷或商業邏輯理解
3. **腳本比人工/LLM 重新推導省時**——一次性的事、或判斷牽涉語意理解，不適合；寫了腳本也還是要 LLM 讀懂結果才能下結論的，等於多繞一手，不划算

**不適合腳本化的例子**（判準第2條會擋掉）：N/A 條款三條件是否成立、Verified Clean 的檢查是否真的查過、驗收標準有沒有做對——這些都需要語意判斷，不是機械比對。**注意：同一個檢查項目裡，可能只有一部分是機械性的**——例如「REQ 追溯是否有測試覆蓋」這個大檢查，「有沒有被任何測試標籤引用到」是機械比對，但「引用到的那個測試是否真的驗證到這條規則」是語意判斷；只有前者適合腳本化，MUST NOT 把整個檢查項籠統貼上「機械性」標籤。

## 跟 `sdlc-entry.md`「治理保證不得只靠腳本」的分工

⚠ 兩者管的是不同層次，不衝突：

- `sdlc-entry.md` 那條擋的是**規則包自己的治理**——「這條規則有沒有被遵守」這種保證，MUST 能只靠規則文字本身成立，不能靠一個不隨規則包發送的腳本才算數。沒有腳本時，人一樣要能靠讀規則文字、手動核對做到同樣的事。
- 本檔講的是**專案執行過程中的效率優化**——腳本本身是**專案的產出物**（寫進專案自己的 repo，跟品質門禁指令、一鍵啟動腳本性質一樣），目的是加速重複性機械檢查、省 token，不是取代規則本身的約束力。**沒有腳本時，同樣的檢查必須還是能用手動/grep 做到同樣結論**——腳本只是比較快的做法，不是唯一路徑，MUST NOT 因為腳本還沒寫就跳過檢查本身。

## 現成案例（已經在包裡的先例）

這個做法不是新概念，下面幾條既有規則就是這個原則的具體實現：

- `dev-setup` 步驟18「一鍵啟動方式」MUST 是可執行檔案（容器編排檔／`Makefile`／套件管理器的 script），不是文字步驟說明
- `dev-setup` 完成條件「品質門禁指令」MUST 逐條寫出可直接複製執行的實際命令並實跑過一次
- `qa-handoff` 步驟26「整合測試」MUST 寫成可重複執行的腳本，下次變更能直接重跑當回歸測試

## 建議套用的重複性檢查點

以下幾個現有規則裡的機械檢查，符合上面三條判準，**檢查對象都是專案自己的 `docs/` 產出物**，MAY 寫成腳本重用（依專案規模與重複次數判斷值不值得，不寫也不算缺失）：

- `qa-handoff` 步驟27 的 `[REQ-nn]`／`[REQ-nn-AC1]` 追溯窮舉核對——**只有「有沒有被任何測試標籤引用到」這部分可腳本化**（每次驗收都要重跑一次的 grep 比對，比對對象是專案的 `requirements-spec.md` 與測試檔，找出零引用的 REQ/AC 候選清單）；「測試是否真的驗證到位」「沒覆蓋的理由是否合理」仍需語意判斷，不在腳本範圍內，腳本只是縮小人工/AI 覆核的範圍
- `docs/` 產出物「≤200行」長度治理檢查——每次寫產出物都要做的 `wc -l` 檢查
- `docs/handoff-log.md` 固定標頭（例如 `## Phase 5 — Implementation`）與狀態行（`狀態：進行中`／`狀態：完成`）存在性檢查——每次 phase 交接都要確認的字串搜尋
- **工單證據欄空白掃描**——`ticket-spec.md` 定義的四種工單（`ISSUE-nn`／`BUG-nn`／`FB-nn`／`FD-nn`）登記在專案 `docs/handoff-log.md`／`docs/change-log.md`／`framework-defects.md` 登記簿裡時，證據欄空白視為不受理，每次登記/覆核都要重查一次
- `severity-format.md` 四種狀態值（`PASS`／`BLOCKED`／`NEEDS WORK`／`FAIL`）有沒有被自創第五種——每份 reviewer/verifier 報告都要檢查的字串比對
- **工單編號格式驗證**——`ticket-spec.md` 定義的四種工單前綴＋流水號格式（工作票 `ISSUE-nn`、缺陷 `BUG-nn`、維運回饋 `FB-nn`、框架缺陷 `FD-nn`）是否符合正則，每次開票都要做。⚠ 不含 `REQ-nn`（那是 `traceability.md` 的需求編號，不是工單）與 `CR-nn`（`KNOWN-ISSUES.md` 記載為既有缺口，不在 `ticket-spec.md` 正式定義的四種格式裡，此檢查不應該把它當合法格式驗證）

`ticket-spec.md` 與 `framework-defects.md` 各自的登記簿規則裡已經留了「使用環境可另加機械檢查輔助」的措辭，指的就是本檔案——兩處可以直接把措辭改成指過來，不用各自重新定義一次判準。
