# 4-Tier Severity Format — SDLC 審查共用定義（領域中立）

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

`sdlc-reviewer`/`sdlc-verifier` 兩個 agent 角色共用此格式，不綁定任何語言/框架。

## Tier 定義與 Lead 對應行為

| Tier | 符號 | 意義 | Lead 處理 |
|------|------|------|----------|
| Critical | 🔴 | MUST fix，任一條 → 整體 FAIL | 修正後重審，不准進下一步 |
| Major | 🟠 | 強烈建議修，任一條 → NEEDS WORK | 修正或使用者明確授權列為已知風險才能放行 |
| Minor | 🟡 | 可改善，不擋放行 | 記錄，可後補 |
| Suggestion | 🔵 | 風格/重構建議 | 僅參考，不強制 |

## Finding 格式（強制，缺任一欄視為 invalid finding）

| 欄位 | 內容 |
|------|------|
| 位置 | 檔案路徑 + 行號 |
| Runtime 可達性 | 這段程式碼是否在實際執行路徑上生效（`live` / `test-only` / `未被實際呼叫/掛載` / `宣告了但沒接上實際邏輯`）|
| 觸發條件 | 什麼情境/輸入會讓這個問題發生 |
| 具體失敗場景 | ≥3 步：從觸發到實際造成的錯誤結果 |
| 影響 | 具體後果（資料錯誤/權限繞過/服務中斷等），不是「可能有風險」這種空話 |
| 修法 | 具體改法或程式碼片段，不可只寫「應該…」 |
| 如何自動偵測 | 未來怎麼用 grep/lint/測試抓到同類問題 |

## 禁止輸出的句子（出現任一即 invalid finding，直接打回重審）

- 「建議加強安全」/「應該檢查權限」/「建議避免洩漏」
- 「應該避免…」/「最好…」/「考慮…」（無具體修法）
- 「可能有問題」/「不太理想」/「有風險」（無具體失敗場景）
- 沒有檔案路徑 + 行號的 finding
- 跟本次改動無關的「一般性建議」

## False Security 規則

任何「宣稱有保護但實際沒接上/沒生效」的 finding（例如：設定寫了但沒載入、middleware 定義了但沒掛到實際路由、防護邏輯存在但有明確繞過路徑）→ **強制標記為 🔴 Critical**，不論原本判斷的 Tier 是什麼——「以為有保護其實沒有」比「明顯沒做」更危險，會誤導後續所有人。

## Verified Clean 撰寫原則

MUST 列出「每個檢查項目的結論」，不能只列「發現的問題」——讓 Lead 一眼判斷「是沒問題」還是「根本沒查」。格式：`項目名稱：查詢方式 + 查詢結果`。禁止只寫「XXX：無問題」而不說怎麼查的。

## Report 狀態判斷

| 狀態 | 條件 | 性質 |
|------|------|------|
| PASS | 0 Critical，0 Major，Verified Clean 章節完整列出檢查項目，**且一次就綠** | 可接受 |
| BLOCKED | 外部因素導致跑不完（環境起不來／相依服務掛掉／缺權限／缺測試資料），**不是程式碼判定** | 可重試——MUST 寫明卡在哪、需要誰解 |
| NEEDS WORK | 任一 Major／**多個 Minor**／Verified Clean 不完整（無法判斷是否真的查過）／**同一項目重跑 ≥2 次才綠** | 不確定 |
| FAIL | 任一 Critical | 不可接受 |

**重跑次數怎麼算（兩條，缺一就會有狀態出不來）：**

1. **`BLOCKED` 不計入。** 「一次就綠」計的是**程式碼判定**的次數；環境起不來、相依服務掛掉的那幾次**根本沒有判定過程式碼**。把它們算進去，會讓任何被環境卡過的項目永遠拿不到 `PASS`（而 `BLOCKED` 又不准當終態，整條路封死）。正確算法：阻塞解除後的**第一次真正跑完**若是綠的就是 `PASS`，並註明先前被阻塞幾次與原因。
2. **修正後計數歸零。** 判定為 `NEEDS WORK`／`FAIL` 並**實際改了程式碼或測試**之後，重審是**對新版本的第一次判定**，計數從 1 重新起算——一次就綠即 `PASS`。⚠ 沒有這條，修好的東西會永遠停在 `NEEDS WORK`（第 3 次執行仍滿足「重跑 ≥2 次才綠」），`implementation-handoff` 的「修完重審」變成無限迴圈，`狀態：完成` 永遠寫不了。
   **「不穩定」指的是同一份程式碼跑出不同結果**，不是「改過之後又跑了一次」。改動後仍需重跑 ≥2 次才綠 → 那是新版本自己的不穩定，照舊記 `NEEDS WORK`。

**改壞實驗的預期紅燈**：依 `test-case-coverage.md` 規則四，一次只改壞隔離副本，目標斷言按預期失敗屬於實驗成功證據，不是交付版本 FAIL，也不計為同版本不穩定重跑。正常／還原版本仍須通過；無關失敗或環境故障不算抓到錯誤。

**只有這四種狀態，不得自創第五種。** 特別禁止「未要求」「不適用」「略過」這類豁免式標記——真的不適用要走**下方「N/A 條款」**（需具體理由 + 實作者以外的角度確認），不能在報告裡自行豁免。

**防假綠燈三條：**

1. **重跑到過 ≠ PASS。** 同一個檢查／測試需要重跑 2 次以上才綠 → 記 **NEEDS WORK**，並寫明前幾次為什麼失敗。不穩定本身就是缺陷，不是雜訊。
2. **禁止自動 pass。** 任何「跑不動就當它過」的機制（例外被吞掉、找不到就 skip、逾時視為成功）一律視為 Critical——這是 False Security 的一種，比明顯失敗更危險。跑不動就是 **BLOCKED**，不是 PASS。
3. **BLOCKED 不能當終態。** 只是「這輪先擱著」，MUST 記錄阻塞原因並在解除後重跑；**不得**以 BLOCKED 收尾宣告該階段完成。

**Default 立場（`sdlc-verifier` 適用）**：預設 NEEDS WORK，除非有完整證據才給 PASS——第一次嘗試就給 PASS 是例外不是常態。


## N/A 條款（所有 phase 共用的唯一豁免出口）

任何 Exit Criteria 項目**真的不適用於本專案**時（例：純 CLI 工具沒有 UI 操作介面、內部工具沒有對外 API），可標 `N/A`，但**同時 MUST 滿足三條**：

1. **具體理由**——寫明為什麼這個專案不適用，不得只寫「不適用」
2. **實作者以外的角度確認**——自己標自己過視為未完成
3. **記在該 phase 的產出物裡**，不是口頭帶過

⚠ **這是唯一合法的豁免出口。** 不得自創「未要求」「略過」「暫不適用」等其他標記；也不得把「還沒做」當成「不適用」——前者是未完成，後者是本專案沒有這回事。
