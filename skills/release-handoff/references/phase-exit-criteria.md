# Release Handoff — Phase Exit Criteria 詳細清單

每個步驟的具體檢查項，全部確認才算 Phase 7 完成、可以進入 Phase 8。

## 步驟 29 部署前檢查
- **已確認「有東西可以部署」**：本次變更**已合併進部署來源分支**，且要部署的 artifact 確實建自該 commit。⚠ Phase 5-6 全程沒有任何一步負責交付（多數環境的版控動作由人工進行），**Phase 5 完工 ≠ 程式碼已進到部署得到的地方**；不確認就部署，會部到舊版而測試報告是新版的
- 環境變數/憑證/資料庫 migration 逐項確認就緒
- 檢查清單狀態為「通過」，不是「大致準備好了」
- **測試資料與測試帳號已從即將上線的環境移除**（含寫死的預設帳密、種子資料、debug 開關）
- **開發／測試環境與正式環境確實分離**，且部署權限與開發權限不是同一組人同一把鑰匙
- **變更紀錄六項齊備**：變更原因與說明、影響評估、核准者、測試結果、失敗回復程序、以及本次是否屬於需要額外驗證的重大變更

## 步驟 30 部署到測試環境（staging）
- staging 已實際運行並可存取驗證
- 部署動作由使用者手動觸發，Lead 沒有代為執行

## 步驟 31 部署到正式環境（production）
- production 已實際上線
- 部署動作由使用者手動觸發，Lead 沒有代為執行

## 步驟 32 上線後煙霧測試
- 核心功能路徑已快速驗證（綠燈才算過，不是「應該沒問題」）
- 若煙霧測試不過，已明確記錄要退版還是修正

## 成功上線後的維運模式交接
- production 上線且煙霧測試綠燈後，已依 `../../sdlc-orchestrator/references/tailoring.md`「宣告檔建立與維運交接時機」檢查／建立 `docs/sdlc-mode.md`；模式、理由、決定者齊備，交接紀錄有連結與決定依據。
- 既有模式的變更有使用者明確決定；沒有因退版或未部署而切換模式，沒有重寫創世歷史。缺檔或待確認時不得宣稱交接完成。

## 與既有機制的關係
本階段是新內容，不涉及分工問題；部署動作一律人工手動觸發是不可越過的安全紅線，不是待補的既有工具問題。
