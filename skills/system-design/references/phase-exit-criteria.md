# System Design — Phase Exit Criteria 詳細清單

每個步驟的具體檢查項，全部確認才算 Phase 3 完成、可以進入 Phase 4。

## 步驟 11 系統架構設計
- 分層/服務邊界清楚畫出
- 技術選型有明確理由（不是「因為習慣」）
- 標明是否新增外部資源/服務
- 標明影響哪些既有模組

## 步驟 12 資料庫設計
- ER 圖涵蓋所有新增/異動的資料表
- 標明使用哪個資料庫/datasource（若專案有多重資料庫架構）
- 有無跨資料庫一致性需求
- Migration 計畫（資料量、downtime、回滾方案）
- **逐一檢查所有關聯欄位，確認沒有宣告 `FOREIGN KEY`/`REFERENCES`**——關聯欄位是純 ID 型別，邏輯關聯寫在欄位說明；有宣告就是違規，打回步驟 12 修正
- 關聯欄位仍有加索引（沒有 FK 約束不代表可以省略索引）

## 步驟 13 API 設計
- 端點清單 + method + 請求/回應格式
- 錯誤處理格式一致
- 是否需要向下相容（既有 client 呼叫）
- **每個端點/指令都有完整範例，用該介面實際的序列化格式**（不預設 JSON）：至少一個成功案例 + 至少一個錯誤案例（含狀態碼或錯誤碼）；有認證的附標頭範例
- 格式非文字或不易內嵌（如二進位報文）→ 已改附欄位對照表 + 一筆編碼後樣本，**沒有因為「不是 JSON」就整段跳過**
- 範例值是真實感資料，不是 `"string"`/`0.0` 這類 placeholder 型別字串

## 領域模型（條件式：專案有領域物件時才檢查）
- 每個領域物件的職責寫清楚（負責什麼、不負責什麼）
- **模組/類別引用關係已畫出**，且這份文件單獨讀得懂——不必回頭翻程式碼就能追邏輯
- **資料模型對應表已產出**（有持久化或跨層傳輸時）：一列一個模型類別，`模型類別 ↔ 資料表 ↔ 對外傳輸物件` 三欄齊全，且**欄位不是一對一的地方已標明**（改名／合併／拆開／只在某層存在／轉換規則）
- 物件有多種狀態時：**所有合法狀態、每個狀態的合法轉移、觸發者、釋放/結束條件**都已列出，沒有「未定義的狀態組合」
- 沒有領域物件的專案已明確標註不適用並註明理由

## 步驟 14 前端元件規劃（若涉及前端）
- 元件清單標明可重用範圍
- 頁面組成藍圖涵蓋所有使用情境

## 步驟 15 模組拆分
- 標明涉及哪些模組/套件邊界
- 模組邊界清楚，無循環依賴
- 模組/類別引用關係已記錄（不是只有對外介面）

## 步驟 16 拆分任務
- 每個工作項目的驗收標準可獨立驗證
- 標明跨模組的項目，避免漏派
- 沒有另外指派獨立票號——每個工作項目都標明是 Phase 1 工單號底下的哪個子項目（例：「ISSUE-42／後端 API」），Phase 5 的 handoff-log 以「工單號／子項目名稱」記完工狀態，沒標明對應子項目就對不上帳
- 有依賴的子項目（例：前端依賴後端才能真的測到）已標記為同一驗收批次，不是各自獨立宣告驗收通過；能用 mock/contract test 獨立驗收的部分才允許各自拆開驗收

## 步驟 17 設計文件
- 彙整以上所有產出成單一文件
- 標記設定/機敏資訊管理系統異動（若有）
- 標記跨環境部署影響（若有多環境部署）

## 步驟 10.5 架構意圖（**硬性關卡：未完成 MUST NOT 進入步驟 11**）
- **已與使用者確認「要什麼樣的架構」並定案**，不是執行者用自己的預設值寫完整份設計
  - **新建**：想要什麼樣的架構；優先服務哪些性質（可維護／可擴充／可變更／效能／上線速度／簡單度）——**已請使用者排序，不是挑一個**
  - **既有系統**：現在的架構哪裡不滿意、想調整成什麼；**哪些部分不能動**；這次變更的邊界到哪
  - **單一面向 delta**：已回答「這個 delta 要服務既有架構意圖的哪一項」；既有架構意圖若無文件紀錄，才需完整跑一次
- 提問**用具體後果表達，不是術語**（❌「缺乏抽象層」 ✅「日後要加第二個資料源時，所有查詢程式碼都要動」）
- **已標明「這個選擇日後最難改的是什麼」**
- **定案已寫進設計文件**，且**步驟 11-17 的每個重大取捨都標明它服務哪一項**——沒標就無法事後檢查一致性

## 提問充分性（`../../sdlc-orchestrator/references/questioning-sufficiency.md`「遵守證據」段，本 phase 一體適用）
- **維度覆蓋表**逐支複查，**每一列都是「已答」或「使用者說不適用」**（⚠ 正面表列）
- 「已答」的深度依規則 1-E2 **設計級**：要**足以做出技術決策**——說不出這一支影響哪個設計選擇就是還沒問透
- **自決事項清單**分 `已問並拍板` 與 `僅揭露未問` 兩區，且**技術選型／資料模型核心結構／模組邊界／破壞既有安全或權限模型的例外，一律 MUST 在「已問並拍板」區**——只列進「僅揭露未問」不算數（揭露是被動的，詢問才是主動的）
- 清單 MUST 逐項列出：欄位枚舉值、識別碼長度與格式、狀態機、唯一約束語意、預設／上限／逾時值、模組邊界與命名
- **「值由應用層解讀」的欄位 MUST 定義值本身的格式與比較語意。** 凡欄位被設計成自由文字／JSON／key-value 的 value 側，而其內容日後要被解析、比大小或做範圍查詢者，MUST **逐個 key** 寫出：①值的格式（單位、數值或字串、可列舉就列出）②比較語意（等值／大小／區間）。⚠ **只寫「由應用層依 key 解讀」不算定義**——被列舉的是 key，真正要被解析的是 value；那句話把問題丟給下游，而下游會各自編一套。**這種缺口在設計階段不會暴露（設計不寫業務邏輯），會延到實作才炸**
- **上游範圍或約束變更後，既有技術選型已重新確認**，不是直接沿用
- **殘餘猜測清單為空**，或每項都註明誰放行、並在設計文件裡標成假設

任一缺漏 → 本 phase Exit Criteria **不算通過**（SKILL.md 的硬性關卡，本檔同步）。

## 與既有機制的關係
本階段是新內容，不涉及分工問題；不變性（invariants）、邊界條件、回滾方案、模組邊界等判準已內建在步驟 11-17 各自的檢查項裡，不需要額外套用其他審查框架。
