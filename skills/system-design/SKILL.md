# System Design — SDLC Phase 3 設計

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 11-17，做系統設計並產出設計文件。

## 提問規則（本階段所有對使用者的提問一體適用）
向使用者確認關鍵決策（技術選型/schema 異動/模組邊界）時 **MUST 選項化**：每題附 2-4 個具體選項（把你最建議的放第一個並標「建議」，附一句理由），讓使用者勾選或回編號即可；自由補充永遠允許。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。**禁止開放式問「你想用什麼技術？」**——先依需求規格提出具體候選讓使用者選。

## 觸發條件
- 需求規格書已存在（來自 requirement-scoping 或使用者直接提供），且需要正式系統設計決策（新系統、跨模組大改、新增資料來源等）
- 也適用：從 `change-request` 轉來、只需要「單一設計面向」的情況（例如只需要補一個 API 端點設計）——這時只做那一個面向，不必走完整 11-17 步驟
- 不適用：完全不涉及新設計決策的小範圍功能改動（用範圍判斷在這裡不循環，因為需求規格書已存在，範圍是已知資訊，不像 `product-discovery` 的入場判斷那樣「規模要等做完才知道」）

## 完成條件（Phase Exit Criteria）
7 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 系統架構圖 + 技術選型
2. ER 圖 / DB schema
3. API 規格
4. 元件清單 + 頁面組成藍圖（若涉及前端）
5. 模組劃分
6. 任務清單（tickets）
7. 設計文件（彙整以上全部）

## 持久化
步驟11-16 的中間產出至少要整合進步驟17的設計文件；設計文件 MUST 寫成 `docs/` 下的 md 檔（可依面向拆成多檔，如 `docs/architecture.md`/`docs/db-schema.md`/`docs/api-spec.md`，或彙整成單一 `docs/design.md`）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。不可只留在對話紀錄裡。

## 流程

| 步驟 | Action | 誰做 | Output |
|---|---|---|---|
| 11 系統架構設計 | 決定分層/服務/技術棧 | Lead-direct 或派工（見下方判斷標準） | 系統架構圖 + 技術選型 |
| 12 資料庫設計 | 設計 ER 與資料表 | 同上 | ER 圖 / DB schema |
| 13 API 設計 | 定義端點、請求/回應格式 | 同上 | API 規格 |
| 14 前端元件規劃 | 識別可重用元件、頁面組成 | 同上（涉前端時） | 元件清單 + 頁面組成藍圖 |
| 15 模組拆分 | 切模組、定邊界 | 同上 | 模組劃分 |
| 16 拆分任務/開票 | 切成可執行任務，**每張票指派票號**（如 T-01、T-02；專案已有編號規則就沿用）——下游 Phase 5 的 handoff-log 以票號記錄完工狀態，沒有票號就對不上帳 | Lead | 任務清單（含票號，整合進步驟17設計文件） |
| 17 產出設計文件 | 彙整以上所有 | Lead | 設計文件 |

**誰做的判斷標準**（完整分級表 → `../sdlc-orchestrator/references/agent-teams.md`）：單一設計面向若範圍明確且不複雜 → Lead-direct 對話產出；範圍大/需要多角度比較（例如架構有多個候選方案）→ 派 `general-purpose` agent，每個面向一個 agent、可平行派多個，每次只指定一個設計面向不跨面向擴張，最後由 Lead 彙整成單一設計文件（步驟17）並跟使用者確認關鍵決策（技術選型、schema 異動、模組邊界）。**Core rule：不假設不清楚的地方**——既有系統慣例不確定時，先讀現有程式碼/文件確認再設計，仍無法確認就明確列出待使用者確認的問題，不要憑空猜。

## 停止條件
- 設計產出跟既有系統慣例衝突 → 停下來跟使用者確認是否要破例
- 步驟 16 開票時發現任務範圍模糊、或發現前面階段（`requirement-scoping`）的產出有問題 → 明確告知使用者要回哪個 phase 重新確認，不要憑空猜著往下做
- 涉及設定/機敏資訊管理系統異動、跨環境部署影響、新雲端資源 → 逐項確認風險（機敏資訊管理方式、各環境差異、新資源存取權限）
