# Dev Setup — Phase Exit Criteria 詳細清單

每個步驟的具體檢查項，全部確認才算 Phase 4 完成、可以進入 Phase 5。

## 步驟 18 建立專案骨架與開發環境
- 骨架已實際驗證可運行，不是「應該可以」（若在既有模組/專案內開發、骨架已存在，本項視為自動通過）
- **本機一鍵啟動已實測跑過**：從乾淨環境用**一個**指令拉起來，並記錄那個指令。是可執行檔案（容器編排檔／Makefile／`npm run` 之類的套件 script／自寫腳本），不是文字步驟說明
- **相依也一起起來了**——資料庫／快取／訊息佇列／模擬器都在內；只起主程式、要人另外手動準備相依的，**不算通過**（專案本來就沒有外部相依則自動通過，但要註明）

## 步驟 19 設定版控與分支策略
- 清單包含建議分支名稱、命名規則、目標 MR
- 已確認清單只是「列給使用者看」，Lead 沒有自動執行任何 branch/push 動作

## 步驟 20 排定開發排程
- 排程對應任務清單（來自 `system-design` 步驟 16），每個任務有粗估時程
- 沒有任務清單以外的排程項目（避免排程比實際任務多，代表任務清單本身有缺漏）

## 附加產出：測試描述
- 任務清單每個項目都有對應的白話測試描述，且是依 `requirements-spec.md` 撰寫（不是照抄 `system-design` 技術文件用詞）
- Tier 0-1：已由 Lead 自行看過確認
- Tier 2-3：已交使用者過目確認，沒有跳過這一步就落地

## 附加產出：品質門禁指令（Phase 5 完工第 1 關要用的那條指令）
- **已定義本專案的品質門禁指令並寫進 `docs/dev-setup.md`**：該語言／框架慣用的型別檢查／lint／測試／build，**逐條寫出可直接複製執行的實際指令**，不是「跑一下 lint」這種描述
- **已實跑過一次並附 command output**，確認在乾淨環境下可執行且 0 issues
- **「0 issues」的計數範圍＝上一行你自己列出的那幾條指令的輸出，不含它們以外的任何工具。** 特別是**相依套件的安全稽核（`npm audit`／`pip-audit`／`dependency-check` 這類）預設不在門禁內**——它掃的是上游套件不是你寫的程式碼，而現代生態的官方 scaffold 出廠就可能帶著當下修不掉的告示。要納入是**專案自己的決定**，納入時 MUST 一併定義「哪個嚴重度以上才算 fail」
- **達不到 0 時的出口**（沒有這條，上面就是一個沒有合法出路的門檻）：確認該問題**非由本專案程式碼造成**、且**不阻擋任何其他 Exit Criteria** → 寫進 `docs/dev-setup.md` 的「已知限制」即可放行。該段 MUST 含四件事：實際數字、根因出處、**試過哪些修法與各自為什麼失敗**、重新評估的時機。**只寫「已知問題」四個字不算**
- ⚠ **這一項不能留到 Phase 5 才想**：`implementation-handoff` 的完工第 1 關要求「0 issues＋MUST 附實際 command output」，但它明文「具體指令依專案自己的工具鏈」——**沒有任何 phase 定義過那條指令的話，Phase 5 會卡在一個從沒被定義過的門禁上**。骨架剛建好正是定義它的時機
- 使用環境的 CLAUDE.md／AGENTS.md 若已有該技術棧的門禁指令表，直接引用即可，不必重寫

## 提問充分性（`../../sdlc-orchestrator/references/questioning-sufficiency.md`「遵守證據」段，本 phase 一體適用）
- **維度覆蓋表**逐支複查，**每一列都是「已答」或「使用者說不適用」**（⚠ 正面表列）
- 「已答」的深度依規則 1-E2 **開發前準備級**：要**足以寫出每個任務項目的白話測試描述**——答不出「這個功能應該怎麼運作」就是還沒問透
- **自決事項清單**分 `已問並拍板` 與 `僅揭露未問` 兩區
- **殘餘猜測清單為空**，或每項都註明誰放行

任一缺漏 → 本 phase Exit Criteria **不算通過**（SKILL.md 的硬性關卡，本檔同步）。

## 與既有機制的關係
本階段是新內容，不涉及分工問題；版控步驟不自動執行是不可越過的安全紅線，不是待補的既有工具問題。
