# Fix — 修 bug 的骨架

⚠ **這不是第四條流程。** 修 bug 走的就是既有那條演進路線，本檔只做兩件事：**把 bug 特有的前置動作講清楚**，然後**把你接回主流程**。任何 Tier 分級、審查編制、品質門禁的細節都不在這裡——那些各有唯一擁有檔，本檔只指路。**如果你發現這裡跟那些檔講得不一樣，以那些檔為準，並登記一筆框架缺陷。**

## 進來之前

| 你的狀態 | 去哪 |
|---|---|
| 不確定這是 bug 還是新需求 | `converge` |
| 確定是 bug，但**不知道根因** | `debug`——找到根因再回來 |
| 確定是 bug，**根因已知** | 繼續讀本檔 |

**「根因已知」的判準**：你能用一句話說出「哪一段邏輯、在什麼輸入或狀態下、做了什麼不該做的事」。說不出來就是還沒找到，**不要靠猜著改**——猜著改的修正通常只是讓症狀消失。

## 三件 bug 特有的事（新增功能不用做，所以主流程沒寫）

### 1. 先寫得出「怎麼重現」

MUST 寫下：**前置狀態 → 操作 → 實際結果 → 預期結果**。四項缺一不可。

重現不出來的 bug **MUST NOT 宣告修好**——你沒有辦法證明它不見了。真的重現不了（時序性、環境性）→ 明確記錄「無法重現」與已排除的可能，交給使用者決定要不要繼續，**不要改一改就當作修好**。

### 2. 先有一個會失敗的測試

修之前先寫一個**現在會失敗**的測試，讓它重現這個 bug。順序是刻意的：

- 先寫測試 → 看到它失敗 → 修 → 看到它通過。**這條路徑證明了兩件事**：測試真的測到那個 bug，而且修正真的有效
- 反過來（先修再補測試）只證明了「測試跟現在的程式碼一致」——**那是一個一定會過的測試**

既有專案沒有測試框架 → 建最小可跑的即可，這是測試關的第一件事不是前置條件（細節見測試關的 SKILL）。

### 3. 找同類

同一個根因通常不只犯一次。修完 MUST 反查：**同樣的寫法在別處還有沒有**。

有的話 **MUST NOT 順手一起改**——那超出本次範圍，會讓回歸測試失去意義。**另開一筆記錄**，讓它變成下一件被排序的工作。

## 然後接回主流程

1. **分診** → `change-request`。修 bug 幾乎都落在「在既有範圍內」，但**判斷仍要做**：根因如果是設計本身有缺，那不是修 bug，是設計變更；根因如果是**需求本身沒釐清**（不是設計問題，是當初的需求理解就有誤），那也不是修 bug、也不透過 `change-request`（那是走新變更的路）——這是回歸情境，狀態回寫與跨 phase 處理規則 → `../sdlc-orchestrator/sdlc-entry.md`「回歸」段
2. **實作** → `implementation-handoff`（Phase 5）
3. **測試** → `qa-handoff`（Phase 6）。**這一關不因為「只是修個 bug」而免除**——bug 修正落在既有程式碼上，回歸保護的價值在這裡最高
4. **部署**（需要才走）→ `release-handoff`（Phase 7）

**派幾個人、誰覆核** → 見 `../sdlc-orchestrator/references/agent-teams.md`（唯一擁有檔）。
**品質門禁指令、工單系統、要附哪份技術棧規範** → 依你的 `CLAUDE.md`／`AGENTS.md` 綁定層；**本檔刻意不寫死任何工具名**。

## 停止條件

- 改了兩次仍未修好 → 停下來重新確認根因，**不要繼續試**。多半是第一步的「根因已知」根本沒成立
- 修正範圍開始擴大到本來沒要動的邏輯 → 停，退回只改必要的部分，其餘另開記錄
- 卡住的原因是**流程規則本身**（規則矛盾／判準模糊／缺一步接不上）→ 不要就地改規則、不要停工：append 一列到框架缺陷登記簿（status=`proposed`，**證據欄必填**）。位置 → `../sdlc-orchestrator/references/framework-defects.md`
