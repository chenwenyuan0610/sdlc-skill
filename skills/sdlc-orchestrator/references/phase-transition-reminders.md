# Phase 轉換提醒（下一步）的呈現規則

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

> **這份檔案解決什麼**：各 skill 的「下一步」段都要求「提醒使用者接著用某個 phase」，部分還明講「不是可選項」，但都沒規定提醒要用什麼機制呈現。實際執行時，這種「提醒」很容易被寫成完工總結裡的一句話，淹沒在其他資訊中，使用者沒特別回應，後續新一輪工作接著蓋過去，該轉換點就再也沒被提起——**規則存在，但沒有強制力**。
>
> **誰引用它**：任何 skill 的「下一步」段，只要該轉換**明講「不是可選項」或「MUST 接下一個 phase」**（不是單純的順口建議）就適用。目前已知引用：`implementation-handoff`（Phase 5→6）、`qa-handoff`（Phase 6→7）。
>
> **觸發脈絡**：cloud-oa-system 專案 ISSUE-5（框架缺陷登記簿 `FD-03`）——`implementation-handoff` 完工後，「下一步」提醒只寫進完工總結的一段文字裡，不是獨立的是非題；使用者沒有特別回應，後續兩輪 bug 修復都沒有重新提出，直到使用者自己主動問「為什麼不執行 qa-handoff」才發現 Phase 6 從頭到尾沒有真的被觸發過。同一份對話裡，凡是規則明文要求「MUST 選項化」的決策點都確實有用明確選項處理，只有「下一步」提醒沒有這個要求，行為上也確實比較弱——顯示規則內容本身的嚴謹度不足，不是單純執行疏失。

## 規則一：MUST 選項化，不能只是文字提醒

「下一步」段落若明講「不是可選項」／「MUST 接下一個 phase」，該提醒 **MUST 用跟其他決策點同樣的明確是非/選項提問呈現**（例如：「Phase 5 已完工，要現在接著執行 Phase 6（`qa-handoff`）嗎？」附選項：現在執行／先擱置待之後再說／其他），**不得只寫進完工總結的一段敘述文字裡**。

理由：文字提醒容易被使用者在一堆其他資訊裡略過；明確的是非題才會真的觸發使用者做出回應，跟其他「MUST 選項化」的決策點（分診路由、架構決策等）用同一套機制，沒有理由這裡特別弱化。

## 規則二：沒有得到明確回應前，MUST 在下一輪回覆重新提出

使用者沒有針對這個提醒給出明確答覆（現在做／先不做／其他決定）時，**這個提醒狀態視為「未結案」，MUST 在下一次相關回覆的開頭重新提出**，不得被後續新工作（新 bug 回報、新功能請求）默默蓋過。

**判斷「相關回覆」的範圍**：同一個工單號／變更底下的後續工作都算——不因為使用者轉而先處理別的事（例如回報新 bug）就視為提醒已經處理過。

## 規則三：每一輪新的 Phase 5 完工都要重新觸發

**同一個工單號底下，只要又發生一次「開發工作完工」（包含後續的 bug 修復輪、新功能追加輪，不限第一次），就要重新走一次本提醒**，不能因為「已經問過一次了」就假設後續輪次不用再問——使用者在前一輪選擇「先擱置」不代表後續輪次也適用同一個答案，情境可能已經變了（例如缺陷數量、風險評估都可能不同）。

## 落在哪個 skill

- `implementation-handoff/SKILL.md`「下一步」段（Phase 5→6）
- `qa-handoff/SKILL.md`「下一步」段（Phase 6→7）
