# 框架缺陷登記簿（Framework Defect）

> **登記簿放哪，由使用環境的綁定層（`CLAUDE.md`／`AGENTS.md`）指定。**
> **綁定層沒指定 → 就用本檔下方的「## 登記簿」表，直接 append 一列。** 不必先去建別的檔、也不必先問誰。

要登記一筆 → append 到表尾，並在「## 角色與覆核紀錄」表補一列填**發現者**。

## 什麼時候該登記

**判準只有一條：規則本身把執行者卡住，而卡住的原因不是使用者做錯。**

典型：規則寫死了某種技術選擇但本專案用的不是那個／兩條規則互相矛盾，照 A 做就違反 B／規則要求一份產出物但沒說「本專案不適用時怎麼辦」／判準模糊到兩個人會判出不同結果／流程中間缺一步，上一階段的產出接不到下一階段。

**不算框架缺陷**（走各 skill 既有的停止條件）：專案產出物本身有問題 → 回上一個 phase；技術或環境問題 → `debug`；需求本身模糊 → `converge`。

## 撞到的當下怎麼辦

1. **不要就地改規則。** 改規則要走修法流程，不是實作到一半順手改。
2. **不要停工。** 登記完照現行規則繼續走（用最接近的合理解讀），把工作做完。
3. **append 一列**，`status` 填 `proposed`。
4. 繼續。

## 為什麼規則與登記簿分開

`references/` 裝的是**規則**（工單規格、提問規則、派工分級），每個人拿到的都一樣；登記簿是**各自累積的資料**，每個人的內容都不同。分開放，打包時才不必逐檔判斷「這是規則還是資料」。

⚠ **規則包不依賴任何既有登記內容**，只依賴 `ticket-spec.md` 的格式定義。收到的登記簿是空的，是正常的。

## 登記格式

欄位、狀態機、硬規則 → `ticket-spec.md`。本類型（`FD-nn`）的表頭：

| ID | 發現於 | 描述 | 證據 | 類型 | 影響範圍 | status |

- `描述`＝規則怎麼卡住你的
- `證據`＝**必填**，卡住你的那個規則在哪（檔名＋段落或行號）＋當下的具體情況。空白＝不受理
- `類型`＝`矛盾`／`模糊`／`缺步驟`／`過度specific`
- `影響範圍`＝只影響本專案／影響所有走這個階段的人
- `負責人`／`發現者`／`覆核者` 記在下方「角色與覆核紀錄」表（欄位太長，分兩張表，以 `ID` 對應）
