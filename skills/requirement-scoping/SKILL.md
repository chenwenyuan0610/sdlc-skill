# Requirement Scoping — SDLC Phase 2 需求分析

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 6-10，把「可行方案」收斂成正式需求規格書。**對話式引導，Lead + 使用者共同拍板，不派 agent 執行**（步驟10可選派風險掃描）。

## 提問規則（本階段所有對使用者的提問一體適用）
向需求方提問 **MUST 選項化**：每題附 2-4 個具體選項（把你最建議的放第一個並標「建議」），讓使用者勾選或回編號即可；自由補充永遠允許——選項是降低回答成本，不是限制答案。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。**禁止純開放式問題轟炸**——把你能推測的先寫成具體選項讓使用者確認，猜不出來的才開放問。範圍/優先序這類拍板題，把「做/不做」「先後」直接做成可勾的清單。

**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：追到**維度覆蓋表每一列都標「已答」或「使用者說不適用」**才算問完（不是「使用者沒再補」；還有任何一列是「進行中」或「未走」都不算）；寫需求規格前先列出「我打算自己決定的事項清單」（含驗收條件的具體門檻、預設值）。**若本階段發現需求顆粒度不足（答不出「這條需求的具體樣子是什麼」）→ 依該檔規則三回 `product-discovery` 補挖，不得用自己的假設填滿。**

## 觸發條件
- 已有明確的可行方案（不論是否經過 product-discovery），要往下細化成可執行的規格
- 不適用：方案還沒定 → 先回 product-discovery

## 完成條件（Phase Exit Criteria）
5 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 功能清單
2. 範圍界定（做/不做）
3. 排序後功能清單
4. 需求規格書——**每條需求 MUST 有 `REQ-nn` 編號並寫成一張表**（這張表是後續全部文件的唯一真相源；編號規則、引用格式 `[REQ-07]`、豁免條件 → `../sdlc-orchestrator/references/traceability.md`）
5. 依賴/風險/限制清單
6. **維度覆蓋表**（承接 `product-discovery` 那張並逐支複查；本階段新增的維度一律補進表內，格式與判準 → `../sdlc-orchestrator/references/questioning-sufficiency.md` 規則一）

**⚠ 硬性關卡**：**維度覆蓋表上還有任何一列**不是「已答」或「使用者說不適用」**（含「未走」「進行中」）→ MUST NOT 進入步驟 9（撰寫需求規格），也 MUST NOT 宣告本 phase 完成。** 需求規格是下游設計的唯一依據，這裡漏掉的維度會在設計或實作階段變成「執行者自己猜」——**而猜錯的代價是整條 pipeline 回頭改**。
**且 MUST 另列「殘餘猜測清單」並清空**（規則四 4-A）：每個功能的驗收門檻、預設值、上限值若是「我猜的」→ 問掉或請使用者放行，**不得直接寫進需求規格**。放行的 MUST 在規格裡標成假設並註明誰放行。

## 持久化
5 個 Output MUST 寫成 markdown 檔案存進專案的 `docs/` 資料夾（例如 `docs/requirements-spec.md`、`docs/dependencies-risks.md`）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。不可只留在對話紀錄裡，檔案不存在視為本階段未完成。

⚠ **同名檔已存在時 MUST NOT 直接覆寫**——先讀它，再決定是併入、另存不撞名的檔、還是請使用者確認可以覆寫。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測、風險清單。

## 流程

### 步驟 6：收斂功能清單
- Action：把可行方案拆成具體功能項目
- 誰做：Lead 對話
- Output：功能清單

### 步驟 7：劃定範圍
- Action：決定這一版做/不做什麼
- 誰做：Lead 提案，使用者拍板（**範圍決定權在使用者，不是 Lead 自己決定**）
- Output：範圍界定

### 步驟 8：功能優先排序
- Action：依重要性/急迫性排序 in-scope 功能
- 誰做：Lead + 使用者
- Output：排序後功能清單

### 步驟 9：撰寫需求規格文件
- 若設定涉及外部環境狀態，MUST 依 `../sdlc-orchestrator/references/test-case-coverage.md` 規則五，將狀態責任、確認方式與失敗行為寫入需求／AC。
- Action：把每個功能寫成正式規格（細節、規則）。**同時發需求編號**——一條需求一個 `REQ-nn`，流水、不補洞、不重用，且**與工單號分開兩套**（工單會被合併關閉重開，需求不會；混用的話第一次工單合併就對不上帳）。**一條 `REQ-nn` 若包含多條可獨立驗證的業務規則/情境（例如「登入功能」底下「帳號不存在顯示錯誤」「密碼錯誤顯示錯誤」「連續失敗鎖帳號」），MUST 逐條列出並各自編號**（`REQ-nn-AC1`、`REQ-nn-AC2`……，同一 `REQ-nn` 底下依序、不補洞、不重用）；只有單一情境時不需要編號，`REQ-nn` 本身即可。**判準（這條規則算不算獨立情境）**：把這條規則整句拿掉，剩下的描述還能不能單獨判斷「做對了沒有」——能，就是獨立情境該拆；拿掉後只是少了補充說明或例外處理細節、不影響能不能判定對錯，就不用拆。**卡在拆或不拆之間時傾向拆**：拆多了的代價可回收（事後發現太細，兩條 AC 的內容可以在描述裡整合說明「這兩點視為同一情境驗證」，不需要刪號）；漏拆的代價是實際的測試覆蓋缺口，不可回收。完整規則（含 AC 引用格式、拆分子編號的回歸情境）→ `../sdlc-orchestrator/references/traceability.md`
- 誰做：Lead 撰寫，使用者審閱確認
- Output：需求規格書（含 `REQ-nn` 對照表）

### 步驟 10：盤點依賴、風險與限制
- Action：找技術依賴、風險、限制
- 誰做：Lead 對話；範圍較大或涉及既有系統時，可選派 `general-purpose` agent 做風險掃描。**唯讀**：只給 Read/Glob/Grep/WebSearch，不給 Edit/Write，這階段還沒真的要動手實作，agent 只做調查不做決策
- Output：依賴/風險/限制清單

## 停止條件
- 範圍界定卡住（使用者一直想擴大範圍）→ 提醒 scope creep 風險，但範圍決定權仍在使用者
- 發現前面階段（`product-discovery`）的產出有問題，例如需求規格書寫到一半發現跟原始問題陳述矛盾 → 明確告知使用者要回 `product-discovery` 重新確認，不要在已知有問題的情況下把需求規格書硬寫完；確認要回頭後依 `../sdlc-orchestrator/sdlc-entry.md`「回歸」段回寫狀態（含連鎖回開判斷），不能只在對話裡講一講
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完
