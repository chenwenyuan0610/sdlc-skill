# Release Handoff — SDLC Phase 7 部署

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 29-32。**Lead 只負責檢查清單與唯讀驗證，實際部署動作 MUST 由使用者手動觸發**（不可越過的安全紅線）。

**綁定層優先（僅限「用哪個工具」，不含安全紅線）**：使用環境的 CLAUDE.md / AGENTS.md 若對本 phase 定義了工具綁定（例如「Phase 7 → 走某某既有部署稽核流程」的綁定表），照綁定走；本 skill 的內建做法只是「無綁定專案」的 fallback。

⚠ **但綁定層只能加嚴，不得放寬。** 上面那條「實際部署動作 MUST 由使用者手動觸發」是**不可越過的安全紅線**，綁定表寫什麼都不能作廢它——**綁定表指定的是「按哪個按鈕」，不是「可以由 AI 代按」**。填了「Phase 7 → 我們的 CI 自動部署 pipeline」的意思是「使用者去那條 pipeline 上手動觸發」，不是「執行者可以自己觸發它」。

## 觸發條件
- 驗收結果已通過（來自 qa-handoff）
- 不適用：測試還沒過 → 先回 qa-handoff

## 完成條件（Phase Exit Criteria）
4 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 部署檢查清單（通過）
2. staging 運行
3. production 上線
4. 煙霧測試結果（綠燈/退版）

## 持久化
交接結果 MUST 記進 `docs/handoff-log.md`（部署檢查結果、目標環境、煙霧測試結果），**用固定標頭 `## Phase 7 — Release` 分節**。分節的第一行 MUST 是狀態行 `狀態：進行中` 或 `狀態：完成`——**標頭存在不等於做完**，沒有這一行的話下一個接手的人／agent 會誤判本階段已結束而跳過（原因同 `implementation-handoff` 的「## Phase 5」標頭）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。

**⚠ 本次變更不需要部署時**（例如只改文件、或改動不進到任何執行環境）→ 狀態行寫第三個值 `狀態：不適用（理由：<一句話>／決定者：<誰>）`。**理由與決定者缺任一項就退回當「未做」**——空的「不適用」等於默默跳過一關。完整裁剪規則與三種模式 → `../sdlc-orchestrator/references/tailoring.md`。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測（檔名固定 `docs/<phase>-evidence.md`）、風險清單。
⚠ **累加型紀錄例外**（`change-log.md`／`handoff-log.md`／`feedback-log.md`）：流水帳沒有段落語意可拆、也沒有段落編號可保留。改用**時間分卷**——超過 200 行時把舊內容整段移到 `<原檔名>-<年份或期別>.md`，主檔保留最近期內容 ＋ 一行分卷索引。**NEVER 為了守行數而刪除歷史。**

## 流程

### 步驟 29：部署前檢查
- Action：檢查環境、設定、資料就緒（環境變數/憑證/資料庫 migration 已跑）。**MUST 一併確認「有東西可以部署」**——本次變更**已合併進部署來源分支**，且要部署的 artifact 確實建自該 commit。⚠ Phase 5-6 全程沒有任何一步負責交付（多數環境的版控動作是人工進行、不由執行者自動化），**Phase 5 完工 ≠ 程式碼已進到部署得到的地方**；不確認就部署，會部到舊版而測試報告是新版的
- 誰做：Lead 列出檢查清單，逐項確認；合併／推送動作依使用環境的版控規則，**不由本 skill 代勞**
- Output：部署檢查清單（通過）。**完整檢查項 → `references/phase-exit-criteria.md`**，其中三項容易漏：**測試資料與測試帳號已從即將上線的環境移除**、**開發／測試環境與正式環境確實分離**、**變更紀錄六項齊備**

### 步驟 30：部署到測試環境（staging）
- Action：部署到 staging
- 誰做：Lead 列出部署步驟，**使用者手動執行**，Lead 不自動觸發
- Output：staging 運行

### 步驟 31：部署到正式環境（production）
- Action：部署到 production
- 誰做：同上，**使用者手動執行**，Lead 不自動觸發
- Output：production 上線

### 步驟 32：上線後煙霧測試
- Action：快速測核心功能是否活著
- 誰做：Lead 可協助執行唯讀檢查（健康檢查端點、關鍵頁面回應等），不涉及任何寫入/部署動作
- Output：煙霧測試結果（綠燈/退版）
- ⚠ **只有綠燈才可以把 `## Phase 7` 寫成 `狀態：完成`。** 判定退版時：分節維持 `狀態：進行中`，記下退版原因與退到哪個版本，**然後回 `implementation-handoff`（Phase 5）修**，修完重走 Phase 6、Phase 7——**這是「回歸」的一個特例，通用規則（含 Phase 5／6 分節是否要一併回開）→ `../sdlc-orchestrator/sdlc-entry.md`「回歸」段**，本條只講煙霧測試退版這個具體情境不重複定義通則。**NEVER 把退版寫成完成**——退版代表功能沒上線、問題還在，寫成完成之後下一次定位會判「Phase 7 已完成」而進入維運，把一個失敗的發布當成上線中的產品在監控。

## 停止條件
- 使用者要求 Lead 直接觸發部署 → 拒絕，這是人工手動觸發的範圍，Lead 只能協助檢查
- 部署前檢查發現前面階段（`qa-handoff`）的產出有問題 → 明確告知使用者要回 `qa-handoff` 重新確認，不要在已知有問題的情況下放行部署；確認要回頭後依 `../sdlc-orchestrator/sdlc-entry.md`「回歸」段回寫狀態（含連鎖回開判斷），不能只在對話裡講一講
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完

## 下一步
煙霧測試綠燈 → 提示使用者可以接著用 `ops-feedback` 開始維運監控。**不自動呼叫**，只是提醒。
