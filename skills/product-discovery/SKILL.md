# Product Discovery — SDLC Phase 1 需求發想

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 1-5，引導使用者從零散訴求走到可行方案。**對話式引導流程，Lead 全程主導，不派 agent 執行實作**（步驟5可選派 general-purpose 做技術可行性調查）。

## 提問規則（本階段所有對使用者的提問一體適用）
向需求方提問 **MUST 選項化**：每題附 2-4 個具體選項（把你最建議的放第一個並標「建議」），讓使用者勾選或回編號即可；自由補充永遠允許——選項是降低回答成本，不是限制答案。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。**禁止純開放式問題轟炸**（「你想要什麼？」）——把你能推測的先寫成具體選項讓使用者確認，猜不出來的才開放問。

## 觸發條件
**用「確定性」判斷，不是用「規模」判斷**——規模是需求發想後才會知道的東西，拿最終規模去決定要不要先做需求發想是循環依賴。
- 問題本質、目標使用者、解決方案任一還不確定 → 走本 skill，不論預期規模大小
- 問題、情境、方案都已經明確 → 不適用，直接跳到後面對應的 phase（`system-design`/`dev-setup`）或既有的功能開發流程，不論規模大小

## 完成條件（Phase Exit Criteria）
5 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 原始需求清單
2. 問題陳述 + 商業目標
3. 使用者與情境描述
4. 候選方案清單（≥2 個，不收斂）
5. 可行方案（含技術/時間/成本初步評估）

## 持久化
5 個 Output MUST 寫成 markdown 檔案存進專案的 `docs/` 資料夾（例如 `docs/product-discovery.md`）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。不可只留在對話紀錄裡，檔案不存在視為本階段未完成。

## 流程

### 步驟 1：蒐集原始需求
- Action：訪談、記錄、彙整使用者的零散訴求
- 誰做：Lead 直接問使用者，不派 agent
- Output：原始需求清單（條列式即可，不用正式文件）

### 步驟 2：釐清問題本質與商業目標
- Action：對每條需求追問「為什麼」，挖出真正要解決的問題
- 誰做：Lead 對話
- Output：問題陳述 + 商業目標（1-2 句話）

### 步驟 3：定義目標使用者與使用情境
- Action：描繪誰會用、在什麼情境用
- 誰做：Lead 對話
- Output：使用者與情境描述

### 步驟 4：發想解決方案
- Action：擴散發想多個解法，**不收斂**，至少 2 個候選
- 誰做：Lead 對話，可主動提議方案讓使用者評估
- Output：候選方案清單

### 步驟 5：初步可行性評估
- Action：從技術/時間/成本角度評估每個候選方案
- 誰做：Lead 對話；技術細節不確定時，可選派 `general-purpose` agent 做技術可行性調查（本階段唯一允許派 agent 的步驟）。**唯讀**：只給 Read/Glob/Grep/WebSearch，不給 Edit/Write，這階段還沒真的要動手實作，agent 只做調查不做決策
- Output：可行方案（1 個，附評估理由）

## 停止條件
- 使用者對候選方案還在猶豫、想不清楚 → 不要強行收斂，留在步驟 4/5 繼續討論
- 使用者跳過需求發想直接要功能規格 → 提醒這樣會跳過本階段，確認使用者真的要跳過再放行
- 本輪是從 `ops-feedback` 迴圈重跑 → 先確認上一輪是哪裡出了問題才需要重跑，不要照抄上一輪的答案

## 下一步
5 個 Output 都有了 → 提示使用者可以接著用 `requirement-scoping` 做需求分析。**不自動呼叫**，只是提醒。
