# 提問充分性與自決揭露（所有 phase 共用）

> **這份檔案解決什麼**：原本各 skill 的提問規則只規定「MUST 選項化」與「一批 ≤5 題」，**沒有任何條款定義「問夠了」**——充分性由執行者自己說了算。結果是問到「夠我往下做」就停，剩下的自己決定，錯了才重來。
>
> **每一條都來自實跑時真的踩到的坑**，不是憑空想的規範。各條的原始案例記在使用環境自己的 `framework-defects.md` 登記簿。
>
> ⚠ **本檔是通用規則，寫作要求兩條**：①條文一律寫成**任何領域都適用**的形式；②**不得把單一案例的敘事寫進條文本體**（也不得留下只有原作者查得到的編號引用）——否則讀者要先看懂別人的專案，才看得懂規則。

## 規則零：分清「事實」與「決策」

- **事實**（環境裡查得到的：檔案內容、版本、既有慣例、外部服務的規格與定價）→ **MUST 自己去查，不准拿來問人。** 拿事實去問人是把工作推回去。
- **決策**（取捨、優先序、範圍、要不要做、用哪個方案）→ **MUST 交給人拍板**，不得因為「我覺得這比較合理」就自決。
- 判斷不出是事實還是決策時，先花一次查詢成本去查；查不到才問。

## 規則一：覆蓋率驅動，不是「問到他不講」

> 「追到使用者沒有新增就算問完」**是自評式的**——「有沒有下一輪」由執行者決定，不問下一輪，條件就自動滿足。取樣權在執行者手上，等於沒有判準。

### 1-A 動手前 MUST 先落維度覆蓋表

提問之前 **MUST 把要問的維度寫成一張表**（每列一個維度，標**四種狀態之一**：「已答／進行中／使用者說不適用／未走」），並隨提問逐輪更新。

- **停止條件＝表上每一列都是「已答」或「使用者說不適用」**。
  ⚠ **用正面表列，不用「沒有未走」**——後者會讓整排標「進行中」的表合法過關，而「進行中」正是「問了但還沒問透」的狀態。
- 這張表 **MUST 進該 phase 的產出物**，讓任何人都能檢查哪一支沒走。
- 表上只要還有任何一列是「未走」**或「進行中」**，就進下一步 → 該 phase 的 Exit Criteria **不算通過**。

### 1-B 維度清單 MUST 來自領域中立生成框架

**不得只從使用者已說過的往同類推**——那樣只能碰到使用者已暗示的鄰近維度，永遠碰不到他完全沒提的維度。至少走完這十一支：

| # | 維度 | 問什麼 |
|---|---|---|
| 1 | 誰 | 誰會用、誰受影響、有哪些利害關係人、人數與特殊需求 |
| 2 | 何時 | 頻率、時機、時間限制、要提前多久 |
| 3 | 何地 | 地點、範圍、環境限制 |
| 4 | 要什麼 | 功能、內容、品質要求 |
| 5 | 多少 | 預算、規模、數量上限 |
| 6 | 誰付錢／誰負責 | 成本歸屬、權責、憑證需求 |
| 7 | 出錯怎麼辦 | 失敗情境、備案、降級行為 |
| 8 | 不能碰什麼 | 隱私、法規、禁區、**明確不做的範圍** |
| 9 | 決策怎麼收 | 誰拍板、平手／衝突怎麼解 |
| 10 | 事後 | 結果要不要留、下一輪怎麼用 |
| 11 | **誘因／動機** | **為什麼有人願意做這件事**、不做會怎樣、做了得到什麼 |

⚠ 第 11 支的觸發判準：**產出物中只要有任何一項依賴使用者主動投入**（填寫、上傳、評分、回報、審核），MUST 問誘因——否則等於設計了一個沒人會用的功能。

### 1-C 使用者主動補充＝覆蓋不足的實證

使用者自願提出一個**不在你任何一題選項裡**的需求 → **直接證明覆蓋不足**（外部可觀察，不需執行者自評）。發生時 MUST：

1. 回頭補一輪，把該維度與其鄰近維度一起問完
2. 在提問記錄裡標明**這是第幾次被使用者主動補**——次數本身就是覆蓋品質指標
3. **分開計數兩種病因**：①漏問了某個維度（覆蓋不足）②問了但**選項集不完整**，正確答案不在你給的任何一個選項裡（選項設計錯）。兩者修法不同

### 1-D 選項全不命中時，MUST 記為選項集失敗

每批提問 **MUST 附明確出口**：「以上都不對，我要的是＿＿」。使用者走這個出口時，**MUST 把它記成選項集失敗**而非單純的補充——代表你對這個問題的理解本身就偏了。

### 1-E 回頭重掃

任何一輪的答案若**產生新角色／新利害關係人、改變產品定位、或推翻既有的技術與約束前提**，MUST 把受影響的上游維度標回「進行中」並重問。**不得因為已標「已答」就跳過**。

### 1-E2 深度判準：勾了不等於走過

**一支維度標「已答」的條件，依 phase 分級**——每個 phase 只被要求它的產出物真正需要的深度：

| Phase 類型 | 「已答」的門檻 |
|---|---|
| **收斂**（問題本身還沒定義，pipeline 外） | 問到**足以判斷「這是什麼問題／要不要做／該分流去哪」**即可。此時連方案都還沒發想，答不出情境細節是正常的——**這是全表最低的門檻**，不得拿需求發想級的深度去卡收斂 |
| **需求發想**（方案尚未定案） | 問到**有哪些情境／要不要處理／誰受影響**即可。此時方案還沒發想，寫不出可驗收條件是正常的 |
| **需求分析**（收斂成規格） | 要**足以寫出可驗收條件**——答不出驗收條件就是還沒問透 |
| **分診**（既有專案的變更，判斷走哪條路） | 要**足以判斷「這次變更涉不涉及新設計決策」與「影響範圍到哪」**——判不出來就傾向保守，當成需要新設計決策 |
| **設計**（決定怎麼做） | 要**足以做出技術決策**——說不出這一支會影響哪個設計選擇，就是還沒問透 |
| **開發前準備** | 要**足以寫出每個任務項目的白話測試描述**——答不出「這個功能應該怎麼運作」就是還沒問透 |

⚠ **不得用「反正下個 phase 會問」當藉口跳過**：分級降低的是**深度**，不是**是否要問**。每一支在每個 phase 都要走到，只是走到多深不同。

自我檢驗方式——對每一支問自己：**「我現在能不能把這一支寫成一條別人可以判定通過或失敗的驗收條件？」** 答不出來就是還沒走完。

⚠ 常見的假性走完：使用者回了一個分類詞就標「已答」（例：回「要能篩選」就當篩選這支走完，但篩什麼、依據哪個欄位、資料哪來全都沒問）。**廣度是覆蓋表，深度是這一條，兩個都要。**

### 1-F 抽象答案 MUST 追具體實例

收到抽象標籤（分類名詞、形容詞）時 MUST 追問具體實例：

> 「你上次真的想做、但做不到的那一次，具體是什麼情況？原話是什麼？」

**一句真實的敘述勝過十個分類標籤**——抽象標籤承載不了可執行的顆粒度。

## 規則二：走決策樹，一次一題

- **走決策樹的每一支，把決策之間的依賴逐一解掉**，不要平行丟出一堆彼此相關的問題。
- **會影響後續問題的決策：一次只問一題，等回答再問下一題。**
- **每題 MUST 附上自己推薦的答案**與推薦理由。
- **與各 skill「一次一批 ≤5 題」的關係**：彼此獨立的事實確認／偏好勾選可以一批；**有依賴關係的決策一次一題**，本節優先；判斷不出有無依賴 → 當成有依賴。

### 2-A 跨領域提問（對方不熟這個領域時）

「附上推薦答案讓對方可以只說同意」在對方熟悉該領域時是降低成本，**在對方不熟時會退化成「同意或不同意」**，喪失讓人真正參與決策的意義。當決策屬於使用者可能不熟的專業領域（架構、資安、資料庫、法遵、授權）時：

| MUST | 說明 |
|---|---|
| 用**具體後果**表達，不用術語 | ❌「缺乏抽象層」 ✅「日後要加第二個資料源時，所有查詢程式碼都要動」 |
| 標明「**這個選擇日後最難改的是什麼**」 | 決策成本不在寫的時候，在改的時候 |
| 主動提供 **1–2 個對方可能沒想到的角度** | 包含**反對你自己推薦**的角度；只列自己想好的選項等於讓人在你的框內選 |

### 2-B 執行者自己想到的，MUST 主動問

**沒問，就等於執行者自己決定了——而那通常不是使用者要的。**

執行者在任何階段憑自己的專業判斷發現的**疑點、矛盾、風險、遺漏、更好的做法**，即使**使用者從未提過**，也 **MUST 主動提出來問**。不得因為以下任何理由略過：

| 禁止的理由 | 為什麼不成立 |
|---|---|
| 「使用者沒提，應該不重要」 | 使用者沒提通常是**不知道有這件事**，不是判斷過不重要 |
| 「這是實作細節」 | 是不是細節由使用者判定（規則三） |
| 「問了會拖慢進度」 | 做錯重來比多問一次慢得多 |
| 「我照最佳實務處理就好」 | 最佳實務有多個且互相衝突，選哪一個是取捨不是事實 |

發現矛盾時**尤其**要問：兩條使用者自己給的需求互相打架時，**不得由執行者挑一條實作**，MUST 把矛盾攤開請使用者裁決。

## 規則三：自決揭露與必問分界

在寫任何 `docs/` 產出物**之前**，執行者 **MUST 列出「我打算自己決定的事項清單」**，一行一項。

### 3-A 必問清單 vs 可揭露清單

**揭露 ≠ 詢問**：揭露是被動的（使用者要自己看清單、自己發現要拉回），詢問是主動的（把選項端到面前）。下列**一律 MUST 主動選項化詢問，不得只列進自決清單**：

- 技術選型
- 資料模型的核心結構（決定資訊如何被表達與呈現的那些）
- 模組邊界與職責劃分
- **任何破壞既有安全模型、權限模型或已宣告約束的例外**

其餘（命名、內部結構、實作細節、可回退的預設值）列清單即可。
**自決清單 MUST 分兩區**：`已問並拍板` 與 `僅揭露未問`，讓使用者一眼看出哪些其實沒問過。

### 3-B 上游變更後，既有選型 MUST 重新確認

上游範圍或約束變更後，**不得直接沿用先前的技術選型**。沿用時 MUST 明說「這是基於舊範圍做的決定，要不要重新評估」。

### 3-C 選項共同夾帶的前提 MUST 明講

若一批選項全部共用某個未說出口的假設（同一個父目錄、同一個預設值、同一個技術前提），使用者就只能在你的前提內選、無法否決那個前提。出選項時 MUST 一併寫出共同假設並邀請否決。

- **「我覺得這不重要所以沒問」正是本規則要擋的。** 重要性由使用者判定，不由執行者判定。

## 規則四：殘餘猜測清單為空才准動手

- **在使用者明確確認理解一致之前，不得開始產出。** 「沒有反對」不等於共識，**沉默不是同意**。
- 已動手後才發現理解不一致 → 停下、講清楚哪裡不一致、退回提問，不要一邊改一邊猜。

### 4-A 殘餘猜測清單

動手前 **MUST 額外列出「我現在還在猜的事項」**，與自決清單**分開兩張**：

| | 自決事項 | 殘餘猜測 |
|---|---|---|
| 狀態 | **我知道**有哪些選項，我選了一個 | **我不知道**答案，我在填空 |
| 風險 | 選錯，可討論 | **錯了整段白做**，而且沒人知道那裡有個假設 |

**硬關卡：殘餘猜測清單非空 → MUST NOT 動手產出。** 每一項三個出口：

1. **查掉它**——若是事實，依規則零自己查，不准問人
2. **升級成提案讓使用者選或放行**——合理的填空可以做，但 MUST 附「推薦哪一個」＋「為什麼」＋「代價是什麼」＋「什麼情況下該翻盤」。**不得只寫「我建議 X」就要人放行**，那等於要人盲簽
3. 使用者明確放行「這項你猜就好」→ 才可保留，且 **MUST 在產出物裡標成假設並註明誰放行**

出口 2 的品質判準：只有結論沒理由＝無效；理由只有形容詞（「比較好／比較安全」）＝無效，**MUST 寫出拿什麼換什麼**；沒寫翻盤條件＝無效。

⚠ **禁止把猜測寫進產出物而不標記。** 未標記的猜測讀起來跟已確認的需求一模一樣，下游會拿它當依據繼續蓋。

## 規則五：發現上游沒挖夠就回上游

- 任何 phase 若出現「這個值從哪來」「這條需求的具體樣子是什麼」答不出來，**MUST 停下並回需求階段補挖**，不得在下游用自己的假設把空格填滿。
- 回補後 MUST 重新檢查下游已產出的文件要不要跟著改，並標明**哪一段是因為上游變更而重寫的**。

## 遵守證據（各 phase 產出物必備）

| 段落 | 內容 |
|---|---|
| **提問記錄** | 問了幾輪、每輪問什麼、**使用者主動補充幾次**（並分開「漏問維度」與「選項集失敗」） |
| **維度覆蓋表** | 十一支逐列標記，**每一列都是「已答」或「使用者說不適用」**（正面表列——寫「沒有未走」會讓整排「進行中」的表合法過關，見 1-A） |
| **自決事項** | 分 `已問並拍板` 與 `僅揭露未問` 兩區 |
| **殘餘猜測清單** | 為空，或每項都註明誰放行 |

任一缺漏 → 該 phase 的 Exit Criteria 不算通過。

**這四段 MUST 獨立成檔，檔名固定 `docs/<phase>-evidence.md`**（例：`discovery-evidence.md`／`scoping-evidence.md`／`design-evidence.md`），主產出物只留一行指過去。理由有兩個：①這四段**天生會隨每輪補挖無上限成長**，留在主檔會先撐破 200 行治理；②**其他所有產出物都有明文檔名，只有這四段沒有**——沒檔名就是每個執行者自己編路徑，下一個人不知道去哪找，而 Exit Criteria 又拿「有沒有這張表」當判準。
