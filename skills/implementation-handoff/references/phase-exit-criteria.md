# Implementation Handoff — Phase Exit Criteria 詳細清單

每個步驟的具體檢查項，全部確認才算 Phase 5 完成、可以進入 Phase 6。

> **「設計文件」在演進模式指哪一份**：從 `change-request` 轉來的既有專案變更**明文不產生完整設計基線**，下列各條的「依 API 規格／與設計文件不符」對照的是**該路徑實際存在的那一份**——「在既有範圍內」→ `docs/change-specs/<變更名>.md` 的輕量 spec ＋ 程式碼現況基線；「需要新設計決策」→ `system-design` 產出的 design-delta。**不得因為沒有完整設計文件就把這幾條標 N/A 或跳過回寫**：缺的是文件的完整度，不是「本專案沒有這回事」（N/A 條款的適用範圍見上方）。

## 步驟 21 資料庫建置
- 資料庫與資料表已依 DB schema 實際建立並可連線驗證，不是「應該可以」

## 步驟 22 後端 API 開發

- 品質門禁（型別檢查/lint/測試/build）已跑過，**這次異動新增/修改的程式碼** 0 issues；範圍外的既有問題（若有）已列進 `handoff-log.md`，不是默默略過

## 步驟 23 前端元件開發
- 元件依元件清單實作，可先用假資料
- 品質門禁已跑過，**這次異動新增/修改的程式碼** 0 issues；範圍外的既有問題（若有）已列進 `handoff-log.md`，不是默默略過

## 步驟 24 前端頁面組裝與串接
- 頁面已組裝完成，並接上步驟 22 的真實 API（不是假資料）
- 每個工作項目的驗收標準逐條可驗證，不是「大致做完」

## 測試資料與環境準備（全步驟一體適用）
- 已對照 `dev-setup`／`change-request`／`system-design` 產出的測試描述，逐條反推隱含的資料狀態需求——不是憑空猜要準備什麼，也不是等 Phase 6 測試跑起來才發現缺口
- 需要的資料／種子已在本機或隔離環境備妥；需要外部服務 sandbox 帳號／測試金鑰的，已取得或已回報使用者並記錄缺口
- **MUST NOT** 用共用 dev／staging／production 的正式資料或憑證頂替——理由與步驟21資料庫隔離要求相同
- 真的判斷不需要額外準備時，MUST 寫明具體理由並記錄——這是「內容判斷為無」，不是「這項檢查不適用」，不得套用 N/A 條款省略記錄本身

## 基礎安全（全步驟一體適用）
- **常見攻擊面已逐項對照**：注入、輸入驗證、密碼學用法、業務邏輯濫用（含跨站腳本與跨站請求偽造）、存取控制繞過、已知高風險套件——每項寫「本次怎麼防」或「本次不涉及＋理由」
- **第三方套件清單已隨本次變更同步更新**（含新增套件與版本）
- 實作出來的介面行為若與設計文件不符 → **已回寫設計文件**，不是讓文件跟程式碼各說各話
- **模組/類別結構與資料模型對應若與設計不符 → 同樣已回寫**（實作時拆出新類別、合併、改名、欄位對應改變都算）。設計階段畫的引用關係圖若沒隨實作更新，下一個人照它追邏輯會追錯——**這份文件的價值就是「不用翻程式碼」，一旦過期就是負值**

## 完工三關（SKILL.md 的「完工關卡」段，本檔同步；三關全過才可寫 `狀態：完成`）
- **第 1 關 品質門禁**：型別檢查／lint／測試／build，**這次異動新增/修改的程式碼**全部 0 issues，**且已附實際 command output**——不接受「跑過了」的口頭宣稱。指令來自 `dev-setup` 定義的那條（創世）或使用環境既有的門禁表。範圍外的既有問題不強制修，但已列進 `handoff-log.md`，不是默默略過
- **第 2 關 獨立覆核**：**已由實作者以外的角色覆核，不分 Tier**（編制與角度 → `../../sdlc-orchestrator/references/agent-teams.md`）。⚠ **「Lead 覆核輸出」不算**——Lead 是派工、定範圍、決定怎麼做的人，讓他驗自己派的活等於實作者自己勾自己的驗收項
- **第 3 關 最小改動確認**：diff 未超出票的範圍（無順手重構、無改到別的模組、無無關的格式或依賴變動）。判準＝**這一行拿掉的話，本票的驗收條件會不會不過**；答案是「不會」就該拿掉，真的該修另開一張票。**演進模式 MUST 逐項查**
- 覆核結果 `NEEDS WORK`／`FAIL` → **修完重審**，不是記錄一下就放行；重審時計數歸零（`severity-format.md`「重跑次數怎麼算」第 2 條）
