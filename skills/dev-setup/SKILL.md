# Dev Setup — SDLC Phase 4 開發前準備

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 18-20。**Lead-direct，版控步驟只能列清單，不自動執行。**

## 提問規則（本階段所有對使用者的提問一體適用）
需要使用者拍板的事（排程優先序、分支策略選擇等）**MUST 選項化**：每題附 2-4 個具體選項（建議的放第一個並標「建議」），使用者勾選或回編號即可；自由補充永遠允許。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。禁止開放式問答轟炸。

**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：追到**維度覆蓋表每一列都標「已答」或「使用者說不適用」**才算問完（不是「使用者沒再補」；還有任何一列是「進行中」或「未走」都不算）；動手前 MUST 列出自決事項清單與**殘餘猜測清單**，猜測清單非空不得產出。

## 觸發條件

**本 phase 限創世模式（全新專案）。** 三個步驟的 Output——骨架、版控、排程——對既有專案恆為既存，把它們當前置去卡增量變更，等於**為了改一個功能先解一個部署題**。

- 設計文件已確認（來自 `system-design` 或使用者直接提供），且**專案骨架尚未建立**
- 不適用：設計還沒做 → 先回 `system-design`
- 不適用：**既有專案的增量變更（演進模式）** → 不走本 phase，改由 `change-request`（在既有範圍內）或 `system-design`（需新設計決策）產出**測試描述**後直接進 `implementation-handoff`

⚠ **演進模式唯一不能丟的是「測試描述」**（下方附加產出），它已被移交給上述兩個 skill 承接——**跳過本 phase 不等於跳過測試描述**。
⚠ **例外**：既有專案要**新增一個獨立子模組／子專案**、骨架真的要從零建時，仍走本 phase，範圍限該新模組。

## 完成條件（Phase Exit Criteria）
3 個步驟 + 1 項附加產出的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 可運行的專案骨架
2. 版控就緒（只列清單，不自動執行）
3. 開發排程
4. 自然語言測試描述（依 `requirements-spec.md` 設計，見下方「測試描述」）
5. **品質門禁指令**——本專案「0 issues 才算過」的那條指令，逐條寫出可直接複製執行的實際命令並實跑過一次。⚠ **不能留到 Phase 5 才想**：`implementation-handoff` 完工第 1 關要求 0 issues ＋ 附 command output，卻明文「具體指令依專案自己的工具鏈」——沒有任何 phase 定義過它的話，Phase 5 會卡在一個從沒被定義過的門禁上。使用環境已有該技術棧的門禁指令表就直接引用

## 持久化
版控清單、開發排程、測試描述 MUST 寫成 `docs/dev-setup.md`；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。

⚠ **同名檔已存在時 MUST NOT 直接覆寫**——先讀它，再決定是併入、另存不撞名的檔、還是請使用者確認可以覆寫。專案骨架本身就是實際建立的檔案，天然已持久化，不用另外記錄。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測、風險清單。

## 流程

⚠ **這四項產出彼此沒有依賴，編號是閱讀順序不是執行順序。** 只有步驟 18 與品質門禁需要外部世界配合（裝得起來、版本相容），其餘三項（版控清單／開發排程／測試描述）純寫作、零外部相依。**任一項卡住時 MUST 先把其餘幾項做完再回頭**，不得停在原地——否則單點失敗會讓整個 phase 的可見產出歸零，看起來像「什麼都沒做」，實際上有 3/4 隨時可以完成。

### 步驟 18：建立專案骨架與開發環境
- Action：建 repo、專案結構、裝環境。**MUST 一併定義「本機一鍵啟動方式」**——新人 clone 下來後，用一個指令就能把東西跑起來。判準有三個：①**一個指令**（不是「先做 A 再做 B」）②**含相依**——資料庫／快取／訊息佇列／模擬器都要一起起來，只起主程式不算③**是可執行的檔案**（容器編排檔／`Makefile`／套件管理器的 script，如 `npm run dev`／自寫啟動腳本），不是文字步驟說明。<br>**工具不指定**：沒有外部相依的專案，直接跑執行檔、`java -jar`、`npm run dev` 就達標，硬套容器反而多餘；**有相依時容器編排通常是最省事的解**，但用別的方式只要滿足三個判準一樣算過
- 誰做：Lead 依技術選型執行；若在既有模組/專案內開發，骨架通常已存在，此步驟跳過（但一鍵啟動若不存在仍要補）
- Output：可運行的專案骨架 + 本機一鍵啟動方式

### 步驟 19：設定版控與分支策略
- Action：設定 Git、分支規則
- 誰做：**Lead 只列清單交給使用者執行**——NEVER 自動建 branch / push，本步驟不可自動化（版控安全紅線，不論哪個專案都適用）
- Output：版控就緒（清單形式：建議分支名稱、命名規則、目標 MR）

### 步驟 20：排定開發排程
- Action：排序、估時、排 timeline
- 誰做：Lead + 使用者
- Output：開發排程（依任務清單粗估，不用精確到工時）

### 附加產出：測試描述（掛在步驟 20 之後，不是獨立編號步驟）
- Action：對任務清單裡每個項目，用白話文寫「這個功能應該怎麼運作」——**依據 `requirements-spec.md` 需求規格書設計，不是照 `system-design` 的技術方案寫**（技術細節如 API 路徑、欄位名稱才對照 `system-design` 填進去）。例如「呼叫 `/api/orders/search` 帶 `status=pending`，應該只回傳待處理的訂單」。這段話寫在程式碼之前，是給 `qa-handoff` 撰寫真正測試的依據草稿，不是給開發者自己參考用——就算開發者事後看過自己的 code 才補測試，也不會把「code 現在的行為」誤當成「應該有的行為」。**MUST 同時涵蓋正向與反向情境（含綠地專案的紅軍測試），規則與最低涵蓋類別 → `../sdlc-orchestrator/references/test-case-coverage.md`**——只寫正向案例視為本項未完成
- 誰做：Lead + 使用者；**過目審查依 Tier 分級**（Tier 定義 → `../sdlc-orchestrator/references/agent-teams.md`）：Tier 0-1（單檔小改動）Lead 自己看過即可；Tier 2-3（安全/共用資料/多模組）MUST 給使用者看過確認才能落地成後續測試依據
- Output：自然語言測試描述（依任務清單項目逐條列，草稿性質，正向+反向情境皆須涵蓋，`qa-handoff` 會再對照 `requirements-spec.md` 覆核後才寫成真正的測試）

## 停止條件
- 使用者要求 Lead 直接建分支/push → 拒絕，這是版控安全紅線，改列清單交給使用者自己做
- 發現前面階段（`system-design`）的產出有問題（例如設計文件缺任務清單、範圍不清）→ 明確告知使用者要回 `system-design` 重新確認，不要在已知有問題的情況下把骨架/排程做完；確認要回頭後依 `../sdlc-orchestrator/sdlc-entry.md`「回歸」段回寫狀態（含連鎖回開判斷），不能只在對話裡講一講
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完
- **同一個技術問題連續失敗**（工具鏈／相依／環境裝不起來這類）→ **第 2 次失敗改為查證來源，第 3 次仍不通就停手**，不得繼續重試。判準是「**它擋不擋得住 Exit Criteria 的某一項**」——擋不住就不是本 phase 該解的，寫進 `docs/dev-setup.md` 的已知限制往下走；真的擋住才升級成阻塞問題並回報。⚠ 本條的存在理由：本 phase 是 Lead-direct，沒有 agent 派工的停損機制接手，**不明文寫就等於沒有停損**；使用環境另有更嚴格的停損規則時以更嚴格者為準

## 下一步
**Phase Exit Criteria 全過**（含自然語言測試描述）→ 提示使用者可以接著用 `implementation-handoff` **開始實際開發**（Phase 5 是真的寫程式：建資料庫、實作 API、做元件、組頁面，不是再檢查一次前置條件）。**不自動呼叫**，只是提醒。
