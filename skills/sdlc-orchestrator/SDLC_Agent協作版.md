# SDLC 主流程版 · Agent 協作設計

> **讀者：本包維護者。** 這是設計過程的內部記錄，不是使用說明。
> 要知道**怎麼裝** → 包根目錄的 `README-給同事.md`；**怎麼用** → `INSTALL.md`；**設計摘要** → `DESIGN.md`。
> 本檔提到的部分檔案路徑（如 `agents/sa.md`、`.claude/rules/*`）屬於維護者自己的環境，**不在這個包裡**，點不開是正常的。

> 沿用 `SDLC_主流程版_IAO.md` 的 8 階段結構。完整 35 步驟 Input/Action/Output 請對照原文；本文件呈現「為了讓 AI 協作進來，討論過哪些做法、選了哪個、為什麼」。
> 本檔是十三輪決策的完整演進史——部分早期拍板在後續輪的實測中被修訂（各段附「演進」說明，這些轉折本身就是設計過程的一部分）。

## 現況總表（最終運作狀態，2026-07-10）

**9 個 Skill**（skill = 給 AI 照做的一份流程說明書。8 個對應開發階段 + 1 個處理「做到一半冒出的新需求」；全部不綁公司內部工具、不綁技術棧，任何專案拿去就能用。每個做完都把產出寫成專案 `docs/` 資料夾下的檔案）：

| Skill | 做什麼 | Output 落檔（專案的 `docs/` 下） |
|-------|--------|--------------------------------|
| `product-discovery` | Phase 1 需求發想：問題本質/使用者/方案/可行性（對話引導） | `product-discovery.md` |
| `requirement-scoping` | Phase 2 需求分析：功能清單/範圍/優先序/規格/風險 | `requirements-spec.md` + `dependencies-risks.md` |
| `system-design` | Phase 3 設計：架構+DB+API+元件+模組（一組一起做）+ 開票（含票號） | `design.md`（可拆 architecture/db-schema/api-spec） |
| `dev-setup` | Phase 4 開發前準備：骨架/版控清單（人工執行）/排程 | `dev-setup.md` |
| `implementation-handoff` | Phase 5 實作：依任務票逐張開發（小改 AI 直接做，大票派 AI 分身，可多票並行） | `handoff-log.md`「## Phase 5」節（票號+檢查結果） |
| `qa-handoff` | Phase 6 測試：各層測試+獨立審查角度 | `handoff-log.md`「## Phase 6」節（含 bug 修正狀態） |
| `release-handoff` | Phase 7 部署：檢查清單+煙霧測試；**部署動作永遠人工觸發** | `handoff-log.md`「## Phase 7」節 |
| `ops-feedback` | Phase 8 維運：監控/回饋/優化，接回 Phase 1 成迴圈 | `feedback-log.md`（含 Monitoring 節+狀態欄） |
| `change-request` | 跨 phase 分診＝**既有專案的演進入口**（含跨包變更 SOP） | `change-log.md`（跨包時另有綁定層指定的單一真相檔） |

**3 個 Agent 角色檔**：
- `sdlc-implementer`——**寫程式的**：先看懂專案既有寫法再動手，寫完必須跑該專案的檢查工具到零錯誤才算完
- `sdlc-reviewer`——**看設計和邏輯的**：只讀不改，檢查功能做對了沒、設計合不合理
- `sdlc-verifier`——**找碴的**：立場是「先假設有問題，拿出證據才放行」，專查安全漏洞、或查「說測過了」到底有沒有真的測

**2 份共用參考文件**：`agent-teams.md`（判斷「這件事 AI 自己做、派一個分身、還是派一組」的分級表）、`severity-format.md`（審查發現的問題怎麼寫：分四級嚴重度、每個問題要附齊哪些資訊）。

**進場機制**：一張「開工前先查 `docs/` 有哪些檔案」的對照表（貼在各團隊自己的 CLAUDE.md 或 AGENTS.md 裡），查到對應階段就打開那份 skill 照做——Claude 和 Codex 使用者都適用。

## 怎麼應用：做完就關、看檔接力（介紹這套 skill 的核心）

**Output 位置**：所有 skill 的產出一律寫進「當下工作的那個專案」的 `docs/` 資料夾——位置相對各專案根目錄，不是固定路徑。（`docs/` 不存在 skill 會自己建）。

**接力機制**：每個階段做完就可以關掉 AI 對話、下班、換人。下次任何人重新打開專案（哪怕是一個全新的 AI、完全不知道之前聊過什麼），只要看 `docs/` 裡實際有哪些檔案，就知道現在走到哪、該進哪個階段：

```
docs/ 全空（且是新構想）              → product-discovery
有 product-discovery.md，缺 spec      → requirement-scoping
有 requirements-spec.md，缺設計文件    → system-design
有設計文件，缺 dev-setup.md           → dev-setup
有 dev-setup.md，handoff-log 無「## Phase 5」 → implementation-handoff
handoff-log 有 Phase 5、無 Phase 6            → qa-handoff
handoff-log 有 Phase 6、無 Phase 7            → release-handoff
已上線 / 有 feedback-log.md                   → ops-feedback
（既有系統出現新變更、範圍不明 → change-request，不論 docs/ 有沒有檔案）
```

這張對照表同一份內容放在三個地方：各團隊自己的 CLAUDE.md/AGENTS.md（安裝時貼進去的那段）、`DESIGN.md` 的正本、每份 skill 結尾的「下一步」提示。判斷永遠看「檔案存在不存在」，不靠任何人的記憶——所以「換人接手」「隔週繼續」「AI 重開一個對話」都是同一件事：打開 `docs/` 對表。

**驗證狀態**：已經用「完全沒有先前記憶的 AI」測過兩次（一次 Claude、一次 Codex），都只靠 `docs/` 檔案就正確接對了階段；目前正在做終極版實測——把一個專案清空從零開始，每個階段都換一個全新的 AI 接力，一路做到上線維運。另外兩條驗證線（2026-07-10）：①**冷啟動安裝實測**——user 本人另開全新環境，照 `DISTRIBUTION.md` 步驟實裝整包，驗證「同事拿到就能用」（進行中，結果回填第十三輪段）；②**平價模型路由測試**——用最便宜的模型跑進場判斷，四個情境 S1 已 PASS，S2-S4 待補。

## 為什麼長這樣——六條貫穿全部輪次的設計原理

每條都是被實測打臉後才成形的，不是先驗設計；對應輪次可翻後面完整史。

1. **顆粒度跟著產出物走，不跟著步驟走**（9 份不是 35 份）：綁在一起的步驟是同一份文件的連續形成過程，拆開等於把一件事切碎。真需要單獨跑某一步的，已有專門入口（`change-request` 分診後轉單一設計面向）。→ D2.5、第十二輪③
2. **狀態放檔案，不放對話**：每階段產出必落專案 `docs/`，下一棒（新對話、另一個 AI、另一個人）靠讀檔接手。這是「跑流程不需要協調者」的前提——接力棒在 `docs/` 裡，不在誰的記憶裡。→ 第六輪持久化反轉
3. **流程通用、綁定分層**：skill 本體不寫死任何環境工具；「這個 phase 用什麼工具」只放各團隊自己的 CLAUDE.md/AGENTS.md 綁定層。教訓：「解法綁環境」前後復發四次，是本設計最容易犯的病。→ 第七輪、第十一輪
4. **自動觸發是加分，Entry Protocol 是保底**：白紙測試證明不能賭 AI 自己想到要查 `docs/`，所以把「開工先查現況再定階段」寫成貼進 CLAUDE.md/AGENTS.md 的固定文字，Claude/Codex 都走得通。→ 第五輪、第九輪
5. **問人要給選項**：需求方是人，開放式問題轟炸是把整理成本丟給對方。AI 推測得出的先寫成選項讓人勾選，猜不出的才開放問。→ 第十二輪①（真實運轉第一棒當場學到）
6. **任何宣稱都要過證據關**：階段有 exit criteria、審查有嚴重度格式、「修好了」要冷測試、連審查意見本身也要驗證（第十三輪 Tier 誤報案例）。文件多了必有滯後——靠機械 diff 與交叉稽核接住，不靠自律。→ 第九輪、第十三輪

## 四個關鍵決策

### D1. 這套流程要管多大範圍

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 全流程包裹 | 8 階段（需求→維運）全部涵蓋 | ✅ |
| 只做前段規劃 | 只做需求→設計，後面交給既有開發流程接手 | |
| 純檢查清單 | 只給一份可勾選的流程表，不涉及 AI 協作 | |
| 純部門 SOP 文件 | 只是一份給人看的流程規範，跟 AI 助手無關 | |

**理由**：既然是「Agent 協作 SDLC」，就要涵蓋整個流程，才看得出每個階段 AI 能幫上什麼忙；後段（開發/測試/部署）不重做，直接沿用既有流程

### D2. 流程要拆成幾份 Skill 文件（討論兩輪，第二輪推翻第一輪）

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 一份總管文件 + 附屬細節 | 8 個階段的細節都收在同一份文件底下的附屬章節 | 第一輪選中，後改 |
| 8 份各自獨立的階段文件 | 一個階段一份，彼此不互相依賴 | ✅ 第二輪改選 |
| 用自動化腳本全程串接 | 寫程式讓 AI 自動依序執行全部 8 階段，不需人工介入 | |

**第一輪理由**：只有一個入口好找、狀態好追蹤；另外 Claude Code 對單份指令文件有長度限制，拆太細反而管理成本高

**改選理由**：這是給部門團隊用的流程，希望之後能做到「AI 依照當下情況，彈性引用需要的那幾個階段」——這件事要求每個階段的文件本來就是獨立存在、可以被單獨引用的單位；如果全部綁在同一份總管文件裡面，就沒辦法被彈性引用

**✅ 已解決（演進：本做法後於第七輪跨專案實測中修訂——Phase 5-8 改為完全自包含，工具綁定移到各團隊自己的 CLAUDE.md 綁定層；以下為當時決策原文）**：第五到第八階段（開發實作/測試/部署/維運）的文件，不會在背後自動幫忙觸發「開發功能」「三方審查」「部署稽核」這些既有流程。原因是：讓一個 AI 協作模組在背後直接觸發另一個模組，一旦出錯很難追蹤是哪個環節壞掉，風險太高。做法改成：這幾個階段的文件只負責「確認前置條件是否備齊」，然後提醒現在該去用哪一套既有流程，真正執行還是交給人工或既有流程自己觸發。這跟現有 `debug` 文件「找到根因了，去用 `fix` 流程」是同一種銜接模式——既有專案本來就這樣運作，不是新發明，只是把既有做法套用到新的階段文件上。

### D2.5 為什麼 35 個步驟最後變成 9 份 Skill，不是 35 份

`SDLC_主流程版_IAO.md` 原文有 35 個步驟，但拆分的最小單位從一開始就不是「步驟」，而是原文本來就分好的「8 大階段」。理由：同一階段內的步驟是連續、緊密相關的同一段工作，拆成一步一份文件只會把同一件事切得支離破碎，沒有實際好處（詳見上方 D2 的「一份 vs 8 份」討論，那次比較的單位本來就是階段，不是步驟）。

| 階段 | 步驟範圍 | 對應 Skill | 為什麼是這個顆粒度 |
|---|---|---|---|
| 一、需求發想 | 1-5 | `product-discovery` | 5 步是同一段對話式引導，一路問下去中間不會被打斷去做別的事 |
| 二、需求分析 | 6-10 | `requirement-scoping` | 功能清單→範圍→排序→規格→風險是連續遞進的思考過程，同一份文件講完 |
| 三、設計 | 11-17（7步）| `system-design` | 架構/資料庫/API/前端/模組拆分是同一個角色（`sa` agent）換不同輸出面向在做，步驟17還要把前面全部彙整成一份設計文件——本質上是同一個產出物的形成過程，不是7件互不相干的事 |
| 四、開發前準備 | 18-20 | `dev-setup` | 建骨架/設版控/排時程，都是「開工前最後準備」，做完直接進開發 |
| 五、開發實作 | 21-24 | `implementation-handoff` | **不重寫**——這4步在既有專案已有成熟的 `feature`/`fix` 流程在做，新開一份 skill 重寫等於做兩套會打架的邏輯，所以只負責「確認可以開工」，真正動手交給既有流程 |
| 六、測試 | 25-28 | `qa-handoff` | 同上，既有專案已有多角色審查 review 在做 |
| 七、部署 | 29-32 | `release-handoff` | 同上，既有專案已有 CI/CD 稽核 + pipeline 在做 |
| 八、維運 | 33-35 | `ops-feedback` | 監控/回饋/優化沒有既有機制覆蓋，是新內容；優化後若有新需求，這份 skill 負責接回第一階段形成迴圈 |
| （額外）| 不對應特定步驟 | `change-request` | 步驟9（需求規格書）跟步驟17（設計文件）有雙重性質：專案剛開始整段寫一次，之後每次變更需求又要再寫一次（規模小很多）。這個「增量變更」情境原文35步驟裡沒有專門對應的步驟，額外開一份 skill 接住，是為了填補原文沒講清楚的縫隙，不是某個步驟的化身 |

**演進（第七輪）**：上表五~七的「不重寫、交給既有 feature/fix/三方審查/CI/CD 稽核」在跨專案實測後修訂——Phase 5-8 現為完全自包含（照 IAO 步驟 21-35 自己執行），與既有專案工具的銜接改放 `<你的專案>/CLAUDE.md`「SDLC Phase 5-8 綁定」段。**顆粒度結論（一階段一份 skill）不變**，變的只是 Phase 5-8 的內容從「轉交」變「自做」。

**核心判斷原則（演進同上：「交給既有機制」部分已於第七輪修訂，顆粒度判斷仍有效）**：新開一份 skill 值不值得，取決於「這件事有沒有既有機制在做」——步驟1-20（需求發想到開發前準備）在既有專案完全沒有對應的既有流程，這4份 skill 是真正的新內容；步驟21-35（開發實作到維運）已有成熟流程在跑，新開的4份 skill 故意寫得很薄（只做「檢查前置條件+提醒轉交」），避免同一件事被兩套邏輯各管一次、日後改一邊忘了改另一邊。

這也是「35 步驟沒有變成 35 份文件」的根本原因：步驟是原文用來說明「這階段要做什麼」的顆粒度，但「該不該獨立成一份 skill」的判斷標準是「這件事有沒有被既有系統覆蓋、還是全新內容」——這個判斷天然是以「階段」為單位在做，不是以「步驟」為單位。

### D3. 每個階段怎麼確認「真的做完了」

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 沿用既有的五項檢查 | 既有專案現有派工前已有一套「該不該進一步設計」的五個檢查問題，直接套用 | |
| 每階段自訂一套檢查清單 | 8 個階段各自定義「做完的標準是什麼」 | ✅ |
| 不設正式檢查 | 依流程表順序走完就算數，沒有驗收關卡 | |

**理由**：讓檢查標準跟每個階段的實際內容更貼合，不硬套一套原本為別的用途設計的檢查表

**討論過程**：一開始發現新檢查清單跟既有五項檢查在「設計階段」（邊界條件、回滾方案等）內容有重疊，考慮過「兩邊都用、分工管不同顆粒度」的做法，但後來覺得這樣還是會有兩邊同時要維護、容易改一邊忘了改另一邊的風險。

**最終決定：改成「依路徑決定用哪一套」，不是內容分工**
- 走完整 SDLC 流程（經過 `system-design` 這份 Skill）的工作：只用新的階段檢查清單，**不再額外套用**既有五項檢查，避免同一件事重複檢查一次
- 沒有走完整 SDLC 流程的工作（例如小型 bug fix、個人非正式專案、小工具開發，直接用 `feature`/`fix` skill）：**維持現況，繼續用既有五項檢查**，這部分不受本次設計影響，保留原本的開發彈性

這樣兩套檢查機制不衝突：差別在於「這件工作有沒有走公司 SDLC 正式流程」，不是「哪一套內容比較準」。

### D4. 這套流程要不要設計成通用版

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 拆兩層：通用原則 + 既有專案專屬版 | 通用原則獨立一份，之後其他團隊也能直接套用；既有專案版才寫「銜接哪個既有流程」 | |
| 不拆層，直接寫既有專案專屬版 | 內容直接綁定既有專案現有的開發工具與流程 | ✅ |

**理由**：先求真的能落地使用，之後若要推廣到其他團隊，再回頭抽出通用的部分

**⚠️ 澄清（初步驗證測試時發現需要講清楚）**：「綁既有專案」是指技術上直接接既有專案現有的 skill/工具（`feature`/`fix`/多角色審查/`CI/CD 稽核工具`），**不是限定只能用在 既有業務領域 相關專案**。公司要開發的任何項目都要走這套流程，不分領域。
**演進（第七輪）**：「技術上直接接」這半句後續再修訂——skill 本體現已完全領域中立、不寫死任何工具名，既有專案綁定只放在 `<你的專案>/CLAUDE.md` 綁定層；「任何項目都走這套流程」的範圍宣告仍有效。

## Input/Output 怎麼在階段之間交接

**第六輪已反轉**：AI 助手 **MUST 負責保存與建檔**。每個階段的 Skill 引導這階段該問什麼、該產出什麼概念性成果，且必須把實際的需求規格書、設計文件、ER 圖等產出物寫成 markdown 檔案存進專案的 `docs/` 資料夾（專案尚無此資料夾就直接建立），不可只停留在對話裡。原本「給部門通用、不綁定個人工具」的顧慮，user 在實際使用後明確選擇放棄，理由是持久化的實際價值更重要——完整討論過程見下方「第六輪」段落。

## 拍板結果：8 份 Skill——第一輪快照（現況為 9 份：第四輪 +`change-request` 分診）

## 8 份 Skill 建好後，第二輪討論的 4 個補強決策

### E1. 什麼時候該從第一階段開始，什麼時候可以直接跳後面

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 用工作規模判斷 | 規模大→走全流程，規模小→直接用既有開發流程 | 曾提出，自我推翻 |
| 用「確定性」判斷 | 問題/使用情境/解決方案只要有一項還不確定→從第一階段開始；都已明確→不論規模大小直接跳後面階段 | ✅ |

**為什麼推翻「用規模判斷」**：規模本來就是做完需求發想才會知道的東西，拿最後才知道的規模去決定「要不要做最先的步驟」，邏輯是繞圈的。改用「確定不確定」判斷才站得住腳。

### E2. 流程做到一半，發現前面階段其實有問題怎麼辦

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 8 份 Skill 統一補一條規則 | 發現前面階段有問題→明確講清楚要回哪一階段重新確認，不能明知有問題還硬做下去 | ✅ |
| 只在後段（風險較高的階段）補 | 只加在設計階段之後 | |
| 不特別處理，靠 AI 本身的判斷力 | | |
| 另外做一份共用文件給 8 份 Skill 一起參照 | | 跟「8 份彼此獨立」的既有原則衝突 |

### E3. 其他階段要不要也比照第三階段（設計）做正式的完成度檢查清單

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 全部都比照著補齊 | 8 個階段都有自己的正式檢查清單，風格一致 | ✅ |
| 只挑重要的補 | 只給某幾個關鍵階段補 | |
| 都不補，維持簡易版 | | |

**補的時候怎麼避免跟既有流程打架**：第五到第七階段（開發實作/測試/部署）的檢查清單刻意只檢查「有沒有正確交接」，不重複檢查程式品質本身——程式品質已經有既有流程在把關，這裡不重做一次。

### E4. 「AI 依情況彈性組隊」這件事，現在要做到什麼程度

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 先不做，等真的遇到需求再設計 | | |
| 只先寫下未來設計時要注意的限制條件 | | |
| 先在最容易派上用場的地方做一個小範圍雛形 | 只限「設計階段的架構評估」這一步，多找幾個角度（效能優先/成本優先/維護性優先）平行比較方案，其他階段不受影響 | ✅ |

這不是整套「8 份 Skill 互相彈性引用」的完整解法，只是先在最明顯需要多角度比較的地方，做一個小範圍的示範。

## Agent 派工怎麼做（第三輪討論）

### F1. 設計階段要派誰做架構/資料庫/API 設計

既有的 `sa`（系統分析）角色原本只用來寫「單一 PR 的規格」，跟「畫系統架構圖、ER 圖、API 規格」不是同一件事，格式對不上。

| 選項 | 說明 | 選中 |
|---|---|:---:|
| 新開一個專門的設計角色 | 跟既有的 `sa` 角色並存，各司其職 | 一度選中，後推翻——擔心「為了 SDLC 特地弄一組員工」，AI 助手角色不該分太細 |
| 擴充既有的 `sa` 角色，不新開 | 同一個角色多一種用途，用的時候講清楚是哪一種 | ✅ |
| 就將就用，不改 | 格式不貼合但省事 | 落差是真的問題，沒選 |

**最終做法**：`sa` 角色現在有兩種用途——原本的「寫單一 PR 規格」跟新增的「寫系統設計產出（架構/資料庫/API/前端元件/模組拆分，一次只做一種）」。同一個角色，用的時候講清楚要用哪一種，不是開兩個角色。
**演進（第七、八輪）**：本做法在 SDLC 範圍內後續取消——`system-design` 改用通用的 Lead-direct/派工判斷（`sa` 雙用途只留給既有專案非 SDLC 場景）；第八輪另立 3 份 `sdlc-*` 角色檔。與本輪「不新開角色」不矛盾：當時否決的是「綁既有專案的 SDLC 專屬分身」，第八輪開的是領域中立、隨這套 skill 一起分發的可攜角色。

### F2. 需求發想/需求分析階段可以派 AI 幫忙調查，但邊界要講清楚

原本寫得比較模糊，現在明確定義：只能做「唯讀調查」（查資料、查現有系統，不能改任何東西），因為這兩個階段都還在釐清方向，還沒真的要動手做。

## 第四輪：一次性 vs 重複用，新增第 9 份 Skill

### G1. 35 個步驟裡，哪些只做一次、哪些每次新任務都要重複做

對照原文逐步分類後發現：大部分步驟很單純（要嘛只在專案剛開始做一次，要嘛每次新功能都要重複做），但**需求規格書（步驟9）跟設計文件（步驟17）是特例**——專案剛開始是完整重量級版本，之後每次有新的變更需求，又要再寫一次，只是規模小很多。這個「特例」就是後續要接住的東西。

### G2. 專案進行中出現新變更，要怎麼接

| 方案 | 說明 | 選中 |
|---|---|:---:|
| 開一個新 Skill，自己做輕量版的範圍界定+設計+開票 | Lead 原本的草案 | 被自己推翻——這場討論已經連續 3 次發生「差點重複造一套邏輯，最後都改成用轉交解決」，這個草案有一樣的風險：會變成第二個縮小版「設計」Skill |
| 不開新 Skill，比照 `sa` 角色的做法在既有 Skill 裡加「輕量模式」 | 邏輯上最一致 | 跟已經決定要開新 Skill 的方向不符 |
| 開一個新 Skill，但只負責「對照既有文件、判斷這次變更該去哪」，自己不做設計 | 核心價值是檢查新變更跟既有需求/設計文件一不一致——這件事目前沒有任何 Skill 在做 | ✅ |

**最終設計（`change-request`，第 9 份 Skill）**：不做需求分析、不做設計，只做「分診」——對照既有需求規格書/設計文件，判斷這次變更該走三條路的哪一條：瑣碎且在既有範圍內 → 輕量開票交 `feature`/`fix`；牽涉新的設計決策 → 轉 `system-design` 只做需要的那個面向；其實是全新方向 → 轉 `product-discovery`。

## 第五輪：AI 沒照著新流程走的問題

**問題**：9 個新流程做好後，AI 實測時還是直接跳去舊的開發方式——兩份規則清單文件沒有更新，AI 只看得到舊規則裡「新功能 → 直接寫程式」。

**修正**：兩份規則清單文件補上判斷原則：需求還不清楚 → 先走新流程；需求已經清楚 → 才直接開發。

**驗證**：找一個沒看過這次討論的全新 AI，實測同樣情境，結果正確走新流程、沒有跳過確認需求就動手。

**保留**：測試用模擬環境進行，非正式重開對話驗證；因果尚未 100% 切割證明，但結果與預期一致。

## 第六輪：Output 持久化政策反轉

**觸發**：用一個獨立的測試專案實測整套 9 份 SDLC skill，`product-discovery`/`requirement-scoping` 階段 user 主動要求把每階段討論產出寫成 `docs/` 下的 md 檔。跑完 Phase 1-2 後回頭問「這是因為我要求你，還是 skill 有說要做」——如實回答：skill 本來允許純對話（例如 `product-discovery` 步驟1明寫「條列式即可，不用正式文件」），這次持久化純粹是這次臨時要求，跟三份設計文件白紙黑字寫的「不負責持久化」政策衝突。

**決定**：user 選擇「全面改成必須持久化，刪掉部門通用性説法」——放棄「部門任何人（含沒裝 agentic coding tool 的同事）都能走這套流程」的原始設計目標，換取「用 Claude Code 實際跑這套流程時，產出物不會隨對話消失」的實際價值。

**落地**：9 份 SKILL.md 都加上「## 持久化」規則（各 phase Output MUST 寫成專案 `docs/` 下的 md，資料夾不存在就直接建立）；`change-request` 額外連動修正：步驟1「取得既有脈絡」從「只能靠使用者貼內容」改成「優先搜尋專案 `docs/` 資料夾」，步驟3「記錄分診結果」從「提醒使用者自行記錄」改成「MUST 寫進 `docs/change-log.md`」。

**保留**：本輪只反轉持久化政策本身，沒有重新設計「phase 之間要不要自動讀取對方寫好的 docs/ 檔案」（例如 `requirement-scoping` 開始時自動 Read `docs/product-discovery.md`）——這個更進一步的聯動問題留待下次有具體需要再議。

## 第七輪：Phase 5-8 從「轉交既有工具」改成「完全自包含」

**觸發**：用測試專案實際走到 Phase 5，發現 `implementation-handoff` 寫死「轉交 `feature`/`fix` skill」——但 該測試專案是 Next.js 專案，`feature`/`fix` 是既有專案 Java/Vue 專屬工具，用不上。Lead 第一次修正時換成「呼叫 `typescript-dev`」，被 user 抓到這是換個對象犯同一種錯——`typescript-dev` 一樣是 Lead 個人環境才有的東西，其他同事不一定裝了。

**決定**：user 明確拍板「所有流程都按照 `SDLC_主流程版_IAO.md` 去設計，不要再管現有的 skill/agent」——這是給團隊用的通用流程，不能繼續假設對方有 `feature`/`fix`/多角色審查/`CI/CD 稽核工具`/`sa` agent 這些既有專案專屬東西存在。

**落地**：`implementation-handoff`/`qa-handoff`/`release-handoff`/`ops-feedback` 從「檢查前置條件+轉交既有工具」整個改成跟 Phase 1-4 一樣自包含——直接照 IAO 步驟 21-35 的內容自己執行，不轉交任何外部工具。`system-design` 拿掉重度依賴的 `sa` agent 雙 mode 設計，改成 Lead-direct/派工的通用判斷。同時發現一個新缺口：原本「Lead-direct 或派工皆可」沒有給判斷門檻，導致 Lead 在測試專案全部自己寫、完全沒派工——補上具體門檻：單一票 ≤20行/單檔/無新依賴 → Lead-direct；超過就 MUST 派工，多張獨立票平行派。

## 第十一輪：一次性 vs 重複用——創世/演進兩種生命週期（2026-07-10）

**觸發**（user 提出新框架）：SDLC 步驟其實分兩類生命週期——**一次性「創世」**（蒐集原始需求、技術選型、整體架構：專案生一次，之後漏掉的東西走 CR，不會回頭重跑）與**重複用「演進」**（每次新功能都要走的一整組：需求-delta → 設計-delta（架構/DB/元件一組一起做）→ 實作 → 測試）。而且新開專案與既有專案都要能套同一套流程——舊專案不需要技術選型，但一樣有 CR、需求分析要做。

**對照檢查發現的真缺口**：第四輪其實碰過這個維度（35 步驟逐一分類、發現步驟 9/17 雙重性質、開出 `change-request`），**但只解了一半**——`change-request` 寫死「找不到 `docs/` 既有文件 → 當成新方向退回 `product-discovery`」，承重假設是「專案有創世期文件」。具體失敗場景：後端主專案這種跑三年、從沒走過這套 SDLC 的舊系統要加一個需要新 schema 的功能，`docs/` 是空的 → 會被誤判成全新構想送去需求發想。**任何成熟 codebase 採用這套流程的第一天都會踩到。**

**修法（最小路由修法，不拆新 skill）**：
1. 分辨軸從「`docs/` 有沒有文件」改成「**有沒有既有系統**」——看得到程式碼/在跑的服務就算，缺文件 ≠ 新構想
2. `change-request` 步驟 1 改三層 fallback：`docs/` 文件 → **程式碼現況當基線** → 只有純全新構想才退 `product-discovery`；轉去 `system-design` 做單面向 delta 時，產出的 `design.md` 順手替舊專案補上基線，下次變更就有得對照
3. `CLAUDE.md` Step 0 明文拆成創世模式（新構想）與演進模式（既有系統），Entry Protocol 同步
4. **跨包變更 SOP**（同輪 user 追問「改 既有業務領域 幾包的需求會怎麼跑」發現的第二個缺口）：跨 ≥2 repo 的變更，需求級單一真相記錄（規格 delta + 涉及包 + 各包狀態表）——**位置由各環境綁定層指定**，可攜層只講機制。Lead 第一版把位置寫死 `<你的專案>/doc/`，被 user 當場抓到「同事們的路徑不一定是這個」——**這是「解法綁環境」錯誤的第四次變體**（前三次：feature/fix 轉交、typescript-dev、hook 提案），也再次證明這個 pattern 是本設計最容易復發的病。

**為什麼不拆新 skill**：第四輪已三次因「別重複造第二套邏輯」否決類似方案；設計活動的 grouping（架構/DB/API/元件一組）`system-design` 本來就滿足。這個洞見的正確落點是**路由層**（誰接住既有專案的變更），不是 skill 顆粒度。

## 第十二輪：第一次真實全流程運轉，當場修出來的規矩（2026-07-10）

把一個專案資料夾清空、從零真跑整套流程（user 本人當需求方），第一棒（需求發想）一開口就暴露問題、當場立了新規矩：

**① 提問必須選項化（Phase 1-4 全部適用）**。第一棒照舊版 skill 對需求方丟出五題純開放式問題（「你想放什麼功能？為什麼想做？」），user 當場判定不合格——需求方是人，開放式問題轟炸回答成本太高。修法：四份開發前 skill（`product-discovery`/`requirement-scoping`/`system-design`/`dev-setup`）+ `change-request` 的確認環節，統一加「提問規則」：**每題附 2-4 個具體選項（AI 最建議的放第一個標「建議」），使用者勾選或回編號即可，自由補充永遠允許**；一次一批 ≤5 題；AI 能推測的先寫成選項讓人確認，猜不出來的才開放問。原則：選項是降低回答成本，不是限制答案。

**② 用法釐清：跑流程不需要「派工」**。這套 skill 的正常用法就是使用者自己開一個對話（用平價模型即可），skill 觸發 → 做完該階段 → 關掉；下次再開新對話接下一階段。「一個 skill 做完等下一個」，中間不需要任何協調者。多 AI 派工只出現在 Phase 5/6 的票量大時（由該階段的 AI 依分級表派）。

**③ 常見疑問收錄：「35 個步驟變 9 份 skill，是不是有些本來能獨立跑的步驟被綁在一起了？」** 答：綁在一起的步驟，是因為它們**本來就是同一份產出物的連續形成過程**（例如設計階段的架構→DB→API→元件→模組，最後彙整成同一份設計文件；拆開反而把一件事切碎）。真正需要「單獨跑某一步」的情境，其實已經有專門入口：變更時只需要補一個設計面向 → `change-request` 分診後轉 `system-design` 只做那一個面向；需求已明確 → 直接跳過前面階段。所以不是「被迫一起跑」，是「該一起的一起、該單獨的有單獨入口」——若未來實測發現某個步驟常常被單獨需要而沒有入口，再抽出來，不預先拆。

## 第十三輪：發佈前的三軍交叉稽核（2026-07-10）
