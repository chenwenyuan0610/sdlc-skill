# Product Discovery — SDLC Phase 1 需求發想

依 `../sdlc-orchestrator/SDLC_主流程版_IAO.md` 步驟 1-5，引導使用者從零散訴求走到可行方案。**對話式引導流程，Lead 全程主導，不派 agent 執行實作**（步驟5可選派 general-purpose 做技術可行性調查）。

## 提問規則（本階段所有對使用者的提問一體適用）
向需求方提問 **MUST 選項化**：每題附 2-4 個具體選項（把你最建議的放第一個並標「建議」），讓使用者勾選或回編號即可；自由補充永遠允許——選項是降低回答成本，不是限制答案。一次一批 ≤5 題；後面的題目依賴前面答案時分批問。**禁止純開放式問題轟炸**（「你想要什麼？」）——把你能推測的先寫成具體選項讓使用者確認，猜不出來的才開放問。

**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：本階段是需求挖掘的源頭，**抽象標籤不算挖到需求**——收到抽象答案 MUST 追問「你上次真的想查、但查不到的那一句話原話是什麼」；追到**維度覆蓋表每一列都標「已答」或「使用者說不適用」**才算問完（不是「使用者沒再補」；還有任何一列是「進行中」或「未走」都不算）；寫 `docs/product-discovery.md` 前先列出「我打算自己決定的事項清單」。

## 觸發條件
**用「確定性」判斷，不是用「規模」判斷**——規模是需求發想後才會知道的東西，拿最終規模去決定要不要先做需求發想是循環依賴。
- 問題本質、目標使用者、解決方案任一還不確定 → 走本 skill，不論預期規模大小
- 問題、情境、方案都已經明確 → 不適用。**去哪一站，看你手上已經有什麼**（三處措辭以本表為準：frontmatter、本段、使用環境的觸發詳表要一致）：

| 手上已有 | 去哪 |
|---|---|
| 只有明確的方案，還沒有需求規格 | **`requirement-scoping`**（它的觸發條件正是「已有可行方案」）|
| 已有需求規格，還沒有設計文件 | `system-design` |
| 設計文件也有了，骨架還沒建 | `dev-setup` |
| 已經是既有系統要改東西 | `change-request` |

⚠ **不要直接說「跳到後面的 phase」就了事**——`system-design` 要求「需求規格書已存在」、`dev-setup` 要求「設計文件已確認」，**方案明確不蘊含這兩件事**，直接跳過去會被那一站的觸發條件擋下來。

## 完成條件（Phase Exit Criteria）
5 個步驟的 Output 都產出，且通過本階段專屬檢查（完整條目 → `references/phase-exit-criteria.md`）：
1. 原始需求清單
2. 問題陳述 + 商業目標
3. 使用者與情境描述
4. 候選方案清單（≥2 個，不收斂）
5. 可行方案（含技術/時間/成本初步評估）
6. **維度覆蓋表**（十一支維度逐列標「已答／進行中／使用者說不適用／未走」，格式與判準 → `../sdlc-orchestrator/references/questioning-sufficiency.md` 規則一）

**⚠ 硬性關卡**：**維度覆蓋表上還有任何一列**不是「已答」或「使用者說不適用」**（含「未走」「進行中」）→ MUST NOT 進入步驟 4（發想方案），也 MUST NOT 宣告本 phase 完成。** 停止條件是「每一列都是已答或不適用」，**不是「使用者沒有再補」**——後者由執行者控制取樣，等於沒有關卡。使用者主動補了不在任何選項裡的需求 → 覆蓋不足實證，MUST 回補一輪並在文件記明第幾次。
**且「已答」的判準是深度不是勾選**：該維度的答案要足以寫出可驗收條件，答不出來就是「進行中」（規則一 1-E2）。
**且 MUST 另列「殘餘猜測清單」並清空**（規則四 4-A）：清單非空就不准寫產出物，每項只能「問掉」或「使用者明確放行你猜」；放行的 MUST 在文件裡標成假設並註明誰放行。**未標記的猜測讀起來跟已確認需求一模一樣，下游會拿它當依據繼續蓋。**

## 持久化
5 個 Output MUST 寫成 markdown 檔案存進專案的 `docs/` 資料夾（例如 `docs/product-discovery.md`）；專案尚無 `docs/` 資料夾就直接建立，不用先問使用者。不可只留在對話紀錄裡，檔案不存在視為本階段未完成。

⚠ **同名檔已存在時 MUST NOT 直接覆寫**——先讀它，再決定是併入、另存不撞名的檔、還是請使用者確認可以覆寫。

**開票時機**：Phase Exit Criteria 全部通過、確定要往下走、即將寫出這份定案版 `docs/product-discovery.md` 的當下，Lead 才開一張工單（不是步驟 1 一有想法就開，討論階段本來就不產出正式產出物），並在文件裡引用這個工單號。**全程只在這裡開一次票**——後續 phase（含 `system-design` 步驟 16 拆出的工作項目）都掛在同一個工單號底下，不再另開新票。工單的編號、欄位與狀態機照 `../sdlc-orchestrator/references/ticket-spec.md`（工作票型 `ISSUE-nn`）。用哪個工單系統由使用環境的 CLAUDE.md / AGENTS.md 綁定層指定；**綁定層沒指定、或專案查不到可用的工單系統時 MUST 停下來問使用者這次的工單號要怎麼處理（選項化，例如：改用 `docs/` 內的文件工單／使用者自己開好給號／本次不開票），不要自己編一個號，也不要默默跳過**。⚠ **編號判準**：「不要自己編號」只適用**已接工單系統**時——那時號碼必須由系統自動生成，人與 AI 都不得發明；**本機開發／未接工單系統的專案，自編 `ISSUE-nn` 即可**，並在文件註明日後接上系統要以系統號為準並回填。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測、風險清單。

## 流程

### 步驟 1：蒐集原始需求
- Action：訪談、記錄、彙整使用者的零散訴求
- 誰做：Lead 直接問使用者，不派 agent
- Output：原始需求清單（條列式即可，不用正式文件）

### 步驟 2：釐清問題本質與商業目標
- Action：對每條需求追問「為什麼」，挖出真正要解決的問題
- 誰做：Lead 對話
- Output：問題陳述 + 商業目標（1-2 句話）

### 步驟 3：定義目標使用者與使用情境
- Action：描繪誰會用、在什麼情境用
- 誰做：Lead 對話
- Output：使用者與情境描述

### 步驟 4：發想解決方案
- Action：擴散發想多個解法，**不收斂**，至少 2 個候選
- 誰做：Lead 對話，可主動提議方案讓使用者評估
- Output：候選方案清單

### 步驟 5：初步可行性評估
- Action：從技術/時間/成本角度評估每個候選方案
- 誰做：Lead 對話；技術細節不確定時，可選派 `general-purpose` agent 做技術可行性調查（本階段唯一允許派 agent 的步驟）。**唯讀**：只給 Read/Glob/Grep/WebSearch，不給 Edit/Write，這階段還沒真的要動手實作，agent 只做調查不做決策
- Output：可行方案（1 個，附評估理由）

## 停止條件
- 使用者對候選方案還在猶豫、想不清楚 → 不要強行收斂，留在步驟 4/5 繼續討論
- 使用者跳過需求發想直接要功能規格 → 提醒這樣會跳過本階段，確認使用者真的要跳過再放行
- 本輪是從 `ops-feedback` 迴圈重跑 → 先確認上一輪是哪裡出了問題才需要重跑，不要照抄上一輪的答案
- 卡住的原因是**流程規則本身**（規則寫死了不適用本專案的做法／兩條規則矛盾／判準模糊到判不出來／缺一步接不上）→ **不要就地改規則、不要停工**：append 一列到**框架缺陷登記簿**（status=`proposed`，**證據欄必填**）。登記簿位置 → `../sdlc-orchestrator/references/framework-defects.md`；**該檔可能是登記簿本身，也可能是指向使用環境實際登記簿的指標檔，打開照它說的走**，然後用最接近的合理解讀把工作做完
