# 流程裁剪（哪幾關可以不跑）

> ⚠️ 修改本檔案前後，MUST 依 `../CHANGELOG.md` 的規則記錄異動。

> **這份檔案解決什麼**：不是每個專案都該跑滿九關，但「少跑幾關」如果靠臨場判斷，同一種專案這次跳過設計、下次沒跳，**沒人說得出為什麼**。這份定義唯一合法的裁剪方式。
>
> **誰引用它**：Step 0 定位、四個會寫 `docs/handoff-log.md` 的 phase。**本檔是裁剪規則的唯一擁有檔**，別處只放指標。

## 一條不變式（先讀這條，其餘都是它的配套）

> **檔案缺席永遠只能解讀成「還沒做」；唯有一份正面存在的宣告，才能解讀成「刻意不做」。**

**為什麼需要它**：定位機制判斷「這個專案做到哪一關」的方式，是看 `docs/` 裡有哪些產出物。一旦允許裁剪，「檔案不在」就有兩種意思——**還沒做**，還是**決定不做**？定位機制立刻分不出來。

把缺席鎖成單義，兩義性就消失了。代價是**要跳過一關必須先動筆寫一筆**——這個摩擦正是要的東西，它把「默默少做」變成「留下紀錄的決定」。

## 三個配套

| # | 機制 | 內容 |
|---|---|---|
| 1 | **模式宣告** | 專案放一個單行檔 `docs/sdlc-mode.md` 宣告用哪種模式。**模式與關卡的對照表固定在本檔，專案不得自訂**（否則各專案會發明自己的組合，裁剪就失去可比性）。**找不到宣告檔 → 當「全跑」**——舊專案行為完全不變，零遷移成本 |
| 2 | **三值狀態** | `docs/handoff-log.md` 各分節的狀態行從兩值擴成三值：`狀態：進行中`／`狀態：完成`／`狀態：不適用`。標 `不適用` **MUST 同時寫理由與決定者**（`狀態：不適用（理由：<一句話>／決定者：<誰>）`），**缺任一項就退回當「未做」** |
| 3 | **不可裁剪下限** | **實作（Phase 5）與測試（Phase 6）永遠不能標 `不適用`。** 超出宣告模式範圍的裁剪要停下來問人，**不得自己擴大解釋** |

**既有階段例外**：`release-handoff/SKILL.md` 明訂本次變更不需部署時可將 Phase 7 標不適用；這是既有條件式例外，不是可任意裁剪其他階段的許可。其餘超出模式範圍的裁剪仍須人的明確決定，且不得突破 Phase 5／6 下限。合法不適用後的入口判定與缺欄位處理 → `../sdlc-entry.md`「階段完成狀態的判定」。

## 三種模式（固定表，不可增刪）

| 模式 | 宣告檔寫什麼 | 跑什麼 | 給誰 |
|---|---|---|---|
| **全跑** | `mode: full` | 九關都跑 | **預設值**。全新構想 |
| **演進** | `mode: evolution` | Phase 1-2（需求發想／需求分析）以 `change-request` 的輕量 spec 取代；Phase 4 恆為不適用；**Phase 3 起照跑** | **日常主力**。既有系統加功能、改 schema |
| **受規管** | `mode: regulated` | 九關都跑 ＋ 額外證據（每關的自決與猜測清單 MUST 落檔保留） | 需要留稽核軌跡的改動 |

**為什麼要有「演進」**：這是絕大多數工作的型態，卻一直沒有名字——每次都要臨場重新判斷「這次要不要回第一關」。給它名字並宣告化，判斷就不用重來一次。

**為什麼不放「原型」模式**：聽起來合理，但「只是原型」是實務上最常被濫用的理由，而且很多原型最後上線了。它會變成**跳過設計關的正當理由**，而介面與資料結構決策正是最貴的返工來源。真要探索用 `converge`——純討論、不設 exit criteria，那才是它的正職。

## 宣告檔建立與維運交接時機

**主責在 Phase 7 成功上線、交接 Phase 8 時，補查在 Phase 8 接手時；不等到第一次 change-request，也不等維運結束。**

- **Phase 7**：production 已上線且煙霧測試綠燈後，MUST 檢查 `docs/sdlc-mode.md`。缺檔時，依使用者已確認的後續模式建立宣告；一般增量維護建議 `mode: evolution`，並記錄理由與決定者。已有明確決定就直接落檔，不重複詢問；尚無決定則在交接時確認，不能自行填造決定者。已存在的合法宣告可沿用；從 `full` 切換到 `evolution` 或修改 `regulated` 等既有模式，都必須有使用者明確決定。
- **Phase 8**：接手已上線系統時先補查；缺檔就依相同規則確認並建立，非法值或缺理由／決定者則補正。已有合法宣告且沒有模式變更決定時保留原檔。補查完成後再分流下一筆維護工作，不等待 Phase 8 結束。
- Phase 7 的交接紀錄（或 Phase 8 補查的 `docs/feedback-log.md`）MUST 記錄宣告檔連結、採用模式與決定依據。缺檔／待確認時，記錄待辦，不得宣稱模式交接已完成；實際上線結果仍如實記錄。
- 未上線、煙霧測試失敗／退版、或 Phase 7 不適用，均不得據此自動建立或切換為演進模式。若系統原已上線，由 Phase 8 補查承接。
- 模式切換只適用後續工作，不重寫已完成的創世階段、歷史狀態或驗收證據。沒有有效宣告仍依既有預設及本檔「既有專案第一次採用」例外處理；`change-request` 僅讀取宣告，缺漏時提示交接責任，不再於分診後自動建立。

## 宣告檔格式

`docs/sdlc-mode.md`，三行：

```
mode: evolution
理由: 既有系統的增量變更，需求與使用者情境早已確立
決定者: <人名或角色>
```

⚠ **`mode:` 只能是上表三個值之一**。寫了表以外的值 → 當作沒有宣告檔（＝全跑），不要自行解讀。

## 這條不變式管不到的一種情況

**既有專案第一次採用這套流程**時，它缺的那些檔**不是「還沒做」**——是系統早就做完了，只是當初沒用這套流程記錄。這個情境由 Step 0 的「演進模式」路徑處理（用程式碼現況當基線、一邊做事一邊補 `docs/`），**不需要先寫宣告檔**，也不受本不變式管。

兩者的分界：不變式管的是**已經在 pipeline 裡**的專案；老專案首次進場走的是入場判斷，是另一件事。
