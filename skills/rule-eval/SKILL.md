# Eval — 驗規則本身有沒有效

⚠ **這一份驗的是「規則」，不是「產品」。** 產品對不對走測試關；這裡問的是：**規則改完之後，執行者照著做會不會做對事。**

**為什麼需要它**：規則是寫給人與 AI 讀的文字，改壞了不會有任何東西亮紅燈。一份自相矛盾的規則跟一份好規則，在檔案系統裡看起來一模一樣。

## 一條原則

> **驗證的價值不在於它會通過，在於它會失敗。**

一個永遠會過的檢查等於沒有檢查。所以本檔的每個動作都圍繞同一件事：**先證明這個檢查抓得到錯，再拿它去驗。**

## 怎麼跑（三步）

### 1. 動手改之前，先寫下你要驗什麼

一筆一個場景，四欄：

```
場景：什麼情況會觸發這條規則
預期：執行者應該做出什麼行為
實際：<改完之後填，MUST 引用檔名與行號的原文>
判定：符合 / 不符合 + 為什麼
```

**「實際」欄只寫「規則存在」不算數**——要引用原文。**沒有引文的通過宣稱一律無效**，這是本檔唯一的硬規則。

### 2. 改完之後，用「故意弄壞」證明檢查有效

把你剛加的規則**反向做一次**（或把它刪掉），看你的檢查會不會抓到。

- 抓到 → 這個檢查是真的
- 沒抓到 → **這個檢查是裝飾**，重寫它

⚠ 這一步最常被跳過，而它正是唯一能區分「真檢查」與「假綠燈」的動作。

### 3. 找一個不知道你改了什麼的人（或 agent）覆核

**MUST 由沒有參與這次修改的角度執行**，而且**不要給他你的修改說明**——只給他規則檔與場景。

理由：你知道自己想表達什麼，所以你讀自己寫的規則永遠讀得懂。**會漏掉的正是「別人會怎麼誤讀」**，而那才是規則實際運作時會發生的事。

## 該驗哪些面向

不必每次全跑，挑跟這次改動有關的：

| 面向 | 問題 |
|---|---|
| **能不能執行** | 照這條規則走，走得到終點嗎？有沒有哪一步接不上下一步 |
| **判得出來嗎** | 兩個人讀同一條規則，會不會給出不同答案 |
| **會不會互相矛盾** | 這條規則跟別處那條同時成立嗎（**同一件事被寫在兩個地方就是高風險**）|
| **邊界守得住嗎** | 有沒有辦法照著字面走，卻繞過本來要擋的東西 |
| **範圍會不會爆** | 這條規則會不會讓執行者順手做超出範圍的事 |
| **讀它要花多少成本** | 執行者為了判斷一件事，要讀幾個檔 |

## 案例放哪

**具體案例、分數、歷史紀錄一律放你自己的環境**（`CLAUDE.md`／`AGENTS.md` 綁定層指定的位置），**不放進本檔也不放進規則包**——案例綁著各自的技術棧與團隊慣例，跟著規則包發出去對別人沒有意義，而且會變成第二份說法。

**本檔只定義方法。**

## 停止條件

- 同一條規則驗了兩輪還是判不出來 → 那不是驗證問題，是**規則本身判準模糊**：登記一筆框架缺陷（位置 → `../sdlc-orchestrator/references/framework-defects.md`，證據欄必填），不要繼續驗
- 發現「檢查會過但行為明明是錯的」→ 先修檢查，再驗規則。假綠燈比沒有檢查更危險，因為它會讓人停止懷疑
