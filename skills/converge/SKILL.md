# Converge — 需求收斂前哨站（Pipeline 外，不計入 9 份 SDLC skill 編制）

不管是新構想還是 bug，先進本流程討論「問題是什麼、要不要做」，講清楚才分流到 `product-discovery`/`change-request`/`debug`。比照 `debug` 的既有前例，本流程不是 SDLC 8 階段裡的一個 phase，只在需求不明確、需要討論時才會被觸發，不是每次任務都會經過的固定編制。

## 觸發條件
- 不確定這是全新構想，還是既有系統的問題／bug
- bug 不知道 root cause 或詳細需求在哪
- 還沒決定要不要做

## 不觸發
- 問題已經明確 → 直接進 `product-discovery`（全新構想）／`change-request`（既有系統的變更）／對應的既有開發流程
- 問題已明確，只是技術根因不明 → `debug`（root cause 調查是 `debug` 既有工作，這裡不重複造）

## 提問規則
向使用者釐清問題時 **MUST 選項化**：把你推測得出的可能性做成 2-4 個具體選項（最可能的放第一個並標「建議」），使用者勾選或回編號即可；自由補充永遠允許。猜不出來的才開放問，禁止純開放式問題轟炸。

**充分性與自決揭露 MUST 依 `../sdlc-orchestrator/references/questioning-sufficiency.md`**：追問到**維度覆蓋表每一列都標「已答」或「使用者說不適用」**才算問完（不是「使用者沒再補」——那由執行者控制取樣；還有任何一列是「進行中」或「未走」都不算）；抽象答案 MUST 追具體實例；動手前先列出「我打算自己決定的事項清單」讓使用者可以拉回。

## 流程
純討論，不定義正式編號步驟、不設 exit criteria。AI 可唯讀調查（讀 code / log / 既有文件）幫助釐清問題，**MUST NOT 修改 DB／程式碼**——這階段還沒確定要不要做、往哪個方向做，不能動手。

討論方向可包含：
- 這是全新構想，還是既有系統的問題／bug？
- 問題到底是什麼？有沒有具體的 symptom／repro steps／expected-vs-actual？
- 要不要做？為什麼？

**來源先行**：唯讀調查若帶出使用者沒提過的專案／檔案，**MUST 先列「我跑了什麼命令、讀了什麼檔」再講結論**，不可把調查結果直接端成選項——否則使用者不知道資料從哪冒出來，也無從判斷可不可信。

**掃描義務與舊專案定位**：使用者沒指名專案時，**MUST 先掃專案根目錄找同主題既有專案**再判創世／演進（否則會重做一個已存在的系統）。掃到的舊專案是**知識輸入（前車之鑑），不是路由依據**——MUST 問使用者「要接續它，還是只當參考」，NEVER 預設偏向接續。

⚠ **讀到既有程式碼只能得到「它這樣寫」，不等於「這樣做可行」**——後者需要測試證據。引用舊專案的做法時 MUST 標注有無測試證據，並自行補上獨立推導與驗收條件。

**否證優先**：已有同主題舊專案時，收斂的關鍵動作是**把使用者陳述的痛點逐條對舊專案已明文排除或做不到的部分比對**——被明文排除的痛點，往往就是新方向的所在。這比再多問幾個開放問題有效。

## 退出條件
使用者明確確認「可以照這個方向走」才算完成——不因為改動範圍看起來小就有 Lead 自主捷徑跳過確認。**同時 MUST 確認共識摘要的落檔位置**（見下「產出」），只有對話紀錄不算收斂完成。

**⚠ 硬性關卡**：收斂前 **MUST 先落一張維度覆蓋表**（十一支維度逐列標「已答／進行中／使用者說不適用／未走」→ `../sdlc-orchestrator/references/questioning-sufficiency.md` 規則一）。**表上只要還有「未走」或「進行中」就不算收斂完成，MUST NOT 分流到下一站。** 本流程雖然純討論、不設正式 exit criteria，但「問夠了沒有」這件事**不得由執行者自評**——沒有覆蓋表就分流，等於把猜測留給下游 phase 去撞。
**收斂前 MUST 另列「殘餘猜測清單」並清空**（規則四 4-A）：本階段最容易猜的是「使用者到底想解哪個問題」「規模多大」「要不要接既有系統」——這三項猜錯，下游整條做白工。清單非空 → MUST NOT 宣告收斂完成。

## 產出
不用正式 exit criteria 表，但**共識摘要 MUST 落成檔案，NEVER 只留在對話裡**——收斂完成後若只有對話紀錄，工作階段一結束就**沒有任何人接得上**：專案資料夾可能還沒建、方向只存在當時在場的人腦裡。分兩種情境：

| 情境 | 落檔方式 |
|------|---------|
| **當場接續下一站** | 由下一站的第一份文件承接，該文件 MUST 含「converge 共識摘要」章節 |
| **不當場接續**（使用者要停／擱置） | MUST 落 `<專案>/docs/converge-summary.md`；專案資料夾尚未存在時**先問使用者資料夾名稱再建**，NEVER 自己編路徑 |

摘要內容固定四項：**問題是什麼／要不要做／為什麼／路由結論**。若調查過既有專案，另附「帶進下一站的既有知識」表（教訓＋`file:line` 出處＋對新工作的意義）——這是舊專案在本流程唯一該留下的東西。

**⚠ 產出物長度治理**：**單一 `docs/` 產出物 MUST ≤200 行**。超過 MUST 按段落語意拆檔，且**主檔 MUST 保留一頁式索引**（哪一段在哪個檔）。**拆檔 MUST NOT 改變既有段落編號**，否則上下游文件的交叉引用會全斷。**天生會長大的段落一開始就獨立成檔**：原始需求清單、維度覆蓋表／提問記錄／自決與猜測、風險清單。

## 下一步
依討論結論路由，**不自動呼叫**，只是提醒：
- 全新構想 → `product-discovery`
- 既有系統的變更 → `change-request`
- 問題已明確但技術根因不明 → `debug`
- 已經夠清楚，不需要再經過其他 SDLC skill → 直接開發

**銜接工單**：本流程自己不開票。討論收斂、確定要做的當下，帶著結論進入下一站，由下一站的第一個持久化動作開票（`product-discovery` 的「開票時機」段；走 `change-request`／直接開發時則依使用環境綁定層的工單規則）。工單系統查不到或綁定層沒指定 → 停下來問使用者要怎麼處理，不要自己編號。
