## D1. 不明確需求的處理機制

兩層決策：①要不要獨立於既有 9 份 skill 之外 ②算不算 SDLC 編制的第10份。

**① 要不要獨立於既有 skill 之外**

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 只有使用者拍板 | 遇到不明確需求時不新增任何流程，直接問使用者「現在該用哪個既有 skill」 | |
| Lead 自行判斷是否夠清楚 | Lead 自己評估問題是否已經夠清楚，覺得夠了就直接進對應 skill，不停下來問 | |
| 依 Tier 分級決定要不要停下來問 | 小改動（Tier 0-1）Lead 自己判斷夠不夠清楚就往下走；大改動（Tier 2-3）才停下來問使用者 | 已撤回 |
| 塞進 `product-discovery` Phase 1，不新開 skill | 不明確需求一律當「全新構想」處理，套用 `product-discovery` 既有的 5 步驟討論流程 | 已撤回 |
| 新增獨立流程，作為三個既有 skill 的共同前哨站 | 不管是新構想還是 bug，先進這個獨立流程討論「問題是什麼、要不要做」，講清楚才分流到 `product-discovery`/`change-request`/`debug` | ✅ |

**理由**：不明確不是 `product-discovery` 的專利——`product-discovery` 觸發條件本身限定「全新構想、從零開始發想」（`SKILL.md:15`），但 bug 修正需求同樣可能「不知道問題跟詳細需求在哪」，需要一個不分 genesis/evolution、兩邊共用的討論前哨站。其餘選項的限制：只靠使用者拍板沒解決「該去問哪個 skill」本身；Lead 自行判斷有誤判風險，一旦動手改 DB/code 就不可逆；這個 gate 守的是「有沒有解對問題」而不是「改動風險大小」，不該隨 Tier 縮放；塞進 `product-discovery` 會漏掉 bug/既有系統這條線。

**② 算不算 SDLC 編制的第10份**

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 算進 9 份 SDLC skill，變成第10份 | 這個新流程也編號、定義正式 exit criteria，跟其他 8 個 phase 一樣走完整流程 | |
| Pipeline 之外的獨立流程，不計入 9 份編制 | 這個新流程沒有編號步驟、沒有 exit criteria，只在需求不明確、需要討論時才會被觸發，跟 `debug`/`check` 這種本來就不算 phase 編制的既有 skill 同一類 | ✅ |

**理由**：9 份 SDLC skill 是每個新任務都會照順序走過的固定編制，這個新流程只在需求不明確、需要討論時才會被觸發，不是每次都會經過的一個 phase，性質上不算進編制。硬算第10份會讓人誤以為這也是一個要走完整流程的 phase，違背「不用定義流程規範」的設計初衷。

**流程設計定案（名稱：`converge`）**：

| 項目 | 內容 |
|---|---|
| 定位 | Pipeline 之外的獨立流程，不計入 9 份 SDLC skill 編制；比照 `debug`/`check` 的既有前例 |
| 觸發 | 問題本身還不明確——不確定是新構想還是既有系統的問題、bug 不知道 root cause 或詳細需求在哪、還沒決定要不要做 |
| 不觸發 | 問題已明確 → 直接進 `product-discovery`/`change-request`/對應開發流程；問題已明確但技術根因不明 → `debug`（root cause 調查是 `debug` 既有工作，不重複造） |
| 流程 | 不定義正式編號步驟/exit criteria——純討論，AI 可唯讀調查（讀 code/log/文件）幫助找出問題 |
| 限制 | 討論期間 MUST NOT 修改 DB/程式碼 |
| 退出條件 | 使用者明確確認「可以照這個方向走」才算完成，不因改動範圍小有 Lead 自主捷徑 |
| 產出 | 不用正式 `docs/*.md` + exit criteria 表；一段共識摘要（問題是什麼、要不要做、為什麼）+ 路由結論（下一步去 `product-discovery`/`change-request`/`debug`/或已夠清楚直接開發） |
| 銜接 D2（工單） | 討論收斂、確定要做的當下順手開 GitLab issue，帶著 issue 號進入下一站 |

**銜接既有 skill 的缺口**：只新增 `converge` 不夠，`debug` 與 `change-request` 現有的「理解問題」步驟都假設問題本身已經講得出來，沒有明講「講不出來時要停下來轉 `converge`」：

| Skill | 現況缺口（file:line 為證） | 要補的出口 |
|---|---|---|
| `debug` | Phase 1「理解問題」（`SKILL.md:14-19`）假設使用者至少講得出 symptom/repro steps/expected-vs-actual，沒有停止條件處理「這些都問不出來」的情況，會直接滑進 Phase 2 開始瞎猜 root cause | Phase 1 停止條件加一句：symptom/repro/expected-vs-actual 問不出來 → 停下來，轉 `converge` |
| `change-request` | 步驟1「取得基線脈絡」（`SKILL.md:29-33`）假設「這次變更是什麼」本身已知，只是要對照既有範圍；連變更需求本身都講不清楚時，步驟2 三選一判斷無從下手 | 步驟1 加同款出口：需求本身講不清楚 → 轉 `converge` |
| CLAUDE.md Step 0／`sdlc-entry.md` | 進場判斷表本身沒有處理「連該走哪條路都判斷不出來」的情況 | 新增一行：問題/需求含糊到判斷不出走哪條路 → 先進 `converge`，共識/路由確定後再回 Step 0 對表 |

## D2. 工單／GitLab issue 機制

三層決策：①用哪個系統 ②開單時機 ③ `system-design` 還要不要另外開票。

**① 用哪個系統**

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 沒有系統，純人工填號 | 不串接任何外部系統，需求文件裡手動編一個像 `TICKET-001` 的識別碼 | |
| 已有系統，docs 引用票號即可 | 用既有的 GitLab issue 號，docs 檔案裡寫上對應的 issue 編號，不寫程式碼串接 | ✅ |
| 已有系統且串接 API | 寫程式呼叫 GitLab API，自動抓票號/狀態、自動回寫 | |

**理由**：GitLab issue 是既有開單習慣，docs 裡引用票號已經達成「可追蹤」的目的；純人工填號的票號背後沒有真實系統支撐，稽核意義有限；API 串接自動化程度最高，但要看有沒有開放 API、投入產出比未知，目前不需要做到這一步。

**② 開單時機**

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| issue 先開，需求發想在其下進行 | 一有想法就先開一張 GitLab issue，後續討論都記在這張 issue 底下 | |
| 討論成熟、確定要做了才補開 issue | 先在 `product-discovery` 步驟1-5 討論（本來就有「不要強行收斂」的空間），確定方向、有共識了，才正式開一張 issue | ✅ |

**理由**：討論階段本來就不產出正式產出物，issue 號自然也該等那個時間點才有意義去記；issue 先開容易讓 tracker 塞滿還沒定案就放棄的想法。**落地位置**：`product-discovery` 的 ticket 欄位不掛在步驟1，掛在 Phase Exit Criteria 通過、確定要往下走、即將產出 `docs/product-discovery.md` 定案版的那個時間點。

**③ `system-design` 步驟16 還要不要另外「開票」**

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 維持現況，`system-design` 步驟16 另外指派 T-01/T-02 這類設計期票號 | Phase 1 開一次 GitLab issue，Phase 3 `system-design` 又生一套獨立的 T-0x 編號，兩套編號系統並存 | 已撤回 |
| `system-design` 步驟16 不開新票，設計拆出來的工作項目掛在 Phase 1 的 issue 號底下 | 全程只有 Phase 1 一次「開票」動作（GitLab issue）；`system-design` 步驟16 照樣把功能拆成後端/前端/DB 等具體工作項目，但這些項目不再各自擁有獨立票號，改成同一個 issue 號底下的子項目（例：「ISSUE-42／後端 API」「ISSUE-42／前端頁面」） | ✅ |

**理由**：兩套編號系統會造成混亂——「開票」這個詞同時指 Phase 1 的 GitLab issue 跟 Phase 3 的 T-0x，容易搞不清楚在講哪一個，也違背「一個需求只有一個追蹤入口」的精神。改成全程只在 Phase 1 開一次票之後，`system-design` 步驟16 的實際工作內容不變（還是要把功能拆成具體工作項目），差別只在於這些項目不再各自擁有獨立票號，而是同一個 issue 號底下的子項目——`handoff-log.md` 追蹤完工狀態的記法從「T-01 完工」改成「ISSUE-42／後端API 完工」。這也讓 D7 的依賴標記規則更直接：本來就是同一張 issue 底下的子項目，判斷要不要標同一驗收批次不需要跨兩個獨立票號比對。**落地時 `system-design` 步驟16 的標題／敘述要從「拆分任務/開票」改成「拆分任務」，拿掉「開票」這個會跟 Phase 1 GitLab issue 混淆的字眼。**

## D3. 測試案例「先過目」審查強度

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 每條都給使用者看 | 不論改動大小，每一條自然語言測試案例寫完都要先給使用者過目確認才能落地成自動化測試 | |
| Lead 自行判斷 | 測試案例寫完 Lead 自己看過就好，不用給使用者看 | |
| 依 Tier 分級 | Tier 0-1（單檔小改動）Lead 自己看過即可；Tier 2-3（安全/共用資料/多模組）MUST 給使用者看過才能落地 | ✅ |

**理由**：跟既有 `agent-budget-table.md` 的風險分級同一套邏輯，也跟 `qa-handoff` 現有「範圍大或涉及安全/共用資料 → 加派 `sdlc-verifier`」規則同方向。每條都給使用者看，量大時會審查疲勞，稀釋真正該仔細看的案例；完全交給 Lead 等於沒有這道防線。這一項審的是「測試案例寫得對不對」，屬於可用改動範圍衡量的執行細節，跟 D1 守的「問題有沒有解對」性質不同，這裡 Tier 分級才成立。

## D4. `change-request` 快速路徑測試描述門檻

**「自然語言測試案例」的定義**：不是程式碼，是開發前先用白話文寫一小段「這功能應該怎麼運作」，例如「呼叫 `/api/items/search` 帶 `type=A`，應該只回傳 A 類項目」。這段話寫在程式碼之前，之後 `qa-handoff` 拿它去對照驗收，不是給開發者自己參考用——就算開發者事後看過自己的 code 才補測試，也不會把「code 現在的行為」誤當成「應該有的行為」。

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| Tier 0-1 全免，Tier 2+ 才要補 | 小改動（例：改一行 log、調一個 config 值、修 typo）維持現在做法，直接開發，不用寫這段描述；Tier 2 以上的改動（例：新增一個 API 端點、改資料庫查詢邏輯）在動手寫程式之前，MUST 先寫好這段白話描述 | ✅ |
| 不分 Tier，全部都要補 | 不論改動多小，`change-request` 快速路徑的每一筆都要先寫這段描述才能開發 | |
| 完全不加，交給 `qa-handoff` 自己判斷 | `change-request` 快速路徑維持現狀不變，要不要額外仔細驗收由 `qa-handoff` 自己臨場判斷 | |

**理由**：`change-request`「在既有範圍內」快速路徑現況完全跳過 `dev-setup`（`dev-setup` 是原本負責寫這段描述的地方），等於這條快速路徑完全沒有 spec-first 測試保護。「不分 Tier 全部都要補」會讓改一行 log 這種小事也要多一道手續，拖慢快速路徑存在的意義；「完全不加」會讓新增 API 端點這種風險已經不小的改動繼續沒有保護。門檻沿用跟 D1/D3 一樣的 Tier 分級，定義沿用 `agent-budget-table.md` 既有的表，不用另外發明一套新標準。

## D5. `system-design` DB schema 禁用 FK

**規則**：`system-design` 步驟12 MUST NOT 使用 DB-level `FOREIGN KEY` constraint。

**證據**：`後端主專案` 全專案 `@JoinColumn`/`@ManyToOne`/`@OneToMany` 命中 0 筆；`sql/postgresql/<某張表>.sql` 等 6 個 migration 檔裡「foreign key」相關命中全部只是欄位 comment（例：`parent_oid` 註解「foreign key reference to the parent entity OID」），沒有一筆是真正的約束——這是既有生產慣例，不是新發明。`測試專案的 docs/db-schema.md:40` 的 `<子表>_id | uuid, FK → <父表>.id` 是違反既有慣例的實例。

**具體規則**：關聯欄位用純 ID 型別、不宣告 `REFERENCES`；邏輯關聯寫進欄位說明（沿用 `parent_oid` 寫法）；關聯欄位仍 MUST 加索引——沒有約束不代表不用索引。

**怎麼確保這條規則真的被遵守**：

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| Lead 現在手動改 `db-schema.md` | Lead 直接 Edit 測試專案那份文件，把 FK 寫法改掉 | 已撤回 |
| 只在步驟12 補文字規則，靠自己記得不要設計 FK | 規則寫進 skill 敘述文字裡，但沒有一個明確的步驟去驗證產出的 schema 真的沒有 FK——跟其他文字規則一樣，容易被漏看 | 已撤回 |
| 步驟12 加明確的檢查機制，改好後重跑驗證 | 在 phase-exit-criteria 加一條可勾選的具體檢查項——「逐一檢查所有關聯欄位，確認沒有宣告 `FOREIGN KEY`/`REFERENCES`」；skill 改對之後，重新跑一次步驟12，讓這個檢查機制實際跑過該測試專案，抓出並修正現有的 FK 違規 | ✅ |

**理由**：「重跑」是必要動作，但重跑要有效，前提是 `system-design` skill 必須先寫對——也就是要有一個明確可驗證的檢查機制，不是只補一句文字規則指望沒人漏看。規則本身跟「怎麼確保被遵守」要配套：skill 先寫對，重跑才有意義。測試專案現有的 `db-schema.md` 透過這個機制在重跑步驟12 時被抓出來修正，不是 Lead 手動代勞——這樣才是真的驗證規則有沒有生效，而不是人工修正舊產出物假裝規則已經落地。

## D6. API 規格要有具體 JSON 範例

**規則**：`system-design` 步驟13 MUST 附完整請求/回應 JSON 範例，不只成功案例，至少一個錯誤回應範例 + 狀態碼 + 若有 auth 則附 header 範例；範例值用真實感資料，不是 placeholder 型別字串。

**證據**：`測試專案的 docs/api-spec.md` 兩個端點都只有成功案例、型別是 `"string"`/`0.0` 這種 placeholder，沒有錯誤格式/狀態碼/認證範例——現況只滿足 phase-exit-criteria「錯誤處理格式一致」這種抽象敘述，沒有具體到能直接照做的程度。

## D7. 功能拆分不能拆到太小、無法獨立測試

原話：「功能拆分不能拆到太小無法獨立測試，像是前端一定要有後端才能測就是其中一項，等於就是有依賴的功能一起做」。

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 允許自由拆，各自獨立驗收 | 拆出來的每個工作子項目都是獨立單位，各自完工各自驗收，不管彼此之間有沒有依賴關係 | |
| 有依賴的功能，開發可以分開、驗收要一起做 | 依賴的子項目開發時仍照既有的先後順序做（例如介面供應方先行），但要等依賴的部分都做完才能一起宣告「驗收通過」，不能各自分開喊過 | ✅ |

**理由**：以「前端一定要後端才能測」為例——允許自由拆的問題在於依賴的部分沒做完，這部分就只能用假資料/假設混過驗收，掩蓋沒真的測到整合後的行為。能用 mock/contract test 獨立驗收的部分，仍然可以拆開平行做，不是「有依賴就整包合併」，只是驗收要一起做，不能各自分開喊過。

**精確執行點在 `system-design` 步驟16（拆分任務）**——問題的顆粒度其實在 `requirement-scoping` 步驟6（收斂功能清單）就已經決定：功能清單切太細，切出依賴其他服務/設定的項目，到步驟16 拆工作項目時才會冒出這個問題；但步驟6 當下還沒有實際的元件/服務邊界，沒辦法精確判斷哪些項目真的互相依賴，所以拍板點還是留在 `system-design` 步驟16——依 D2③，這裡標記的是同一張 Phase 1 issue 底下的子項目要不要同批驗收。

## D8. 測試描述根據需求規格書設計

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 根據 `system-design` 的技術方案設計 | 測試描述照著 API/DB 規格、票的驗收標準寫，驗證做出來的東西符合設計文件 | 已撤回 |
| 根據 `requirements-spec.md` 需求規格書設計 | 測試描述照著需求規格書寫，驗證做出來的東西符合當初的需求；技術細節（API路徑、欄位名稱）才對照 `system-design` 填進去 | ✅ |

**理由**：只根據技術方案驗證，等於只驗證「做出來的東西符合設計文件」——如果設計文件本身就偏離了需求，這樣測不出來。根據需求規格書才能驗證「做出來的東西符合當初要的需求」，這才是驗收測試真正該守的底線。

**寫在哪個階段**：`dev-setup`（Phase 4，正式寫程式之前），當作第4項產出（原本產出3樣：專案骨架、版控清單、開發排程）。

**技術細節（次要）**：`SDLC` 全流程有一份主文件，把8個階段總共35個步驟從頭到尾連續編號（1號排到35號）。這段測試描述不新增一個新的編號步驟，掛在 `dev-setup` 既有的第20號步驟後面就好——如果硬要插一個新編號，後面所有步驟都要跟著往後挪一號，全部9份skill文件裡提到步驟編號的地方也都要跟著改，代價太大；做法比照「品質門禁」的疊加方式（品質門禁也不是這35步驟裡的正式一號，一樣是掛在既有步驟之上）。

## D9. qa-handoff 依照測試描述寫真正的測試，開發者不能自己補

| 選項 | 這個選項實際上怎麼做 | 選中 |
|---|---|:---:|
| 開發者（`implementation-handoff`）自己補寫驗收測試 | 功能開發完後，開發者順手自己補一份驗收測試 | 已撤回 |
| `qa-handoff` 依照 `dev-setup` 的測試描述寫真正的測試，開發者不參與 | `dev-setup` 產出的白話測試描述（D8）是草稿，`qa-handoff` 拿它、對照 `requirements-spec.md` 需求規格書覆核，寫成真正可執行的單元/整合測試；開發者從頭到尾不寫這段測試 | ✅ |

**理由**：開發者自己補測試，測試容易不自覺照著自己寫的 code 邏輯走，變成「一定會過的測試」——功能其實不符合規格時，這種測試反而測不出來，這正是最初提出的意見要堵的漏洞。`qa-handoff` 獨立撰寫，且依據是 `dev-setup` 在程式碼出現之前就已經寫好、定案的描述（不是憑印象自己想），才能避免這個問題。

**銜接 D8**：`dev-setup` 的描述只是「草稿」，`qa-handoff` 寫真正的測試時，仍要對照 `requirements-spec.md` 原始需求規格書覆核，不能只信 `dev-setup` 的措辭——避免 `dev-setup` 寫的時候用詞不小心貼近某種特定實作方式，`qa-handoff` 照抄等於沒有真的獨立驗證。

**對 `implementation-handoff` 的對稱限制**：開發者 MUST NOT 自行撰寫或修改驗收測試（單元測試以外，涉及驗收/spec對齊的測試都不行）——這段測試的撰寫方是 `qa-handoff`，不是開發者自己。
